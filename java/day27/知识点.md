## 一、先给昨天那坨代码找个"家"：DAO 分层

昨天你是"一个方法里连库 + 拼 SQL + 读结果"混着写。人一多、SQL 一多就乱了。真实项目是这么分层的：

```
main / 界面 / 业务代码     ← 只管"要什么"（调方法，不碰 SQL）
        ↓ 调用
DAO 层（Data Access Object）  ← 只管"怎么跟数据库说话"（SQL 都在这）
        ↓ 操作
实体类（entity / bean）        ← 只管"数据长什么样"（Student）
```

拿你今天的代码对号入座：

| 层次 | 今天的类 | 职责 |
|---|---|---|
| 实体 | `Student` | 三个字段 + getter + toString，**一行数据一个对象** |
| 转换 | `RowMapper.mapRow(rs)` | 把 `ResultSet` 的一行 → 一个 `Student`（**只写一次**）|
| DAO | `StudentDao` / `BatchDao` / `ScoreService` | SQL 全在这一层 |
| 入口 | `main` | 用自己的办法调 DAO，打印给人看 |

**为什么值得这么分？**

1. **SQL 集中**：以后要改 SQL（加个条件、换个表），只进 DAO 层找，不用满项目翻
2. **复用**：`mapRow` 写一次，Ex1/Ex3/Review 都在用
3. **换数据库不太疼**：业务代码不认识 SQL，改底层只动 DAO

> 类比：DAO 就像**公司前台**。你（业务）跟前台说"我要找张三"，你不用知道他在几楼、怎么走（SQL）；前台（DAO）负责跑腿。换办公室了，你说话方式不用变。

## 二、实体类为什么必须有 `toString()`

```java
Student s = RowMapper.one(conn, "张三");
System.out.println(s);       // 不写 toString → Student@1b6d3586（对象地址，没法看）
```

`toString()` 写了之后 → `张三 88 一班`。**Day10 学过的 Object 方法，今天开始天天用**：调试、打印、日志全靠它。

⚠️ 顺带一个坑：**别用 `String` 拼 SQL 列表**，也别把 `toString()` 拿去做 SQL 参数——它的作用是"给人看"，不是"给程序用"。

## 三、⭐ 今天的心脏：事务（Transaction）

先看一个会出事的场景——**转账**：

```java
// 天真写法：两条 UPDATE 各管各的
扣钱(张三, 400);      // ① 张三 1000 → 600
加钱(赵六, 400);      // ② 如果这行之前断电/报错/网络断了……
```
结果：**钱凭空消失了 400**。第 ① 步已经生效，第 ② 步没执行。这就是"没事务"的真实事故。

### 事务就是"全退保险"

```java
conn.setAutoCommit(false);   // ① 关掉自动提交：之后的 SQL 都攒着，不立刻生效
扣钱(张三, 400);
加钱(赵六, 400);
conn.commit();               // ② 一起生效（到这里才真正落库）
```

中间任何一步出问题：

```java
catch (SQLException e) {
    conn.rollback();         // ③ 全部撤销：扣的钱"还"回来
    throw e;
} finally {
    conn.setAutoCommit(true);  // ④ 把 conn 恢复原样（它是 main 借给你的）
}
```

**三个关键点**：

| 方法 | 作用 | 一句话 |
|---|---|---|
| `setAutoCommit(false)` | 关掉自动提交 | "从现在起我说的先别急着办" |
| `commit()` | 提交 | "就这些，一起办！" |
| `rollback()` | 回滚 | "算了，全部取消，回到刚开始" |

> 类比：**转账 = 寄快递**。`setAutoCommit(false)` 是把"扣钱"和"加钱"两个包裹先放车上，`commit()` 是发车；中途发现地址写错了就 `rollback()`——所有包裹原路退回，**绝不会出现"钱扣了、对方没收到"**。

### 不写事务的四个后果（面试常问）

1. **脏数据**：一半生效一半没生效 → 账不平（对账少了 400）
2. **别人会看到中间状态**：你扣了钱还没加，别人这时查余额，看到的是"钱不见了"
3. **出错了没法收拾**：程序崩了，数据就烂在那里
4. **并发下更乱**：两个人同时转账，没事务就可能算错余额

### ⚠️ 最经典的两个错

| 错误 | 现象 |
|---|---|
| 只写了 `setAutoCommit(false)`，**忘了 `commit()`** | 程序跑完**数据一点没变**（看着像"没执行"，其实是没提交）|
| 在 try 里 `commit()` 了，但 catch 里没 `rollback()` | 出错后连接还挂着未提交事务，下一个人拿到这连接就看到脏数据 |

## 四、失败怎么"通知"调用方？三种风格

今天三道题故意用了三种，项目里都常见：

| 风格 | 写法 | 用在哪 | 适合 |
|---|---|---|---|
| **抛异常** | `throw new SQLException("余额不足")` | Ex4 `transfer` | ✅ 最推荐：调用方**必须**处理，忘不了 |
| **返字符串** | `return "余额不足"` | Ex5 `tryTransfer` | 结果要显示给人看时方便 |
| **返 boolean** | `return false` | Review `transfer` | 最简单，但**失败原因丢了** |

💡 **经验法则**：能被调用方补救的失败（余额不足、账户不存在）用异常；纯"是/否"判断（存不存在）用 boolean。

## 五、批量操作：addBatch / executeBatch

一次转 1000 行，按行执行 = 1000 次网络往返。批量是**打包送一趟**：

```java
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    for (Student s : list) {
        ps.setString(1, s.getName());     // 填参数
        ps.setInt(2, s.getScore());
        ps.setString(3, s.getClassName());
        ps.addBatch();                    // ① 放进"待发货"清单（不执行）
    }
    int[] res = ps.executeBatch();        // ② 一次性全发（返回每行的结果数组）
}
```

⚠️ 坑：`executeBatch()` 返回的是 **`int[]`**（每一行一条结果），不是总行数。要总数就循环累加。

## 六、常见坑汇总

| 坑 | 现象 | 正解 |
|---|---|---|
| 事务忘了 `commit()` | 数据没变 | `commit()` 必须写 |
| `rollback()` 写错位置 | 出错后脏数据残留 | 写在 `catch` 里 |
| 忘了恢复 `setAutoCommit(true)` | 借来的 conn 状态被改坏 | 写在 `finally` |
| DAO 里查不到返回 `null` | 调用方每处都要判空，忘了就 NPE | 列表类返回**空 List**（size 0）|
| `SELECT` 用 `executeUpdate()` | 报错或行数没意义 | Query 拿结果，Update 拿行数 |
| 实体类不写 `toString()` | 打印出 `Student@1b6d3586` | 一定要写 |
| 事务里做 `System.out.println` 校验 | 打印"成功"其实已回滚 | 打印放在 commit 之后 |
