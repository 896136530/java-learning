## 第 2 步（5 分）答案：顺序与边界

### 2.1 八步顺序

```
Filter.doFilter 前置 → DispatcherServlet → preHandle → Controller(→Service)
   → postHandle → 视图渲染 → afterCompletion → Filter.doFilter 后置
```

实测日志证据（答案版原文）：

```
[Filter① OrderProbe] 进入 GET /public/ping
[Filter② Cost] GET /public/ping → 200，耗时 87 ms
[Filter① OrderProbe] 退出 /public/ping
```

### 2.2 轨迹把"谁在谁里面"画出来了

```
[Filter①] 进入 → [Filter② Cost] 进入 → [拦截器 Trace] preHandle（handler=HandlerMethod）
→ [拦截器 Trace] postHandle → [拦截器 Trace] afterCompletion（耗时 68 ms，异常：无）
```

### 2.3 三道判断题

**第 1 问：`/abc` 走不走拦截器？→ 走。**
实测 `handler=ResourceHttpRequestHandler`（不是 `HandlerMethod`）。
原因：SpringBoot 给静态资源注册了 `/**`，没匹配到 Controller 的 URL 都会落到它头上；
它发现文件不存在 → 抛异常 → 被统一处理器接住 → 404。
⚠️ 推论：`preHandle` 里**不能**直接把 `handler` 当 `HandlerMethod` 用（会 NPE）。

**第 2 问：拦截器里抛异常，统一异常处理器接不接？→ 接。**

```json
HTTP 409
{"code":"409","message":"拦截器里故意抛的异常（preHandle）","data":null,"fieldErrors":null}
```

日志：`WARN GlobalExceptionHandler : 业务异常：code=409, http=409, message=拦截器里故意抛的异常（preHandle）`
（原因：`preHandle` 在 `DispatcherServlet.doDispatch` 的 try 块里 —— **Spring 6 会接住**；
老博客里"拦截器异常不走 @ControllerAdvice"是 Spring 3/4 的结论。）

**第 3 问：`preHandle` 返回 false 之后呢？**

实测（`GET /sku` 不带 token 的轨迹）：

```
[Filter①] 进入 → [Filter②] 进入 → [拦截器 Trace] preHandle
→ [拦截器 Auth] preHandle → 拒绝（没带 token） → [拦截器 Trace] afterCompletion（异常：无）
→ [Filter②] 退出 → [Filter①] 退出
```

- 后面注册的拦截器（Throw）`preHandle` **不执行**；
- `postHandle` **完全不执行**（一次都没有）；
- **已经通过的**拦截器（Trace）的 `afterCompletion` **照样执行**。

## 第 4 步（15 分）答案：401 的 JSON 信封

### 关键代码（`AuthInterceptor`）

```java
/** ⭐ 统一的 401 出口 —— 两个 401 分支共用，避免两处写法不一致 */
private void writeUnauthorized(HttpServletResponse response, String message) throws IOException {
    response.setStatus(401);                                        // ① 状态码
    response.setContentType("application/json;charset=UTF-8");       // ② 内容类型（charset 不能少）
    Result<Void> body = Result.fail(ResultCode.UNAUTHORIZED, message);
    response.getWriter().write(objectMapper.writeValueAsString(body));   // ③ 用 Jackson 序列化
}
```

调用处：

```java
if (token == null || token.isBlank()) {
    log.warn("[Auth] 拒绝：{} 没有带 {} 请求头", uri, TOKEN_HEADER);
    recorder.record("[拦截器 Auth] preHandle → 拒绝（没带 token）");    // 顺手记进轨迹（可选）
    writeUnauthorized(response, "未登录或登录已过期，请在请求头带上 X-Token");
    return false;
}

String username = tokenStore.findUsername(token);
if (username == null) {
    log.warn("[Auth] 拒绝：token 无效（{}）", token);
    recorder.record("[拦截器 Auth] preHandle → 拒绝（token 无效）");
    writeUnauthorized(response, "token 无效或已过期，请重新登录");
    return false;
}
```

### 实测对照

| 场景 | 交付版 | 答案版 |
|---|---|---|
| `GET /sku` 不带 token | 401 / **0 字符** | 401 / **83 字符（117 B）** `{"code":"401","message":"未登录或登录已过期，请在请求头带上 X-Token","data":null,"fieldErrors":null}` |
| `GET /sku` 带无效 token | **500** | 401 / **76 字符（100 B）** `{"code":"401","message":"token 无效或已过期，请重新登录",...}` |

> ⭐ 两处 401 的 message 不同、信封形状相同 —— 客户端只看 `code` 就能判断。

### 常见扣分

| 扣分点 | 现象 |
|---|---|
| 只 `setStatus(401)` | 响应体 0 字节（就是交付版的样子）→ 直接 0 分 |
| 忘了 `charset=UTF-8` | 中文乱码，但状态码对 → 扣 3 分 |
| 只改了一个 401 分支 | 不带 token 对、无效 token 还是 0 字节 → 扣 4 分 |
| 手拼 JSON 拼错（漏引号/转义） | body 不是合法 JSON → 扣 5 分 |

## 第 5 步（20 分）答案：让拦截器成为 Spring Bean

### ① `AuthInterceptor`：`@Component` + 构造器注入

```java
@Component                                                            // ⭐ 交给 Spring 管
public class AuthInterceptor implements HandlerInterceptor {

    private static final Logger log = LoggerFactory.getLogger(AuthInterceptor.class);
    public static final String TOKEN_HEADER = "X-Token";

    private final TokenStore tokenStore;         // ⭐ final：漏传就编译不过
    private final ObjectMapper objectMapper;
    private final TraceRecorder recorder;

    public AuthInterceptor(TokenStore tokenStore, ObjectMapper objectMapper, TraceRecorder recorder) {
        this.tokenStore = tokenStore;
        this.objectMapper = objectMapper;
        this.recorder = recorder;
    }
    // ...
}
```

**删掉**原来的 `@Autowired private TokenStore tokenStore;`（字段注入既没有 final 保护，也不是必须的）。

### ② `WebMvcConfig`：注入进来，不再 `new`

```java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    private final TraceInterceptor traceInterceptor;
    private final AuthInterceptor authInterceptor;

    public WebMvcConfig(TraceInterceptor traceInterceptor, AuthInterceptor authInterceptor) {
        this.traceInterceptor = traceInterceptor;
        this.authInterceptor = authInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(traceInterceptor).addPathPatterns("/**");
        registry.addInterceptor(authInterceptor).addPathPatterns("/**")
                .excludePathPatterns("/login", "/public/**", "/trace/**");
        registry.addInterceptor(new ThrowInterceptor()).addPathPatterns("/trace/throw/**");
    }
}
```

### 实测对照

| 请求 | 交付版 | 答案版 |
|---|---|---|
| `GET /sku` 带 token | **500**（71 字符） | **200**（**275 字符**，3 条 SKU） |
| `GET /sku` 带无效 token | **500** | **401**（76 字符） |
| `POST /sku {}` | 500 | **400**（145 字符，4 条 `fieldErrors`） |
| `POST /sku` code=abc | 500 | **400**（109 字符）`{"code":"商品编码格式不对（正确格式：SKU-0001）"}` |
| `POST /sku` stock=800 | 500 | **400**（97 字符）`{"stock":"库存不能超过 500"}` |
| `POST /sku` 正常 | 500 | **200**（119 字符）`data.id = 4` |
| `POST /sku/outbound?id=2&count=100` | 409（93 字符，本来就没被拦） | **409**（同样 93 字符） |
| `DELETE /sku/2` | 409 | **409**（85 字符） |
| `PUT /sku {"id":1,"price":99}` | 500 | **200**（130 字符，price→99、title 不变） |
| `PUT /sku {"price":99}` | 500 | **400**（94 字符）`{"id":"更新时必须指定 id"}` |
| `GET /sku/search?limit=0` | 400（没被拦，所以一直是对的） | **400**（98 字符）`{"limit":"limit 至少是 1"}` |

日志证据（答案版）：

> ⭐ 这一步的"标准答案"不只是"能用"，而是**依赖注入方式和 `@Component` 注册方式都对**：
> 拦截器是 Bean（`@Component`）+ 注册处注入（构造器），这两条缺一不可。

### 常见扣分

| 扣分点 | 现象 |
|---|---|
| 只加 `@Component`，`WebMvcConfig` 还 `new` | 依然 500（Bean 有两个实例，注册的是没注入的那个）→ 扣 12 分 |
| 用 `@Autowired` 字段注入但仍 `new` | 依然 500 → 扣 12 分 |
| 改成 `@Component` 但注册处忘了注入 → NPE | 启动就失败（构造器参数拿不到）→ 自己会发现 |
| 顺手把 `ThrowInterceptor` 也改成 Bean 却还 `new` | 能跑（它没依赖），不扣分，但**风格不一致** |

## 第 7 步（15 分）答案：清理 ThreadLocal

### ① 当前登录用户 → `AuthInterceptor.afterCompletion`

```java
@Override
public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                            Object handler, Exception ex) {
    CurrentUser.clear();          // ⭐ 谁 set 谁 clear
}
```

### ② 执行轨迹 → **最外层过滤器的最后一行**

```java
// OrderProbeFilter.doFilter
chain.doFilter(request, response);

recorder.record("[Filter① OrderProbe] 退出");
log.info("[Filter① OrderProbe] 退出 {}", httpRequest.getRequestURI());

recorder.clear();                 // ⭐⭐ 整个请求的最后一句代码
```

**`TraceInterceptor.afterCompletion` 里只记录、不清理**（它清不干净，见下）。

### ⭐⭐ 为什么不能清在 `afterCompletion`（实测）

第一次我写的就是 `afterCompletion` → 实测残留（原文）：

```
下一次请求的"本次请求(进行中)"里多出 3 行：
[Filter② Cost] 耗时 95 ms  →  [Filter② Cost] 退出  →  [Filter① OrderProbe] 退出
```

原因是执行顺序（⚠️ 关键）：

```
Filter①进入 → Filter②进入 → preHandle → postHandle → afterCompletion → 【clear 在这里】
            → Filter② 记"耗时"、记"退出"   ← clear 之后又写了 3 行
            → Filter① 记"退出"             ← 留在柜子里了
```

**"钱包最后动"的那一层才该负责清理** —— 也就是 order=1 的最外层过滤器。

### 实测对照

| | `currentRequest` 行数 | `lastCompleted.steps` |
|---|---|---|
| 交付版 | 3 → 9 → 16 → 21 → 27 | 4 → 10 → 16 → 22 → 28 |
| 答案版 | **每次都是 3** | **5**（正常）/ **4**（被 401 挡掉）/ **4**（409） |

`CurrentUser` 的验证（诚实说明）：

| 步骤 | 答案版实测 |
|---|---|
| `GET /me` 带 token | 200，`username: "xiaoming"`，thread=`exec-2` |
| 紧接着 `GET /trace/whos` | thread=`exec-3`，`currentUser: null` |

> ⚠️ **这次实测没能验证到"清对了"** —— 因为两个请求落在**不同线程**上，
> 本来就读不到残留（换了线程 = 换了柜子）。
> 反过来也说明：**这类泄漏是"看运气"的**，测试环境可能一辈子看不到，生产上偶发越权才暴露。
> 所以：**轨迹的残留（必然可复现）才是本步的硬指标**；
> `CurrentUser` 请用代码审查确认（`afterCompletion` 里确实调了 `CurrentUser.clear()`）。
> 📌 想让它"必然可复现"，可以把 Tomcat 线程池设成 1（`server.tomcat.threads.max=1`）
> —— 项目里**没有**这么配（那会破坏正常的并发演示），这里仅作提示。

### 常见扣分

| 扣分点 | 现象 |
|---|---|
| `recorder.clear()` 写在 `afterCompletion` | 残留 3 行 → 扣 8 分（**本题的核心考点**） |
| `CurrentUser.clear()` 完全没写 | 代码审查发现 → 扣 5 分 |
| 在 `AuthInterceptor.preHandle` 一开始就 clear | 能跑，但**语义反了**（进去先清、出来不清）→ 扣 3 分 |
| 在 `preHandle` 里 `recorder.clear()` | 本次请求轨迹开头几行永远是空的（自己把刚记的清了）→ 扣 8 分 |
| 两处都不清 | `currentRequest` 一直涨 → 0 分 |

## 第 8 步（15 分）答案：`CostFilter` 记耗时

```java
@Override
public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
        throws IOException, ServletException {

    HttpServletRequest httpRequest = (HttpServletRequest) request;
    HttpServletResponse httpResponse = (HttpServletResponse) response;

    long start = System.currentTimeMillis();                    // 交付版已有
    recorder.record("[Filter② Cost] 进入");
    chain.doFilter(request, response);
    long cost = System.currentTimeMillis() - start;

    log.info("[Filter② Cost] {} {} → {}，耗时 {} ms",
            httpRequest.getMethod(), httpRequest.getRequestURI(), httpResponse.getStatus(), cost);
    recorder.record("[Filter② Cost] 耗时 " + cost + " ms");
    recorder.record("[Filter② Cost] 退出");
}
```

| | 日志 |
|---|---|
| 交付版 | **没有** `[Filter② Cost]` 那一行（只有 NPE 堆栈里的类名） |
| 答案版 | `[Filter② Cost] GET /public/ping → 200，耗时 87 ms`（另一次跑是 248 ms，波动正常） |

答案版完整三行（顺序就是第 2 步的答案）：

> 过滤器**包在外面**，多算了 DispatcherServlet 找 handler、响应渲染等框架开销。
> 这不是 bug。

## 第 9 步（5 分）思考题

**1. Filter 和 Interceptor 的区别？各举一个"只能用我"的场景。**

- **出身**：Filter 是 Servlet 规范（Tomcat 调），Interceptor 是 Spring MVC（DispatcherServlet 调）→ Filter 在外层；
- **能力**：Interceptor 的 `preHandle` 能拿到 `HandlerMethod`（方法 + 注解），Filter 只能拿到 URL；
- **范围**：Filter 管所有请求（含 `/favicon.ico` 这类静态资源），Interceptor 管进 DispatcherServlet 的请求；
- **依赖注入**：拦截器天然是 Spring Bean，过滤器（`@WebFilter` 方式）常常注入不到。

场景：**"按方法上的注解做权限校验"只能拦截器**（`handler instanceof HandlerMethod` → 读注解）；
**"统一改请求/响应编码、包装 body、跨域"只能过滤器**（要在参数被解析之前动手）。

**2. 为什么清理要写在最外层过滤器的最后一行？**

因为 `afterCompletion` **不是最后一句代码**：它跑完之后，控制权回到过滤器链，
`CostFilter` / `OrderProbeFilter` 在 `chain.doFilter` 之后还会记 3 行
（实测残留：`耗时 95 ms → [Filter② Cost] 退出 → [Filter① OrderProbe] 退出`）。
清在 `afterCompletion` → 这 3 行留在柜子里 → 下一个请求（同线程）就串了；
清在最外层过滤器最后一行 → `currentRequest` 永远是干净的 3 行。

**3. `afterCompletion` 的 `ex` 为什么在 500 时还是 null？**

因为异常已经被 `@RestControllerAdvice` 的 `GlobalExceptionHandler` **消化**了
（`handleOther` 处理完、写了 500 响应），`DispatcherServlet` 走到
`triggerAfterCompletion(request, response, null)` 时传的就是 `null`。

实测：`GET /sku/boom`（500）和 `GET /trace/throw`（409）的轨迹里都是 `异常：无`。

> 所以复盘异常只能靠日志：`handleOther` 里那句 `log.error("系统异常", e)` 是**唯一**的完整堆栈出口。

## 🎤 三句话总结（今天要能脱口而出）

1. **一条链路**：`Filter 前置 → preHandle → Controller → postHandle → afterCompletion → Filter 后置`
   —— 过滤器包住一切，拦截器在 DispatcherServlet 里面。
2. **两个必须**：拦截器必须成为 Spring Bean（`@Component`）才注入得到依赖；
   拦截失败必须同时给出**状态码 + ContentType(charset) + 统一 JSON**。
3. **一个纪律**：ThreadLocal **谁最后写谁清理** ——
   `CurrentUser` 清在 `afterCompletion`，轨迹清在**最外层过滤器的最后一行**。

## 附：本次实现时踩到 / 验证过的坑（给批改人参考）

| 坑 | 现象 | 结论 |
|---|---|---|
| **`recorder.clear()` 写在 `afterCompletion`** | 下一次请求的 `currentRequest` 多 3 行（`耗时/退出/退出`） | ⭐ 本题最值钱的发现 → 清理放到最外层过滤器 |
| 交付版给 `OrderProbeFilter` 加日志时忘了强转 `HttpServletRequest` | 编译不过（`ServletRequest` 上没有 `getRequestURI`） | 方法签名不许变窄，只能强转 |
| `@Component` 的 Filter + `FilterRegistrationBean` 同时存在 | 过滤器会跑两次 | 本项目过滤器**故意不写** `@Component` |
| `InvalidPathException`（路径里有空格） | `spring-boot:run` 分叉进程丢 classpath | 运行脚本统一用"先 package 再 `java -jar`" |
| PowerShell 5.1 里脚本含中文 | 报"字符串缺少终止符" | 脚本必须存成 **UTF-8 带 BOM**（`.bat` 相反：CRLF、不许有 BOM） |
| 长度统计 | 一开始记的是**字符数**却写成"字节" | 中文 1 字 3 字节：83 字符 = 117 字节，两个数都要说清 |
