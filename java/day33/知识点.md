## 2. 复习：Day32 的三层校验 + 今天的"横切"位置

Day32 把校验分了三层，你今天要往这套图里再塞两个"关卡"：

```
请求
  ↓
【Filter】           ← ⭐ 今天新增：Servlet 容器层，连"要访问哪个 Controller"都不知道
  ↓
DispatcherServlet
  ↓
【Interceptor.preHandle】 ← ⭐ 今天新增：Spring MVC 层，能拿到 HandlerMethod
  ↓
【参数校验（Day32）】  ← 请求体 JSON 转对象时校验；方法参数靠 AOP 校验
  ↓
Controller → Service → Repository
  ↓
【Interceptor.postHandle】← REST 接口里基本没用（见第 14 节）
  ↓
【Interceptor.afterCompletion】← ⭐ 收尾的地方
  ↓
【Filter 返回】
```

**为什么要"插一手"而不是写在每个 Controller 里？**

| 需求 | 写在 Controller 里 | 写成 Filter / Interceptor |
|---|---|---|
| 每个接口都记请求日志 | 8 个接口抄 8 遍，加第 9 个接口又忘一次 | 写 1 处，管全部 |
| 每个接口都查登录 | 同上 + 容易漏（漏一个就是安全漏洞） | 写 1 处，还能顺便列白名单 |
| 接口本身 | 混着"技术逻辑"和"业务逻辑"，读起来累 | 干净：**只管业务** |

> ⭐ 生活类比：小区每个单元都要门禁，但**门禁不装在每户人家家里**，装在大门口。
> 这就是"横切"的意思 —— 它切的是**所有请求**，不是某一个接口。

## 3. ⭐⭐⭐ Filter（过滤器）：Servlet 规范的东西

**一句话**：Servlet 容器（Tomcat）的门卫，请求进来先过他，出去再过他。

```java
public class MyFilter implements Filter {          // ← jakarta.servlet.Filter（新 API）
    @Override
    public void init(FilterConfig cfg) { }         // 启动时一次（可省，接口里有 default 实现）

    @Override
    public void doFilter(ServletRequest request,   // ← 注意是 ServletRequest，不是 HttpServletRequest
                         ServletResponse response,
                         FilterChain chain)        // ← FilterChain：放行用的（新 API）
            throws IOException, ServletException {
        // 前置逻辑
        chain.doFilter(request, response);         // ⭐⭐ 放行 = 交给下一个（不写这行 = 请求死在这）
        // 后置逻辑
    }

    @Override
    public void destroy() { }                      // 关闭时一次
}
```

### 生命周期：init / doFilter / destroy

| 方法 | 什么时候调 | 实测证据 |
|---|---|---|
| `init(FilterConfig)` | 应用启动时 **1 次** | 启动日志里有 `[Filter① OrderProbe] init()` |
| `doFilter(...)` | **每个请求 1 次** | 每次请求日志里都有"进入/退出" |
| `destroy()` | 应用**正常关闭**时 **1 次** | Ctrl+C 停止服务时才打印（第 16 节有说明） |

### ⭐⭐ 两条铁律

**铁律①：`chain.doFilter()` 是命根子。**
不调用它 = 链条到此结束 = 后面的过滤器、DispatcherServlet、Controller **全都不执行**。
浏览器看到的是"一直转圈"或"空白"。
📌 注意它的坑法和拦截器**不一样**：过滤器是"**漏写一行**"，拦截器是"`return false`"。
一个靠手滑，一个靠返回值 —— 想想哪个更容易出事故？**漏写一行**（因为不报错）。

**铁律②：`ServletRequest` 想拿 HTTP 信息要强转。**
方法签名只能用 `ServletRequest`（规范里 HTTP 只是协议之一，而且**参数类型不允许变窄**，
写成 `HttpServletRequest` 就不叫"重写"了，编译不过）。想拿 URI / 请求头 / 状态码，就：

```java
HttpServletRequest httpRequest = (HttpServletRequest) request;     // 强转，实测够用
```

### 生活类比

过滤器 = **小区大门保安**：所有进出的车和人（**包括送外卖的、收废品的 = 静态资源请求**）
都要过他。他只看"包裹"（HTTP 请求），**根本不知道你住几零几**（不知道要进哪个 Controller）。

## 4. ⭐⭐⭐ Interceptor（拦截器）：Spring MVC 的东西

**一句话**：Spring MVC 的接待员，站在 DispatcherServlet 门口，
**知道你是谁、要办什么事**（能拿到要执行的 Controller 方法）。

```java
public class MyInterceptor implements HandlerInterceptor {   // ← Spring MVC 的接口（新 API）

    @Override
    public boolean preHandle(HttpServletRequest request,      // Controller 执行【前】
                             HttpServletResponse response,
                             Object handler) {                 // ← ⭐ 就是"要执行的那个方法"
        return true;      // true = 放行；false = 中断（Controller 不执行）
    }

    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response,
                           Object handler, ModelAndView modelAndView) {   // Controller 执行【后】、渲染【前】
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {           // 请求【彻底结束】后
    }
}
```

### 三个方法的分工（今天最该背的表）

| 方法 | 时机 | 能干什么 | 实测结论 |
|---|---|---|---|
| `preHandle` | Controller **之前** | 查登录、记开始时间、**能读方法上的注解** | 返回 false → 后面的拦截器 + Controller 全不执行；**`postHandle` 也不执行** |
| `postHandle` | Controller 之后、渲染之前 | 改 ModelAndView（**REST 接口没用**） | REST 接口里 `modelAndView` 是 **null**，但方法**确实会执行** |
| `afterCompletion` | **响应都发完了** | 收尾：算耗时、写日志、**清理 ThreadLocal** | ⭐ 无论成功还是抛异常都会执行；第 4 个参数 `ex` **常常是 null**（第 14 节） |

### ⭐ `preHandle` 的第三个参数 `handler` 是今天的"彩蛋"

同一个 `preHandle`，`handler` 的真实类型不一样（实测）：

| 请求 | `handler.getClass().getSimpleName()` | 说明 |
|---|---|---|
| `GET /sku` | `HandlerMethod` | 普通接口：**能拿到 Controller 的类、方法、方法上的注解** ← 过滤器做不到 |
| `GET /abc`（网址不存在） | `ResourceHttpRequestHandler` | 交给"静态资源处理器"了，最后抛 404 |

> ⭐ 这就是"拦截器知道你要办什么事，过滤器不知道"的铁证。
> 真实项目里靠它做权限注解（比如 Day45 的 `@RequiresRole`）——
> `preHandle` 里读一下方法上的注解就知道该不该放行。

### 生活类比

拦截器 = **公司前台**：你进楼时她问"找谁、预约了吗"（`preHandle`），
你要办的事她清楚（知道你的目的）；办完了她会登记一下（`afterCompletion`）。

## 5. ⭐⭐⭐ 执行顺序（面试必问）

```
①  Filter.doFilter 前置
②  DispatcherServlet 找到要执行的 Controller
③  Interceptor.preHandle
④  Controller（+ 里面调 Service）
⑤  Interceptor.postHandle
⑥  视图渲染（REST 接口没有这一步）
⑦  Interceptor.afterCompletion
⑧  Filter.doFilter 后置
```

**真机实测**（本项目答案版，`GET /public/ping` 的控制台日志，一字不改抄下来）：

```
[Filter① OrderProbe] 进入 GET /public/ping
[Filter② Cost] GET /public/ping → 200，耗时 87 ms      ← ② 在①的里面，所以先退出
[Filter① OrderProbe] 退出 /public/ping
```

（同一台机器另一次跑出来是 `耗时 248 ms`，说明这数字随负载波动 —— **稳定的是顺序，不是毫秒数**。）

连 401 的请求也有这一行（`[Filter② Cost] POST /login → 401，耗时 6 ms`），
说明**过滤器对成功和失败一视同仁**：它甚至不需要知道"业务有没有出错"，状态码就在它手里。

`/trace/last` 里的轨迹（结构化的同一条链）：`Filter① 进入 → Filter② 进入 → preHandle → postHandle → afterCompletion`

### 多个拦截器 / 多个过滤器时：正序进、倒序出

| | 进入顺序 | 退出顺序 |
|---|---|---|
| 多个 **Interceptor** | `preHandle` **按注册顺序正序**（①→②→③） | `postHandle` / `afterCompletion` **倒序**（③→②→①） |
| 多个 **Filter** | 按 `setOrder` 的**数字从小到大** | **反过来**（数字大的先退） |

> ⭐ 一句话记：**先进后出，像穿衣服**（先穿的衬衫最后脱）。
> ⭐ 生活类比：进门过两道安检（先刷脸、再查包），出门时顺序反过来（先拿包、再出门）。

### ⚠️ `preHandle` 返回 false 时，谁还会被调用？（真机实测）

`GET /sku` 不带 token（被拦截器拒了）的真实轨迹：

```
Filter① 进入 → Filter② 进入 → [拦截器 Trace] preHandle → [拦截器 Auth] preHandle → 拒绝（没带 token）
             → [拦截器 Trace] afterCompletion → Filter② 退出 → Filter① 退出
```

三条规律：

1. **没走到的拦截器，`preHandle` 不执行**（Auth 之后的 Throw 完全没参与）；
2. **已经成功通过的拦截器，`afterCompletion` 会执行**（Trace 的 afterCompletion 照样跑）；
3. **`postHandle` 一次都不执行**（因为 Controller 没跑）。

> 📌 第 2 条很重要：它保证了"你在 `preHandle` 里申请的资源，`afterCompletion` 里一定有机会释放"。
> 但它**有一个前提**：那个拦截器自己的 `preHandle` 得先返回 true。

## 6. ⭐⭐⭐ Filter vs Interceptor 的区别（面试高频）

| 对比项 | Filter | Interceptor |
|---|---|---|
| **归属** | Servlet 容器（Tomcat）——**Servlet 规范** | Spring 容器——**Spring MVC** |
| 谁 new 的 | 容器（不是 Spring） | 你注册的那个人（可以是 Spring Bean） |
| **能拿到 Controller 方法吗** | ❌ 不能（只知道 URL） | ✅ 能（`preHandle` 的 `HandlerMethod`） |
| **触发范围** | 所有请求（**含静态资源 `/favicon.ico`**） | 只拦 DispatcherServlet 处理的请求（实测 404 也走，见第 12 节） |
| 依赖注入 | 麻烦（用 `FilterRegistrationBean` 时得手动传；`@WebFilter` 方式常常拿不到 Bean） | 天然是 Spring Bean（`@Component` + 构造器注入最省事） |
| 拦死的方式 | **不写** `chain.doFilter(...)` | `preHandle` **`return false`** |
| 典型用途 | 编码/跨域/压缩/请求包装/最外层计时 | 登录校验、权限校验、接口日志、ThreadLocal 清理 |

### 🎤 面试三句话（背这三句就够）

1. **出身不同**：Filter 是 Servlet 规范的（Tomcat 调它），Interceptor 是 Spring MVC 的（DispatcherServlet 调它），
   所以 **Filter 一定在 Interceptor 外面**。
2. **能力不同**：Interceptor 的 `preHandle` 能拿到 `HandlerMethod`（方法 + 方法上的注解），Filter 拿不到；
   所以"按注解做权限"只能用拦截器。
3. **范围不同**：Filter 连静态资源都管，Interceptor 只管进 DispatcherServlet 的请求；
   所以"全站编码/跨域"用 Filter，"业务登录校验"用拦截器。

> **怎么选？** 需要 HTTP 报文级别的东西（编码、跨域、body 包装）→ Filter；
> 需要业务/身份信息（登录、权限、注解）→ Interceptor。

## 7. ⭐⭐ Filter 的两种注册方式

### 方式①：`FilterRegistrationBean`（本项目用的，能精确控顺序）

```java
@Configuration
public class FilterConfig {

    @Bean
    public FilterRegistrationBean<OrderProbeFilter> orderProbeFilter(TraceRecorder recorder) {
        FilterRegistrationBean<OrderProbeFilter> reg =          // ← 新 API：注册器（可设顺序/名字/路径）
                new FilterRegistrationBean<>(new OrderProbeFilter(recorder));
        reg.addUrlPatterns("/*");     // 拦哪些路径
        reg.setName("orderProbeFilter");
        reg.setOrder(1);              // ⭐ 数字越小越先执行（也越后退）
        return reg;
    }
}
```

### 方式②：`@WebFilter` + `@ServletComponentScan`（注解式，简单但顺序不好控）

```java
@WebFilter("/*")                       // ← 新注解：Servlet 规范自带的"我要拦所有路径"
public class MyFilter implements Filter { ... }
// 再在启动类上加：
@ServletComponentScan                  // ← 新注解：让 Spring 去扫 @WebFilter/@WebServlet
@SpringBootApplication
public class Day33Application { ... }
```

| | `FilterRegistrationBean` | `@WebFilter` |
|---|---|---|
| 顺序控制 | ✅ `setOrder(1)` 精确 | ⚠️ 不好控 |
| 拿依赖（如 `TraceRecorder`） | ✅ 构造器手动传 | ⚠️ 常常注入不到 |
| 代码量 | 多一个配置类 | 一行注解 |

> ⭐ 本项目选①：因为今天要**看见顺序**，顺序不可控的写法不适合教学。

### ⚠️⚠️ 千万别"注册两遍"

下面这个坑非常容易踩，而且症状很怪（**过滤器跑两次**）：

- 给 Filter 类加了 `@Component` → SpringBoot 发现"这是个 Filter Bean" → **自动注册一遍**（默认 `/*`）
- 你在 `FilterConfig` 里又 `new FilterRegistrationBean<>(...)` → **又注册一遍**
- 结果：同一个过滤器**每个请求跑两次**，日志/轨迹全是双份

📌 规矩：**用 `FilterRegistrationBean` 注册时，Filter 类本身不要写 `@Component`。**
（本项目的 `OrderProbeFilter` / `CostFilter` 都故意没写 `@Component`，
`TraceInterceptor` / `AuthInterceptor` 才写 —— 看出区别了吗？**过滤器 Bean 会被自动注册，拦截器 Bean 不会**，
拦截器必须自己 `registry.addInterceptor(...)`。这一点特别容易混，记一下。）

## 8. ⭐⭐⭐ 拦截器的注册：路径通配符 + 白名单

```java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {      // ← 新接口：改 SpringMVC 默认配置

    private final AuthInterceptor authInterceptor;           // ⭐ 从容器注入（不是 new！）

    public WebMvcConfig(AuthInterceptor authInterceptor) {
        this.authInterceptor = authInterceptor;
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {   // ← 新 API：注册处
        registry.addInterceptor(authInterceptor)
                .addPathPatterns("/**")                           // 拦哪些
                .excludePathPatterns("/login",                    // 白名单（不拦哪些）
                                     "/public/**",
                                     "/trace/**");
    }
}
```

### 路径通配符（写错就是"漏防一片"）

| 写法 | 匹配 | 坑 |
|---|---|---|
| `/sku` | **只有** `/sku` 这一条 | ⚠️ `/sku/1`、`/sku/search` **全都不拦** ← 本项目交付版的坑（第 6 步） |
| `/sku/*` | `/sku/1`、`/sku/search`（一层） | `/sku/a/b` 不匹配 |
| `/sku/**` | `/sku` 下所有层级 | 业务接口的常用写法 |
| `/**` | 全部（含静态资源、404） | 配合白名单用 |
| `/public/**` | `/public/ping`、`/public/notice` | 白名单里最常用 |

> ⭐ 白名单里的路径**回 Controller 的 `@RequestMapping` 上抄**，不要凭记忆写。
> 实测教训：写 `/api/login` 而实际是 `/login` → 白名单形同虚设 → **登录接口自己被拦**（死循环：要登录得先登录）。

### ⭐ 白名单必须包含哪些？

1. **登录接口**（`/login`）—— 不然谁也登不进来；
2. **公开接口**（`/public/**`：公告、探活、首页）；
3. **调试/文档接口**（`/trace/**`、`/swagger-ui/**`、`/actuator/health`）——
   今天你的观察窗口就靠它，被拦住就没法调试了；
4. （真实项目还要加）**静态资源**：`/static/**`、`/favicon.ico` —— 实测**不加就被拦成 401**（第 15 节）。

## 9. ⭐⭐⭐ 拦截器里 `@Autowired` 为什么是 null

这是今天**最值钱的一课**，也是交付版里那个 500 的根因。

### 三种写法，只有两种对

```java
// ❌ 错法：拦截器是 new 出来的 —— 它压根不是 Spring Bean
@Autowired                       // 这行**不会有任何效果**（Spring 根本不知道有这个对象）
private TokenStore tokenStore;   // → 永远是 null → 用时 NullPointerException

// 注册处：
registry.addInterceptor(new AuthInterceptor());   // ← 元凶在这里
```

```java
// ✅ 正法一：让拦截器成为 Spring Bean（@Component + 构造器注入）
@Component
public class AuthInterceptor implements HandlerInterceptor {
    private final TokenStore tokenStore;
    public AuthInterceptor(TokenStore tokenStore) { this.tokenStore = tokenStore; }   // 启动就会注入好
}

// 注册处：从容器里注入进来用
private final AuthInterceptor authInterceptor;
public WebMvcConfig(AuthInterceptor authInterceptor) { this.authInterceptor = authInterceptor; }
registry.addInterceptor(authInterceptor);
```

```java
// ✅ 正法二：用 @Bean 手工造（@WebFilter 那种场景也能用）
@Bean
public AuthInterceptor authInterceptor(TokenStore tokenStore) {
    return new AuthInterceptor(tokenStore);        // 依赖自己传进去
}
```

### 实测现象（交付版真实数据）

带**正确** token 访问 `GET /sku`：

```json
HTTP 500
{"code":"500","message":"服务器开小差了，请稍后重试","data":null,"fieldErrors":null}
```

日志里的真凶（完整堆栈在 `GlobalExceptionHandler` 的 `log.error` 里）：

```
java.lang.NullPointerException: Cannot invoke
  "com.xiaoming.day33.auth.TokenStore.findUsername(String)" because "this.tokenStore" is null
```

> ⭐ 三个教训：
> 1. **编译通过 ≠ 注入成功**（`@Autowired` 是运行期反射干的活）；
> 2. **`@Component` 只是"它是 Bean"，不等于"它生效"** —— 拦截器还得 `registry.addInterceptor`；
> 3. 凡是"**我自己 new 出来的对象**"，里面的 `@Autowired` **一律是 null**（Spring 只注入它自己管的 Bean）。
>    📌 这条对 `Filter`、`Listener`、`@WebFilter`、手写的 `new XxxService()` 全都成立。
>
> **为什么"构造器注入 + final"更好？** 因为 final 字段**必须**在构造器里赋值 ——
> 万一忘了传，**编译期就红**，而不是等到线上 500。字段 `@Autowired` 没有这个保险。

## 10. ⭐⭐ `ThreadLocal` + **清理到底写在哪一层**

### 10.1 为什么需要 ThreadLocal

**问题**：拦截器验证通过后，"当前登录用户"怎么传给 Controller / Service？
笨办法是层层传参：`orderService.create(form, username)` → 每个方法签名都多一个参数。

**答案**：拦截器存一次，下面谁要用谁自己取。但拦截器和 Service 都是**单例**
（不能把用户名存成字段 —— 并发下会串数据，Day18/19 学过的），
所以要一个"**每个请求自己一份**"的储物柜 —— ThreadLocal：

```java
private static final ThreadLocal<String> HOLDER = new ThreadLocal<>();   // ← 新 API

HOLDER.set("xiaoming");     // 放进"当前线程"的柜子
HOLDER.get();               // 只有当前线程取得出来，别的线程 get() 是 null
HOLDER.remove();            // ⭐ 把柜子清空（不清 = 内存泄漏 + 串数据）
```

> ⭐ 为什么"一个请求 = 一个线程"？因为 Tomcat 从头到尾用**同一个线程**处理一个请求。
> 所以"请求级数据"用 ThreadLocal 存刚刚好。

### 10.2 ⚠️⚠️ 没清理会怎样？（本项目的核心事故）

**Tomcat 的线程是复用的**（线程池：100 个请求可能只用 5 个线程）。
所以 `set` 进去的东西如果不 `remove`，**下一个请求（同一个线程）会看到上一个请求留下的东西**。

实测（交付版，`/trace/last` 里的"本次请求(进行中)"）：

| 第几次打 `/trace/last` | 用的线程 | "本次请求"里的轨迹行数 | 说明 |
|---|---|---|---|
| 第 1 次 | `exec-2` | 3 行（本次的 Filter①进入/Filter②进入/preHandle） | 正常 |
| 第 2、3 次 | `exec-5`、`exec-10` | 3 行 | 换了线程，**看不到**残留 |
| 第 4 次 | `exec-1` | **9 行** | 撞上被复用的线程，开始串了 |
| 第 6 次 | `exec-1` | **16 行** | 越滚越长 |
| 第 9 次 | `exec-3` | **27 行** | 一个请求里塞了 5 个请求的轨迹 |
| 同一份日志里的 `lastCompleted.steps` | | 4 → 10 → 16 → 22 → 28 | 正常应该 4~5 |

> 📌 **为什么每次正好 +6 行？** 一个请求的轨迹一共 6 行
> （`Filter①进入`、`Filter②进入`、`preHandle`、`afterCompletion`、`Filter②退出`、`Filter①退出`），
> 而"存档"发生在 `afterCompletion`（那时只有前 4 行），后 2 行是**过滤器退出时补记**的。
> 所以 `steps` 显示 4，柜子里实际躺着 6 行。**这"多出来的 2 行"就是第 10.3 节那个坑的伏笔。**
> ⭐ `steps` 从 4 涨到 28 —— 这就是"没清理"的铁证。**这类 bug 平时不报错，只在数据出错时爆发**，最难查。
>
> 📌 顺便注意：**第 1~3 次是干净的**（因为 Tomcat 换了线程）。
> 这就是 ThreadLocal 泄漏最恶劣的地方 —— **看运气**：测试时可能一切正常，上线后偶发"看到了别人的数据"。

### 10.3 ⭐⭐ 清理写在哪一层？（**今天实测发现的大坑**）

第 5 节说 `afterCompletion` 是收尾的地方 —— **对，但不完全对**。看实测：

```
把 recorder.clear() 写在 TraceInterceptor.afterCompletion 里（我第一次尝试的写法）：
  下一次请求（同一个线程）的"本次请求"里，带着上一次的残留 3 行（实测原文）：
      [Filter② Cost] 耗时 95 ms  →  [Filter② Cost] 退出  →  [Filter① OrderProbe] 退出
```

**为什么清不干净？** —— 因为 `afterCompletion` **不是最后一句代码**：

```
Filter①进入 → Filter②进入 → preHandle → Controller → postHandle → afterCompletion → 【clear 在这里】 
            → Filter② 记"耗时/退出"  ← ⚠️ clear 之后又记了 3 行！
            → Filter① 记"退出"        ← ⚠️ 这些就留在柜子里了
```

**正确做法：清的代码要放在"整个请求最后跑完的那一层"** —— 也就是 **order=1 的最外层过滤器**的最后一行。
实测改完之后，"本次请求"永远**恰好 3 行**，`lastCompleted` 也不会串。

| 清在哪 | 实测结果 |
|---|---|
| `afterCompletion`（拦截器里） | ❌ 下一次请求的"本次请求"带 **3 行残留** |
| `OrderProbeFilter.doFilter` 的最后一行（最外层过滤器） | ✅ 干净（**恰好 3 行**） |

> ⭐⭐ 口诀：**谁最后动这份数据，谁负责清理**（不是"名字里带 after 的方法就一定能收尾"）。
> 📌 那两个 ThreadLocal 的清理位置还不一样，别混：
> | 数据 | 谁 set | 谁的清理位置 | 理由 |
> |---|---|---|---|
> | `CurrentUser`（当前登录用户） | `AuthInterceptor.preHandle` | `AuthInterceptor.afterCompletion` | 拦截器之后**没有别人再动它**，写在 afterCompletion 就够 |
> | `TraceRecorder`（执行轨迹） | 过滤器 + 拦截器都会写 | **最外层过滤器最后一行** | 因为过滤器在 afterCompletion 之后还会写 3 行 |
>
> 📌 另一种也很常见的防呆写法：**在请求最开始就"重置"一份新的**（`current.set(new ArrayList<>())`），
> 而不是靠结尾清 —— "入口重置"比"出口清理"更难忘。今天用清理，是为了让你亲眼看到残留。

## 11. ⭐⭐ 登录校验拦截器怎么写

### 11.1 token 放哪儿

```java
String token = request.getHeader("X-Token");     // ← 取请求头（新 API）
```

| 方案 | 长什么样 | 优缺点 |
|---|---|---|
| ⭐ 标准做法 | `Authorization: Bearer <token>` | 网关 / Swagger / 前端库都认；要按格式切两半 |
| 本项目 | `X-Token: tk-xiaoming` | 少一层解析，教学更清爽；⚠️ 跨域时必须加进 `Access-Control-Allow-Headers` |

### 11.2 拦截失败怎么回？（⭐ 新手最容易写成"光秃秃 401"）

```java
// ❌ 交付版的写法：只设状态码，不写响应体
response.setStatus(401);
return false;
// → 客户端收到 401 + 【0 字节】→ 前端 res.json() 直接抛异常
//   实测响应体长度：0
```

```java
// ✅ 正确写法：状态码 + ContentType + 统一 JSON 信封（三件套）
response.setStatus(401);
response.setContentType("application/json;charset=UTF-8");     // ⚠️ 忘了 charset → 中文乱码
Result<Void> body = Result.fail(ResultCode.UNAUTHORIZED, "未登录或登录已过期，请在请求头带上 X-Token");
response.getWriter().write(objectMapper.writeValueAsString(body));   // 用 Jackson 转，别手拼字符串
```

实测响应体（答案版，长度 83 字节）：

```json
{"code":"401","message":"未登录或登录已过期，请在请求头带上 X-Token","data":null,"fieldErrors":null}
```

> ⭐ 为什么 401 而不是 400/403？
> **400 = 你说的不对；401 = 你是谁？（没身份）；403 = 我知道你是谁，但不行（没权限）；404 = 你要的没有；409 = 现在不行。**
> 记忆：**401 先登录，403 登录了也没用**。

### 11.3 为什么要在拦截器里返回 JSON，而不是干脆 `throw`？

其实**两种都能用**（第 13 节实测：拦截器里抛异常也会被统一异常处理器接住）。
但生产环境更推荐**自己写响应**，理由：
1. **可控**：我可以决定要不要写 `WWW-Authenticate` 头、要不要记审计日志；
2. **不依赖框架行为**：抛异常走异常处理器的链路更深，一旦别处加了 `HandlerExceptionResolver`，行为可能变；
3. **语义清楚**：401 是"门卫不让进"，不是"业务代码炸了"，不该混进 `log.error`。

> 📌 反面教材就在交付版里：它用 `new AuthInterceptor()` + `@Autowired`，
> 结果"该拦的时候拦了，该过的时候 500" —— **拦截器代码写对了也没用，注入是错的**。

## 12. ⭐⭐ `/abc` 这种 404，走不走拦截器？

**答案（真机实测）：走。** 而且是"走了一半"：

`GET /abc`（带 token）的真实轨迹（答案版）：

```
Filter① 进入 → Filter② 进入
→ [拦截器 Trace] preHandle（handler=ResourceHttpRequestHandler）   ← ⭐ 进来了！但 handler 不是 HandlerMethod
→ [拦截器 Auth] preHandle → 放行（xiaoming）
→ [拦截器 Trace] afterCompletion（耗时 3 ms，异常：无）             ← ⭐ afterCompletion 也执行了
→ Filter② 退出 → Filter① 退出
```

最终响应：`404 {"code":"404","message":"No static resource abc.","data":null,"fieldErrors":null}`

### 为什么？三条推理

1. SpringBoot 给静态资源注册了 `/**` 的映射（`ResourceHttpRequestHandler`），
   所以**任何没匹配到 Controller 的 URL 都会落到它头上** → `getHandler()` 能拿到 handler → 拦截器就生效；
2. 它进去以后发现文件不存在 → 抛 `NoResourceFoundException` →
   被 Day31 写的那个 handler 接住 → **404 + 统一 JSON**；
3. 抛异常 → **`postHandle` 不执行**（它根本没走到），但 `afterCompletion` **照样执行**。

### ⚠️ 由此推出两个实操结论

| 结论 | 说明 |
|---|---|
| **`preHandle` 里不能假设 `handler` 是 Controller 方法** | 写权限注解时一定要先判断 `handler instanceof HandlerMethod`，否则 /abc 这类请求会直接 NPE |
| **拦截器会把 404 也拦成 401** | 本项目实测：`GET /abc` 不带 token → **401**（不是 404）；带了 token → 404 |

> 📌 顺带回答 Day31 那道思考题：`/abc` 为什么"不走全局异常处理器"？
> 那是 Day31 的版本（当时写的是 `@ExceptionHandler(Exception.class)` 兜底，
> 而 `NoResourceFoundException` 被兜底接成 500）。Day32 补了 `NoResourceFoundException` 的 handler 之后，
> `/abc` 就是规规矩矩的 404 了 —— **它一直都有走异常处理器，只是走了兜底那一条**。

## 13. ⭐⭐⭐ 拦截器里抛异常，走不走统一异常处理器？

**答案（真机实测）：走！** 而且格式完全统一。

实验接口 `GET /trace/throw`（`ThrowInterceptor.preHandle` 里 `throw new ApplicationException(...)`）：

```json
HTTP 409
{"code":"409","message":"拦截器里故意抛的异常（preHandle）","data":null,"fieldErrors":null}
```

日志里能看到统一处理器打的 warn：

```
WARN  GlobalExceptionHandler : 业务异常：code=409, http=409, message=拦截器里故意抛的异常（preHandle）
```

### 为什么？（源码层面一句话）

`preHandle` 是在 `DispatcherServlet.doDispatch()` 的 **try 块**里被调用的，
所以它抛出的异常会被 `catch` 住 → 交给 `processDispatchResult` → 交给异常处理器链
（`ExceptionHandlerExceptionResolver`）→ 找到我们 `@RestControllerAdvice` 里那个 handler。

> ⭐ 很多老博客说"拦截器抛异常不会被 @ControllerAdvice 处理"——
> 那是 **Spring 3/4 时代**的事（当时 `applyPreHandle` 在 try 块外面）。**Spring 6（本项目 6.1.14）已经会处理了。**
> 📌 这就是"别背博客、动手测一发"的价值 —— 实测比记忆可靠。

### ⚠️ 但"能接住"不代表"该这么写"

| | 自己写响应（`setStatus` + JSON） | 抛异常 |
|---|---|---|
| 行为 | 完全可控 | 依赖框架链路 |
| 日志 | 你自己决定 warn/info | 走异常处理器的 warn/error |
| 适合 | **认证失败（401）** | 参数/业务校验（400/409） |

> 📌 本项目就是"混着用"的范例：**401 自己写，实验用的 409 走抛异常** —— 两种都实测给你看。

## 14. ⭐⭐ 两个"反直觉"的 null

### 14.1 `postHandle` 的 `ModelAndView` 是 null

我们是 `@RestController`（所有方法都带 `@ResponseBody`）→ **没有视图可渲染** →
`modelAndView` 就是 null，改它**毫无意义**。
但 `postHandle` 方法**确实会被执行**（轨迹里看得到），所以你可以拿它当"路标"，别指望它改响应。

> 📌 真实项目里 `postHandle` 的用武之地是**传统 MVC（返回 jsp/html 页面）**：
> 在渲染前塞公共数据（比如"当前登录用户"给页面用、导航栏菜单）。

### 14.2 `afterCompletion` 的第 4 个参数 `ex` 常常是 null

书上都写"能在这里拿到异常"——**实测并不是**：

| 请求 | 结果 | `afterCompletion` 里记录的"异常" |
|---|---|---|
| `GET /sku/boom`（NPE → 兜底 handler → 500） | 500 | **异常：无**（`ex == null`） |
| `GET /trace/throw`（preHandle 抛 409） | 409 | **异常：无**（`ex == null`） |

**原因**：异常已经被 `GlobalExceptionHandler` **消化**掉了。
`DispatcherServlet` 走到 `triggerAfterCompletion(request, response, null)` 时，传的就是 **null**。

> ⭐ 结论：**想复盘异常，看日志（ERROR + 完整堆栈）；别指望 `afterCompletion` 的 `ex`。**
> 这也解释了为什么 `handleOther` 里那句 `log.error("系统异常", e)` 那么重要 ——
> 它是异常信息**唯一**的出口。

## 15. 静态资源和跨域（了解即可）

### 静态资源也会被拦（实测）

`GET /favicon.ico` **不带 token**：

| 版本 | 结果 | 说明 |
|---|---|---|
| 交付版（拦截器只挂 `/sku`） | **404** `No static resource favicon.ico.` | 没被拦 |
| 答案版（拦截器挂 `/**`） | **401** | ⚠️ 浏览器要的图标被拦成 401 了 |

> ⭐ 所以真实项目的白名单里一定有：`/static/**`、`/favicon.ico`、`/css/**`、`/js/**`、`/images/**`。
> 📌 这个现象也再次说明"Filter 管所有请求、Interceptor 管 DispatcherServlet 的请求"这条区别：
> 静态资源**两条路都会走**（都进了 DispatcherServlet），只是能不能拿到 HandlerMethod 不一样。

### 跨域（CORS）

前后端分离时，浏览器会因为"跨域"拦截请求。两种做法：

```java
// ① 用过滤器（Filter 的经典用途）
@Bean
public FilterRegistrationBean<CorsFilter> corsFilter() { ... }

// ② 用 WebMvcConfigurer（同一个接口的兄弟方法）
@Override
public void addCorsMappings(CorsRegistry registry) {
    registry.addMapping("/**").allowedMethods("*").allowedOrigins("http://localhost:5173");
}
```

> ⚠️ 自定义请求头（比如我们的 `X-Token`）跨域时必须出现在 `allowedHeaders` 里，
> 否则浏览器会先发 OPTIONS 预检，然后**直接把请求掐掉**（后端日志里连一行都没有 —— 因为请求压根没发出去）。
> 📌 症状识别：**Postman 通、网页不通** → 先想跨域。

### 常见坑（每条都在本项目里出现过或有实测依据）

| 坑 | 症状 | 正确做法 |
|---|---|---|
| ⭐ 过滤器不写 `chain.doFilter` | 所有接口空白/转圈，**日志里一行错都没有** | 放行那一行是命根子 |
| ⭐ 拦截器用 `new` 注册，里面 `@Autowired` | 用到那个 Bean 时 **500 / NPE** | `@Component` + 构造器注入，注册处注入 |
| ⭐ 401 只 `setStatus` 不写响应体 | 客户端拿到 **0 字节**，前端解析报错 | `setContentType`（带 charset）+ 写 JSON |
| ⭐ `addPathPatterns("/sku")` 写窄了 | `/sku/1` 等**越权通过**（实测 200） | 业务接口用 `/sku/**`，配合白名单用 `/**` |
| ⭐ 白名单路径写错（`/api/login` vs `/login`） | 登录接口自己被拦 → **永远登不进去** | 回 Controller 抄路径 |
| ⭐ ThreadLocal 不清理 | 同线程的下一个请求看到**上一个用户的身份**（越权） | **谁最后写，谁负责清**（第 10.3 节） |
| ⭐ 清理写在 `afterCompletion` | 过滤器在它之后还会写 3 行 → **清不干净** | 清在最外层过滤器的最后一行 |
| 过滤器 `@Component` + `FilterRegistrationBean` 同时存在 | 过滤器**跑两次** | 二选一 |
| 拦截器以为 `@Component` 就生效 | 拦不住任何请求 | 还要 `registry.addInterceptor(...)` |
| `preHandle` 里直接用 `handler` 当 `HandlerMethod` | 访问不存在的 URL 时 **NPE** | 先 `instanceof HandlerMethod` 判断 |
| 拦截器里把请求数据存成字段 | 并发时串数据（拦截器是**单例**） | 存 `request.setAttribute` 或 ThreadLocal |
| 以为 `afterCompletion` 的 `ex` 有异常 | 拿不到，写了个永远为 null 的分支 | 看日志 |
| 用 `javax.servlet.*`（老教程） | 编译就报错（SpringBoot 3 全是 `jakarta.*`） | 用 `jakarta.servlet.*` |
| properties 里写中文没用 `\uXXXX` | 中文乱码（Day30 的坑，今天同样适用） | 写转义 |
