### 0.1 怎么发 POST / 带请求头的请求？

```powershell
# ① 登录拿 token（POST，body 必须是 UTF8 字节数组）
$b = [System.Text.Encoding]::UTF8.GetBytes('{"username":"xiaoming","password":"123456"}')
$r = Invoke-WebRequest -Uri http://localhost:8080/login -Method POST `
       -ContentType 'application/json; charset=utf-8' -Body $b -UseBasicParsing
[System.Text.Encoding]::UTF8.GetString($r.RawContentStream.ToArray())
# → {"code":"200","message":"操作成功","data":{"username":"xiaoming","token":"tk-xiaoming"},...}

# ② 带着 token 访问业务接口（-Headers 传自定义请求头 X-Token）
$r = Invoke-WebRequest -Uri http://localhost:8080/sku -Headers @{ 'X-Token' = 'tk-xiaoming' } -UseBasicParsing
```

> ⚠️ 三个实测过的坑：
> 1. **POST 必须传字节数组**（`UTF8.GetBytes(...)`），直接传字符串中文会乱码；
> 2. PowerShell 5.1 里 `$r.Content` 显示中文是 `æä½æå`（**显示**问题，不是服务端 bug）——
>    要看清楚用 `[System.Text.Encoding]::UTF8.GetString($r.RawContentStream.ToArray())`；
> 3. **`Invoke-WebRequest` 遇到 4xx/5xx 会抛异常**（不是返回对象）。要"看到状态码和响应体"，
>    就用 `-SkipHttpErrorCheck`（PS7）或者 `try/catch { $_.Exception.Response }`——
>    本项目附带的验证脚本用的是 `RawContentStream` + `try/catch`，你把 `运行Day33.bat` 的
>    `6` 号菜单打开照着打也行。

### 1.4 观察点 ③：`/trace/last` 里的轨迹（今天的主要观察窗口）

`GET /trace/last` 会返回**两段**东西：

```json
{
  "currentRequest": { "thread": "...", "method": "GET", "uri": "/trace/last", "steps": [ ... ] },
  "lastCompleted":  { "method": "GET", "uri": "/public/ping", "status": 200, "steps": [ ... ] }
}
```

| 为什么有两段？ |
|---|
| `lastCompleted` = **上一次请求**跑完后的完整轨迹（这次的请求还没跑完，所以上一次的才是完整的） |
| `currentRequest` = **本次请求**跑到现在为止的轨迹（所以它只有 3 行） |

实测（**交付版**，连续访问 9 次 `/trace/last`，只看 `currentRequest.steps` 的行数）：

| 第几次访问 `/trace/last` | 用的线程 | `currentRequest` 的行数 | 正常应该是 |
|---|---|---|---|
| 第 1 次 | `exec-2` | **3** | 3 ✅ |
| 第 2 次 | `exec-5` | **3** | 3 ✅（换了线程，所以看不到残留） |
| 第 3 次 | `exec-10` | **3** | 3 ✅（又换了线程） |
| 第 4 次 | `exec-1` | **9** | 3 ❌ 多了 6 行 |
| 第 5 次 | `exec-5` | **9** | 3 ❌ |
| 第 6 次 | `exec-1` | **16** | 3 ❌ |
| 第 8 次 | `exec-4` | **21** | 3 ❌ |
| 第 9 次 | `exec-3` | **27** | 3 ❌ 一个请求里塞了 5 个请求的轨迹 |

同一个 `lastCompleted.steps` 也是这么涨的（9 次实测原样抄）：

```
GET /public/ping  -> 200  steps=4
POST /login       -> 401  steps=4
GET /sku          -> 401  steps=4
GET /sku/1        -> 200  steps=4
GET /abc          -> 404  steps=10     ← 从这儿开始串了
GET /sku/boom     -> 500  steps=10
GET /trace/throw  -> 409  steps=16
GET /trace/whos   -> 200  steps=22
PUT /sku          -> 401  steps=28     ← 每跑一个请求就 +6 行
```

**你应该观察到什么**：同一个请求的轨迹**越滚越长**，里面能看到**上一次甚至上上次请求**留下的行
（比如出现两次 `[Filter① OrderProbe] 进入`）。

> 💡 提示：这就是"**没清理 ThreadLocal**"最直接的证据。为什么上一次和这一次会混在一起？
>   因为 **Tomcat 的线程是复用的**（同一个线程干完活不销毁，而是回线程池等下一单）。
>   响应里带着 `thread` 字段，对比一下是不是同一个线程名 —— 实测第 1~3 次换了线程（所以都是干净的 3 行），
>   第 4 次开始撞上重复使用的 `exec-1`，一下就到 9 行。
>
> 📌 **为什么每次正好 +6 行？** 因为一个请求的轨迹一共 6 行
>   （`Filter①进入`、`Filter②进入`、`preHandle`、`afterCompletion`、`Filter②退出`、`Filter①退出`），
>   而"存档（publish）"发生在 `afterCompletion`（那时只有前 4 行），后 2 行是过滤器退出时补记的 ——
>   所以 `lastCompleted.steps` 显示 4，但柜子里实际躺着 6 行。**这 6 行就是下一轮的"残留"。**
>   这个细节在第 7 步会变成一个坑，先记住这 6 行。

## 第 4 步（15 分）TODO② 让 401 也有统一 JSON 信封

**目标**：401 不能"光有状态码"，要和 Day31 定下的信封格式一模一样。

**现状（实测）**：`GET /sku` 不带 token → `HTTP 401`，**响应体 0 字符**。

**要做的事**：在 `AuthInterceptor` 里补一个写 401 的方法，然后**两个 401 出口都用它**
（① 没带 token；② token 无效）。

```java
/** 统一的 401 出口：状态码 + 内容类型（带 charset）+ JSON 信封，三件事缺一不可 */
private void writeUnauthorized(HttpServletResponse response, String message) throws IOException {
    response.setStatus(401);                                        // ⭐ 状态码
    response.setContentType("application/json;charset=UTF-8");       // ⭐ 忘 charset → 中文乱码
    Result<Void> body = Result.fail(ResultCode.UNAUTHORIZED, message);
    response.getWriter().write(objectMapper.writeValueAsString(body));   // ⭐ 用 Jackson 转，别手拼
}
```

> 💡 提示（三条路，推荐第 3 条）：
> 1. **手拼字符串** `response.getWriter().write("{\"code\":\"401\",...}")` —— 能过，但中文/转义容易错；
> 2. 自己 `new ObjectMapper()` —— 也能过，但项目里已经有一个"配置好"的（`indent-output` 等），
>    另起一个会导致两处输出格式不一致；
> 3. ⭐ **把 Spring 容器里的 `ObjectMapper` 注入进来**（第 5 步做成 Bean 之后就能注入了）。
>
> ⚠️ 顺序问题：**第 4 步和第 5 步谁先做都行**，但**第 4 步用第 3 种写法时依赖第 5 步**。
> 如果你先做第 4 步、且用了第 3 种写法，那就先把第 5 步做了再测。

### 验证（实测对照）

| | `GET /sku` 不带 token | `GET /sku` 带无效 token |
|---|---|---|
| 改之前（实测） | `401`，响应体 **0 字符** | **500**（一脚踩进那行 null 代码） |
| 改之后（实测） | `401`，响应体 **83 字符 / 117 字节**：`{"code":"401","message":"未登录或登录已过期，请在请求头带上 X-Token","data":null,"fieldErrors":null}` | `401`，响应体 **76 字符 / 100 字节**：`{"code":"401","message":"token 无效或已过期，请重新登录","data":null,"fieldErrors":null}` |

> ⭐ 注意两个 401 的 **message 不一样**（"没带 token" vs "token 无效"），但**信封形状完全一样** ——
> 这就是统一响应的意义：客户端只看 `code` 就能判断，不用管文案。
> ⭐ 为什么 401 不用 403？（写在笔记里）→ **401 = 你是谁（没身份）；403 = 我知道你是谁，但不行（没权限）。**

### ⭐⭐ 为什么第 ② 处**不能**清在 `afterCompletion`（实测出来的结论）

第一版我就是写在 `afterCompletion` 里的，**实测清不干净** ——
下一次请求（同一个线程）的 `currentRequest` 里会带着上一次的**残留 3 行**
（这是我第一次尝试时实测抄下来的原文）：

```
[Filter② Cost] 耗时 95 ms  →  [Filter② Cost] 退出  →  [Filter① OrderProbe] 退出
```

**原因**：`afterCompletion` 不是最后一句代码。它执行完之后，控制权还要**退回过滤器链**，
`CostFilter` 和 `OrderProbeFilter` 在 `chain.doFilter` **之后**那几行还会继续记轨迹：

```
Filter①进入 → Filter②进入 → preHandle → Controller → postHandle → afterCompletion → 【clear】
            → Filter② 记"耗时/退出"   ← ⚠️ clear 之后又写了 3 行
            → Filter① 记"退出"         ← ⚠️ 这些就留下来了
```

| 清在哪 | `currentRequest` 实测行数 | 结论 |
|---|---|---|
| `afterCompletion` | 3 行 **+ 上一次残留的 3 行** | ❌ 清不干净 |
| **最外层过滤器最后一行** | **恰好 3 行** | ✅ 干净 |

> ⭐⭐ 口诀：**谁最后动这份数据，谁负责清理**（不是"名字里带 after 的方法就一定能收尾"）。
> 顺手记一个更保险的替代写法：**在请求最开始就"重置"一份新的**（`current.set(new ArrayList<>())`），
> 靠"入口重置"而不是"出口清理" —— 真实项目里两种都常见。

### ✍️ 本步作答（AI 代写 · 于 2026-10-16 真机复跑后填写 · 务必自己复述一遍）

**1. Filter 和 Interceptor 有什么区别？至少 3 条 + 各一个"只能用我"的场景**

① **归属不同**：`Filter` 是 **Servlet 规范**的东西（`jakarta.servlet.Filter`），Tomcat 就认；`Interceptor` 是 **Spring MVC** 的东西（`HandlerInterceptor`），不走 `DispatcherServlet` 就没有它。
② **位置不同（谁在外面）**：`Filter` 在 `DispatcherServlet` **外面**，`Interceptor` 在**里面** —— 所以 `Filter` 里抛的异常**不会**被 `@RestControllerAdvice` 接住，`Interceptor` 里的**会**（本题实测：`/trace/throw` → **409 + 统一 JSON**）。
③ **能拿到的东西不同**：`Filter` 只有 `ServletRequest/Response`，**不知道最终是哪个 Controller 方法**；`Interceptor` 的 `preHandle` 第三个参数 `handler` 是 `HandlerMethod`，能读到**类名、方法名、方法上的注解**。
④ **注册与顺序**：`Filter` 用 `FilterRegistrationBean.setOrder()`（精确控序）或 `@WebFilter`+`@ServletComponentScan`；`Interceptor` 用 `WebMvcConfigurer#addInterceptors`，顺序 = 注册顺序。

- **只能用 Filter 的场景**：给**整个请求**（含 `DispatcherServlet` 之外的首尾）计时打日志 —— 本题的 `CostFilter` 就是，它看得到拦截器看不到的那两头；另外 `CharacterEncodingFilter`（统一改编码）、包一层 `HttpServletRequestWrapper`（改/包装请求参数）也只能在 Filter 做。
- **只能用 Interceptor 的场景**：**按 Controller 方法或方法上的注解**做权限/限流（`preHandle` 拿得到 `HandlerMethod`，能读 `@RequiresPermission` 这类注解），以及和"具体业务方法"绑定的 `postHandle`/**`afterCompletion` 收尾。

**2. 为什么"清理 ThreadLocal"要写在最外层过滤器的最后一行，而不是拦截器的 `afterCompletion` 里？**

因为 **`afterCompletion` 不是这条链路的最后一句代码**：它执行完以后，请求还要沿原路"退回去"，两个过滤器在 `chain.doFilter(...)` **之后的代码还会继续跑**。

实测数据（没在过滤器里清的时候）：连续请求的 `currentRequest` 行数是 **3 → 9 → 16 → 21 → 27** 一路涨。残留的正是 **3 行**：`[Filter② Cost] 耗时 … ms`、`[Filter② Cost] 退出`、`[Filter①] 退出` —— 它们在**上一个请求** `afterCompletion` 清完之后才被写进去，于是被**下一个同线程**的请求读到。

改法：把 `recorder.clear()` 放到 **order=1 的 `OrderProbeFilter`** 里、`chain.doFilter` 之后、记完"退出"日志的**最后一行** → `currentRequest` 恒为 **3 行**（本轮实测 3/3/3/3/3）。

> 口诀：**谁最后动这份数据，谁负责清理。**

**3. `afterCompletion` 的第四个参数 `ex`，为什么在 `GET /sku/boom`（500）时还是 `null`？异常信息去哪了？**

因为异常**在到达 `afterCompletion` 之前就已经被"消费"掉了**：Controller 抛的 NPE 被 `DispatcherServlet` 交给 `HandlerExceptionResolver`（我们的 `GlobalExceptionHandler`）处理 —— 它把异常转成了 **500 + 统一 JSON**，这次请求就算"正常收尾"了，于是回调时传的是 `triggerAfterCompletion(..., null)`。

实测证据：`/sku/boom`(500) 和 `/trace/throw`(409) 两次的轨迹里都写着 **`afterCompletion（耗时 … ms，异常：无）`**。

异常信息没丢 —— 它在 `GlobalExceptionHandler` 的 `log.error("系统异常", e)` 里，启动窗口能看到完整 NPE 堆栈（`SkuService.boom(SkuService.java:212)`）。

> ⚠️ **3 行标 ⚠️ 的差异说明**（不是 bug，是设计选择）：
> - `GET /abc`、`/favicon.ico` 不带 token 实测是 **404**，答案版是 **401**。原因：我用的拦截路径是**窄拦** `/sku/**,/me/**`（题目 6.x 验收标准明确允许这种写法），所以这两个路径根本没进拦截器；答案版用的是 `/**` 全拦 + 白名单。
> - `GET /sku` 无效 token 是 **83 字符**、答案版 **76 字符**：我两个 401 出口用了**同一句** message；答案版给"token 无效"单独写了一句。形状/字段/`charset` 都齐全，**不扣分**。

## 🎤 做完之后你应该能回答

1. **Filter 和 Interceptor 的区别？谁在外面？为什么？**
   → 一条链路上：`Filter 前置 → preHandle → Controller → postHandle → afterCompletion → Filter 后置`。
2. **拦截器里 `@Autowired` 为什么是 null？怎么修？**
   → 因为拦截器是 `new` 出来的、不是 Spring Bean；改成 `@Component` + 构造器注入。
3. **`preHandle` 返回 false 之后，谁还会被调用？**
   → 它自己后面注册的拦截器的 `preHandle`、以及所有拦截器的 `postHandle` 都不执行；
   **已经通过的**拦截器的 `afterCompletion` 会执行。
4. **404 的请求、静态资源请求，走不走拦截器？**
   → 走（都会进 DispatcherServlet），handler 是 `ResourceHttpRequestHandler`；抛异常后 `postHandle` 不执行。
5. **ThreadLocal 要在哪里清理？**
   → 看谁最后写它：`CurrentUser` 在 `AuthInterceptor.afterCompletion`；
   `TraceRecorder` 在**最外层过滤器的最后一行**（写在 `afterCompletion` 会残留 3 行）。
