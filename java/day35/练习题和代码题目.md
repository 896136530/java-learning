## 第 1 步：把 MySQL 跑起来，建库建用户（5 分）

### 要做的事

1. **确认 MySQL 服务在跑、能登录**。本机路径（真机实测）：
   ```powershell
   E:\mysql\bin\mysql.exe -u root -proot -e "SELECT VERSION()"
   ```
   > ⚠️ **这个路径是按【本机】写的**（本机把 MySQL 装在 `E:\mysql`）。
   > 换一台机器就得改成本机 MySQL 的安装路径；或者把它的 `bin` 目录加进 `PATH`，
   > 以后直接用 `mysql` 就行。**别照抄路径造成的报错当成"MySQL 坏了"。**
2. **建库**（⭐ 库名就用 `day35`，**别改**，题目后面所有命令都按这个名字写）：
   ```sql
   CREATE DATABASE IF NOT EXISTS day35
     DEFAULT CHARACTER SET utf8mb4
     COLLATE utf8mb4_0900_ai_ci;
   ```
3. **看一眼字符集对不对**（这条是今天所有中文/emoji 问题的根源）：
   ```sql
   SHOW CREATE DATABASE day35;
   ```
4. **建一个专用用户**（不是必须用 root；真项目里也不该用 root），并且**只给它 day35 这一个库的权限**：
   ```sql
   CREATE USER IF NOT EXISTS 'day35'@'localhost' IDENTIFIED BY 'day35';
   GRANT ALL PRIVILEGES ON day35.* TO 'day35'@'localhost';
   FLUSH PRIVILEGES;
   SHOW GRANTS FOR 'day35'@'localhost';
   ```
   > ⭐ 注意 `ON day35.*` —— 这就是"最小权限"：这个账号**连 day21/day26 那些库都碰不到**。
   > 后面如果你用 root 跑项目也行，但要知道**这两者的差别不是"能不能跑"，而是"炸了能炸多大"**。
5. **查一遍你机器上有哪些库**（⭐ 这一步有个纪律）：
   ```sql
   SHOW DATABASES;
   ```
   > ⚠️⚠️ **你机器上的 `day21` / `day25` / `day26` / `day27` / `day28` / `day29` 里有真数据，**
   > **今天任何一条 SQL 都不许碰它们。** 你只许在自己的 `day35` 库里干活。
   > 这不是"小心一点"的问题 —— `DROP DATABASE` 没有回收站。

### 怎么验证（把输出抄进交作业表）

- `SELECT VERSION()` → `______`
- `SHOW CREATE DATABASE day35` → 里面必须有 `utf8mb4` 和 `utf8mb4_0900_ai_ci`
- `SHOW DATABASES` → 列表里必须有 `day35`，**并且你一眼能看到那几个"别人的库"**
  ⭐ 记住它们的名字，接下来 2 小时里你要一直忍着不去碰它们。

### 💡 提示

- **`utf8` 和 `utf8mb4` 不是一回事**（这是今天第一个必须记牢的点，第 7 步会亲手验证）：
  MySQL 的 `utf8` 其实是**假的 UTF-8**（内部叫 utf8mb3），**每个字符最多 3 字节**。
  而 emoji（😀）是 **4 字节** → 存进 `utf8` 列会**直接报错**。
  ⭐ **结论：建库建表一律写 `utf8mb4`，永远不要写 `utf8`。**
- `CREATE USER` 报"已存在"就用 `IF NOT EXISTS` 跳过；报密码强度问题就换复杂点的密码
  （MySQL 8 默认要装 `validate_password` 插件才会有强度检查，本机没装，`day35` 也能过）。
- 如果你用**可视化工具**（Navicat / DBeaver / Workbench）建库，**字符集那一项一定要手选 utf8mb4** ——
  工具的默认值往往是 `utf8`（甚至是 latin1），这一步没选对，第 7 步的 emoji 实验会失败得很莫名其妙。

### 💡 提示

- **H2 和 MySQL 的元数据"字段名不一样"，别以为漏建了**：
  H2 的 `CHARACTER_SET_NAME` 显示 `Unicode`，MySQL 显示 `utf8mb4`；

- **`DECIMAL(10,2)` 是什么**：一共 10 位数字，其中 2 位是小数 → 最大 `99999999.99`。

  "内联 UNIQUE KEY 名字 (列)" 那种**MySQL 专有写法 H2 不认** —— 这就是为什么两个 `.sql` 要分开写。

## 第 3 步：⭐⭐ TODO① 换驱动（pom.xml）（10 分）

### 要做的事

打开 `pom.xml`，找到那两块被注释标注的"数据库驱动"：

**① 把 H2 删掉**（整段删除，或者注释掉）：
```xml
<dependency>
  <groupId>com.h2database</groupId>

```

**③ 关于版本号，有一个"你不知道就会抄错"的事实**：

> 上面这块**不写 `<version>`** 时，版本由 SpringBoot **3.3.5 的 parent** 决定。
> 实测 `spring-boot-dependencies-3.3.5.pom` 里写的是 **`<mysql.version>8.3.0</mysql.version>`**
> → 也就是说**不写版本号会下 8.3.0**（不是网上常说的 8.4.0）。
> 验证命令（`运行Day35.bat` 菜单 6 就是它）：
> ```powershell
> mvn dependency:tree
> ```
> ⭐ 你要能说出：**"不写版本号，SpringBoot 给我的是哪个版本？我凭什么知道？"**

**④ 为什么必须先删 H2？** 一句话：**两个驱动同时在 classpath 上时，SpringBoot 可能挑错那个，
而且它不会报警告。** 你会看到"应用起来了"，但其实连的还是 H2 —— 这种"以为换了其实没换"
是最难查的一类问题。

### 怎么验证（这一步不算完，必须看到"真的换成 MySQL 了"）

| 验证项 | 命令 | 期望 |
|---|---|---|
| 依赖树里没有 h2 | `mvn dependency:tree` | 搜不到 `com.h2database:h2` |
| 依赖树里有 mysql | `mvn dependency:tree` | 有 `com.mysql:mysql-connector-j:jar:8.x.x:runtime` |
| **驱动真的换了** | 启动后看日志里的 `driverClassName` | `"com.mysql.cj.jdbc.Driver"` |

> ⚠️ 注意第 3 行：**"应用起来了"不算证据，日志里的 `driverClassName`/`jdbcUrl` 才算。**

> 现在启动会因为"没有 H2 驱动但 url 还是 h2"而**直接失败**。这是**预期的**，看到就说明你改对了。

### 💡 提示

## 第 4 步：⭐⭐ TODO② 换连接配置（application.properties）（15 分）

### 要做的事

打开 `src/main/resources/application.properties`，找到 `spring.datasource.*` 那 4 行，
把 H2 的换成 MySQL 的（文件里已经给你注释好的模板，照着改）：

```properties
spring.datasource.url=jdbc:mysql://127.0.0.1:3306/day35?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8&allowPublicKeyRetrieval=true
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
spring.datasource.username=root
spring.datasource.password=root
```

**⭐⭐ 这个 url 里有一个参数你必须自己撞一次，才能记住 —— `characterEncoding`：**

| 你写什么 | 结果（真机实测，MySQL 8.4.5 + Connector-J） |
|---|---|
| `characterEncoding=utf8mb4` | ❌ `java.sql.SQLException: Unsupported character encoding 'utf8mb4'` |
| `characterEncoding=UTF-8` | ✅ 连上（协商结果仍然是 utf8mb4） |
| 一个字都不写 | ✅ 也能连上（协商结果也是 utf8mb4） |

**⭐ 为什么 `utf8mb4` 会崩？** 因为 `characterEncoding` 是**给 Java 驱动看的**，
驱动会拿这个值去调 `String.getBytes(charsetName)` —— 而 **Java 的字符集表里只有
`UTF-8` / `utf8`，没有 `utf8mb4` 这个名字**（utf8mb4 是 **MySQL 服务端**的名字）。

> **⭐ 一句话记牢：驱动参数写 `UTF-8`，建库建表写 `utf8mb4`。两边是两套命名。**

**⭐ 顺带纠正两个"网上都说"的误解**（它们**不一定是错的，但绝不是"必然报错"**）：

| 参数 | 网上常说 | 真机实测 |
|---|---|---|
| `serverTimezone` 不写 | "一定报时区错" | **不写也能连**（那是老版本驱动的行为）。真正会报的是 `connectionTimeZone=SERVER`：`The server time zone value '?й???׼ʱ?' is unrecognized ...`；或 `connectionTimeZone=Asia/Shanghai&forceConnectionTimeZoneToSession=true`：`Unknown or incorrect time zone: 'Asia/Shanghai'`（本机 `mysql.time_zone_name` 表是空的） |
| `useSSL` 不写 | "会警告/报错" | **不报错、不警告，能连**。写 `useSSL=false` 只是为了"明确表态" |

⭐ 所以我们**仍然明确写 `serverTimezone=Asia/Shanghai`** —— 理由不是"不写会炸"，
而是"**写上之后，不管本机还是服务器、不管时区表空不空，时间口径都被钉死**"。

**还要改一处（很容易漏）**：H2 网页控制台换成 MySQL 之后没用了（它只能连 H2），
把 `spring.h2.console.enabled` 从 `true` 改成 `false`，免得你以为它还能查 MySQL。

### 怎么验证

1. **启动，日志里必须看到这两行**（真机实测原文，把值抄下来）：
   ```
   HikariConfig : driverClassName................."com.mysql.cj.jdbc.Driver"
   HikariConfig : jdbcUrl.........................jdbc:mysql://127.0.0.1:3306/day35?...
   ```
2. **打 `GET /db/pool`**（这是今天新加的连接池窗口），确认 `driverClassName` 和 `jdbcUrl` 都是 MySQL。
3. **故意写错一次，把原始报错抄下来**（这是作业内容的一部分）：
   把 `characterEncoding` 改成 `utf8mb4`，重启，**原样抄下控制台里的异常**，
   然后改回 `UTF-8`。⭐ 这一行报错原文是交作业必填项。

### 💡 提示

- 连接不上先按这个顺序排查（**从最外层往里查**）：
  ① MySQL 服务起来了吗（`netstat -ano | findstr ":3306"` 有 LISTENING）
  ② 账号密码对不对（用 `mysql` 命令行登一次，排除"是配置还是账号"的问题）
  ③ 库建了吗（`SHOW DATABASES` 里有 `day35`）
  ④ url 参数（`characterEncoding` 写 `UTF-8`）
- **`allowPublicKeyRetrieval=true`**：MySQL 8 默认用 `caching_sha2_password` 认证，
  某些情况下会报 `Public Key Retrieval is not allowed`，加上它省事。
- **`127.0.0.1` 而不是 `localhost`**：`localhost` 可能先走 IPv6（`::1`）再回落，
  慢的时候你会以为"数据库卡了"。本地开发写 `127.0.0.1` 最省心。

- `init()`：不再建表，改为**自检**（表在不在？顺便打一行"我连的是哪个库、什么版本"）
- `reset()`：MySQL 上**不能写 `RESTART IDENTITY`**（H2 方言，MySQL 不认这个词），
  并且 ⚠️⚠️ **必须临时关掉外键检查**，否则：
  ```
  ERROR 1701 (42000): Cannot truncate a table referenced in a foreign key constraint
  (`day35`.`orders`, CONSTRAINT `fk_orders_sku`)
  ```
  → 用 `SET FOREIGN_KEY_CHECKS = 0` … `SET FOREIGN_KEY_CHECKS = 1` **包起来**，
  并且 ⚠️ 那句 `= 1` **必须放在 `finally` 里**（不然中途报错，外键检查就永远关着了）。

> ⭐ **"先清子表再清父表"这个顺序，在 MySQL 上还是不够** —— 哪怕 `orders` 已经空了，
> **只要那张表还在、还带着外键，它就不让你 TRUNCATE `sku`**。这一条跟直觉相反，必须记下来。

**④ 检查一个细节：`orders` 表里有一列叫 `count`。** 它和内置函数 `COUNT()` **同名**，
所以**写 SQL 时统一加反引号** `` `count` ``。H2 和 MySQL 都吃反引号。
> ⚠️ 顺便纠正一个常见说法：`count` **不是** MySQL 的保留字 ——
> 真机实测 `CREATE TABLE t (id INT PRIMARY KEY, count INT)` **建表成功**。
> 真正裸用会报 `ERROR 1064 (42000)` 的是 `order` / `desc` / `key` / `group` 那一类。
> ⭐ 结论不变：**统一加反引号是好习惯**，比背"哪个词是保留字"省心。

**⑤ ⭐ 为什么值得做这个"搬家"？**（这个问题的答案比操作本身值钱，写进作业）

### 怎么验证

| 验证项 | 期望 |
|---|---|
| 启动日志 | `[db] 表结构自检通过：sku / orders / audit_log 都在（由 schema.sql 建好）` |
| 重复启动两次 | **都成功**（说明 schema.sql 是"可重复执行"的） |

| `SELECT COUNT(*) FROM sku` 在 reset 之后 | `3`，且**下次自增 id 还是从 1 开始**（TRUNCATE 重置了自增） |

**⑥ 思考题 ②**（关键收获）：**这次搬家，业务逻辑改了哪怕一行吗？**
如果一行没改，那你改的是什么？（提示：想"DDL 和 DML 分别是谁的活儿"。）

### 💡 提示

- **`schema.sql` 每次启动都会执行**（`mode=always`），所以它**必须可重复执行** ——
  这就是它开头那些 `DROP TABLE IF EXISTS` 的作用。
  ⚠️ 反过来说：**本地开发很爽，线上千万别这么干**（线上表里是有数据的！）。
- **`DROP` 的顺序有讲究**：先删子表（`orders`）再删父表（`sku`），否则外键会拦住。
- **`ch_demo` 只有 MySQL 建得出来** —— H2 的 `CREATE TABLE` 不支持列级 `CHARACTER SET`。
  你可以在 H2 控制台里自己试一句，把语法错误抄下来看看：

  ```

  但也让你看不到后面的接口。今天用 `false` 是**故意的**：让你体会"启动失败"和"运行失败"
  哪个更好查。⭐ 想一想：如果你把建表脚本写成"出错了也继续"，会发生什么？

## 第 7 步：刁钻用例 —— 用真库撞各种约束（20 分）

### 7.3 外键违约（orders.sku_id → sku.id）

GET /db/exec?q=INSERT INTO orders (sku_id, sku_code, title, `count`, amount, created_at) VALUES (999,'X','外键违约',1,1.00,NOW())

### 7.4 CHECK 违约之一：库存超上限
```
GET /db/exec?q=INSERT INTO sku (code,title,price,stock) VALUES ('SKU-0501','超额库存',1.00,501)
```
→ 期望：**HTTP 500**
原文：`Check constraint 'ck_sku_stock' is violated.`（错误码 3819 / SQLState **HY000**）

**⚠️ 这里有一个"跟知识点对不上"的细节，要专门记下来**：
MySQL 的 CHECK 违约**不是** `DataIntegrityViolationException`，
而是 **`UncategorizedSQLException`**（SQLState 是 `HY000`）。
⭐ 所以它**不会**被第 6 步那个 handler 接住 → 仍然走兜底 → **500**。这是对的。

### 7.5 CHECK 违约之二：负数价格

GET /db/exec?q=INSERT INTO sku (code,title,price,stock) VALUES ('SKU-NEG','负数价',-1.00,1)

### 7.6 NOT NULL 违约

### 7.7 ⭐⭐ 字符集：utf8 vs utf8mb4（emoji）
```
GET /db/charset-demo
```
这个接口会**当场做三件事**，返回结果里就是证据：
1. 往 `ch_demo.utf8_col`（`CHARACTER SET utf8`）插 `😀` → **失败**
   → `Incorrect string value: '\xF0\x9F\x98\x80' for column 'utf8_col' at row 1`（错误码 **1366**）
2. 往 `ch_demo.mb4_col`（`CHARACTER SET utf8mb4`）插同一个 `😀` → **成功**
3. 读回来：`HEX=F09F9880`、`LENGTH=4`、`CHAR_LENGTH=1`

**⭐ 这组数字要会解读**：
- `HEX=F09F9880` = emoji 的 4 个字节 → 所以 **`utf8`（最多 3 字节）根本装不下**
- `LENGTH = 4`（字节数）但 `CHAR_LENGTH = 1`（字符数）
  → **"长度"这个词有歧义**，问清楚是字节还是字符

**⑦ 思考题 ⑥**：`ch_demo` 里有 `utf8_col` 和 `mb4_col` 两列，**为什么这个实验只能在 MySQL 上做？**
（提示：去 H2 控制台试一句 `CREATE TABLE t (c VARCHAR(20) CHARACTER SET utf8)`，看它报什么。）

### 7.8 ⭐ 类型对比：字符串长度 / 金额精度 / 时间范围

**（a）超长字符串 —— H2 和 MySQL 在这里不一样！**
```
GET /db/exec?q=INSERT INTO sku (code,title,price,stock) VALUES ('一一一一一一一一一一一一一一一一一一一一一','超长编码',1.00,1)
```
（那是 **21** 个中文"一"，`code` 是 `VARCHAR(20)`）
→ MySQL 期望：**500** + `Data truncation: Data too long for column 'code' at row 1`（错误码 **1406**）
> ⚠️ **真机实测的坑**：**H2 也拦超长字符串**（21 个字符塞 `VARCHAR(20)` 同样是 500），
> 只是**报错原文不同**：H2 `Value too long for column "CODE CHARACTER VARYING(20)"`（`22001-224`）、MySQL `Data truncation: Data too long ...`（`1406`）。⭐ "只能在 MySQL 上看到"是老说法，实测不成立。

**（b）金额：DECIMAL 精确 vs DOUBLE 有误差**
```
GET /db/exec?q=CREATE TABLE IF NOT EXISTS t_money (id INT PRIMARY KEY AUTO_INCREMENT, d DECIMAL(10,2), f DOUBLE)
GET /db/exec?q=INSERT INTO t_money (d, f) VALUES (0.10, 0.10), (0.20, 0.20)
GET /db/sql?q=SELECT SUM(d) AS dec_sum, SUM(f) AS dbl_sum, (SUM(f)=0.30) AS dbl_equals FROM t_money
```
→ 真机实测结果：`dec_sum = 0.30`，`dbl_sum = 0.30000000000000004`，`dbl_equals = 0`
> **⭐ 这就是"金额绝不用 float/double"的硬证据。** 0.1 + 0.2 在浮点里不等于 0.3。
> （做完记得清理：`GET /db/exec?q=DROP TABLE t_money`）

**（c）时间的范围：TIMESTAMP 的 2038 问题**
```
GET /db/exec?q=CREATE TABLE IF NOT EXISTS t_time (id INT PRIMARY KEY AUTO_INCREMENT, ts TIMESTAMP NULL, dt DATETIME NULL)
GET /db/exec?q=INSERT INTO t_time (ts, dt) VALUES ('2038-01-19 03:14:07','2038-01-19 03:14:07')   -- 成功（TIMESTAMP 的极限）
GET /db/exec?q=INSERT INTO t_time (ts, dt) VALUES ('2040-01-01 00:00:00','2040-01-01 00:00:00')   -- ★ 失败
GET /db/exec?q=INSERT INTO t_time (dt) VALUES ('2040-01-01 00:00:00')                          -- 成功（DATETIME 能到 9999）
GET /db/sql?q=SELECT id, ts, dt FROM t_time ORDER BY id
```
→ 第 2 条期望 **500**：`Data truncation: Incorrect datetime value: '2040-01-01 00:00:00' for column 'ts'`
→ 第 3 条期望 **200**
> **⭐ 差异要能说清楚**：
> - `TIMESTAMP` 存的是"**UTC 秒数**"，范围到 **2038-01-19 03:14:07**（32 位有符号整数的极限）；
>   读回来还会**按连接时区换算**（所以 `ts` 读出来是 `2038-01-18T19:14:07Z`，比我们写的少 8 小时）
> - `DATETIME` 存的是"**字面的日期时间**"，范围到 **9999**，**不做时区换算**（读回来就是 `2038-01-19T03:14:07`）
> ⭐ 结论：**"成立时间/发布时间"这种业务时间用 `DATETIME`；"这条记录什么时候写进来的"用
> `TIMESTAMP`（因为要按 UTC 存、按本地时区看）**。别把两者当同一个东西。
> （做完清理：`GET /db/exec?q=DROP TABLE t_time`）

### 7.9 逻辑删除的"证据"（为第 8 步铺垫）
做到这一步时你可能还没改 TODO⑥，**先记住现在（物理删除）的样子**：
```
POST /db/reset
DELETE /sku/3
GET /db/sku     ← 交付版：★ id=3 那一行**不见了**

## 第 8 步：⭐⭐ TODO⑥ 物理删除 → 逻辑删除（5 分）

### 要做的事

**① `SkuRepository.deleteById` 现在是物理删除**：
```java
return jdbc.update("DELETE FROM sku WHERE id = ?", id);
```
改成**逻辑删除**（把标记位置 1）：
```java
return jdbc.update("UPDATE sku SET is_deleted = 1 WHERE id = ? AND is_deleted = 0", id);
```

**⭐ 为什么 `WHERE` 里还要带 `AND is_deleted = 0`？**（这个"眼"要能说出来）
1. **幂等**：重复删同一条，第二次影响行数 = 0（而不是"又是 1"），
   调用方就能区分"真删到了"和"早就删过了"（Day28 的规矩：**0 不是异常**）
2. **不覆盖删除信息**：真实项目的逻辑删除通常还会写 `deleted_at = NOW(), deleted_by = ?` ——
   重复删会把这些信息覆盖成错的
3. **返回值的语义**：影响行数 = "这次删掉了几条"，没这个条件它会永远返回 1，**骗人**

**② 检查那些 SELECT 是不是都带了 `AND is_deleted = 0`**（Day35 的代码里已经带了，
但你要**逐一确认**）：`findAll` / `findById` / `countAll` / `existsByCode` / `search`。

**③ ⚠️ 有一处**故意**没加，是留给你的课后思考题**：`decreaseStock`（扣库存）里
没有 `AND is_deleted = 0`。**想一想：这是 bug 还是有意为之？**

### 怎么验证（逐条对）

| 步骤 | 交付版（改之前） | 你要做到（改之后） |
|---|---|---|
| `POST /db/reset` 然后 `DELETE /sku/3` | 200 | 200 |
| `GET /db/sku` | ⭐ **id=3 那一行不见了** | ⭐ **还能看到 id=3，但 `is_deleted = true`** |
| `GET /sku`（业务列表） | 2 条 | 2 条（一样） |
| `GET /sku/3` | 404 | 404（一样） |
| `GET /db/state` | sku 数组 2 行 | sku 数组 2 行（一样） |
| `GET /db/sql?q=SELECT COUNT(*) AS total, SUM(is_deleted=1) AS deleted FROM sku` | `total=2` | ⭐ **`total=3, deleted=1`** |
| `DELETE /sku/3` **再删一次** | 404 | 404（一样，因为影响行数 0） |

> ⭐ **最后两行是重点**：改完之后，"商品还有几条"这件事**有两个不同的答案**
> （`COUNT(*)` = 3，业务视角 = 2），**两个都是对的** ——
> 你必须清楚自己写统计的时候用的是哪一个。
> ⭐ 交付版里那个 `total=2` 和换成 MySQL 之后的 `total=3` 是**同一个请求的两种世界**，
> 这就是你今天的"改造前 vs 改造后"最强的一组证据。

**④ 再试一件事**：逻辑删除 `SKU-0003` 之后，**再新增一个同编码 `SKU-0003`**：
```
POST /sku  {"code":"SKU-0003","title":"重新上架","price":89,"stock":1}
```
→ **会被拦住（409）！** 回去看第 2 步的思考题 ①，现在你应该能答了。

### 💡 提示

- **逻辑删除的三个代价，今天全都会踩到**（面试爱问）：
  ① **每个查询都必须记得带 `AND is_deleted = 0`** —— 漏一个地方就等于"删了还能查到"。
     真实项目里靠 MyBatis-Plus 的 `@TableLogic` 自动加（Day38~40 会学），或者做成视图。
  ② **唯一索引会打架**：本表既有 `UNIQUE(code)` 又有 `UNIQUE(code, is_deleted)`，
     **严格的那条说了算** → 已经"删掉"的编码**不能重用**。⭐ 这是**故意的教学点**：
     真要允许重用，就得**去掉 `UNIQUE(code)`，只留 `(code, is_deleted)`**
     （但那样 `is_deleted` 只能有 0/1 两种值，删两次就不行了 —— 所以真实项目常用
     `deleted_at` 或 `deleted_flag = id` 这种技巧）。
  ③ **`COUNT(*)` 和 `COUNT(*) WHERE is_deleted = 0` 给出不同的数** —— 写统计时要清楚用哪个。
- ⭐ **为什么不干脆物理删除？** 三个理由：① 数据还能找回来；② 外键/历史数据不会断
  （订单里存着 `sku_id`，把 sku 真删了，历史订单就指向空气了）；③ 删得便宜
  （DELETE 要挪数据页、维护索引；UPDATE 一个标记位轻得多）。

它在一个事务里**故意占住**一条连接 5 秒（⭐ **`@Transactional` 是关键**：
不在事务里，JdbcTemplate 每句 SQL 都是"借一条 → 用完立刻还"，

1. 在 `application.properties` 里**临时加三行**（改完**必须重启**）：

   spring.datasource.hikari.minimum-idle=2
   spring.datasource.hikari.connection-timeout=2000
   ```
2. **同时**打 4 个 `/db/hold?ms=5000`（**是并发，不是一个一个打**）
   ```powershell
   # 起 4 个并发请求（这条命令在 PowerShell 里直接能用）
   1..4 | ForEach-Object { Start-Job { Invoke-WebRequest 'http://127.0.0.1:8081/db/hold?ms=5000' -UseBasicParsing -TimeoutSec 30 | Select-Object -ExpandProperty StatusCode } }

4. **去日志里抄下"池子耗尽"的原话**（作业必填）：
   ```
   java.sql.SQLTransientConnectionException: HikariPool-1 - Connection is not available,
   request timed out after 2013ms (total=2, active=2, idle=0, waiting=0)

| 验证项 | 期望 |
|---|---|
| `/db/pool` 能返回 | 200，且有 `maximumPoolSize` / `totalConnections` / `idleConnections` |

### 💡 提示

- **为什么要连接池？** 因为"建一条数据库连接"很贵（TCP 握手 + 认证 + 服务端分配线程）。
  每来一个请求就建一条、用完就关，QPS 一高服务端直接被连接风暴打垮。
  ⭐ 面试常说"连接池能快一个数量级"—— 记这个量级就够了，别背具体倍数（跟机器和网络有关）。
- **`waiting > 0` 是关键指标**：如果你在真实项目里看到它持续 > 0，
  说明"池子小了"**或者**"有慢 SQL 占着连接不放"。
- **H2 特有的坑（MySQL 上不会遇到）**：`spring.datasource.url` 里那个
  `DB_CLOSE_DELAY=-1` 是 H2 自己的"别删内存库"开关。
  **不加它，连接池空闲回收连接时把最后一条也关了，H2 就顺手把整个内存库删了** ——
  你会看到莫名其妙的"表不存在"。⭐ 这就是"连接池"和"H2 内存库"的交互 bug，
  换成真 MySQL 之后自动消失（数据不在你的进程里了）。

   （提示：让两条路径**最终走进同一个异常**，或者把"先查"变成"锦上添花"而不是"唯一防线"。）

2. **"重复插入"的三种救法**（这是这道题的延伸，也是面试高频）：
   - A：捕获异常 → 转成 409（**今天做的**）
   - B：`INSERT ... ON DUPLICATE KEY UPDATE` —— ⚠️ 注意它的返回值：
     **1 = 插入成功、2 = 更新了、0 = 啥也没变**（这个"陷阱"很多人在统计影响行数时踩过）
   - C：`INSERT IGNORE` —— ⚠️ 它**把所有错误都变成警告**（不只是重复键！数据格式错也悄悄忽略）
   ⭐ 三个方案各自的代价是什么？为什么本包用了 A？

3. **逻辑删除 + 唯一索引的正确组合**：本包现在是 `UNIQUE(code)` 和
   `UNIQUE(code, is_deleted)` **同时存在**（所以已删编码不能重用）。
   如果产品要求"删掉的编码可以重新用"，你会怎么改表？
   （提示：`is_deleted` 只有 0/1 两个值是不够的 —— 想想 `deleted_at` 为 null/非 null 的写法，
   或者"删除时把 code 改名"的取巧办法。）

4. **CHECK 约束该不该用**：MySQL 5.7 会**静默忽略** CHECK，8.0.16 起才真正生效。
   如果你们团队有人用 5.7 开发、5.7 上线，你写在 `schema.sql` 里的 CHECK 会发生什么？
   ⭐ 这意味着"约束"能不能当"保证"，取决于**版本** —— 你怎么防止这类问题？

5. **`DECIMAL` 也会"错"**：今天你看到 `DOUBLE` 算错钱，所以用了 `DECIMAL`。
   那 `DECIMAL(10,2)` 存"单价 0.005 元"会发生什么？（提示：想想四舍五入发生在哪一步，
   `Java` 的 `Integer` → `BigDecimal` 那条路还没走完 —— 这是本包**诚实标注**的遗留问题。）

6. **连接池大小的"标准答案"其实是错的**：网上常说"`maximumPoolSize` 设成
   CPU 核数 × 2 + 磁盘数"。⭐ 但如果你去看 `/db/pool` 里的 `waitingForConnection`，
   你会发现真正决定池子大小的**不是公式，而是"一次请求占用连接的时长"**。
   想一想：如果有一个慢 SQL 占着连接不放，你把池子调到 100 有用吗？

7. **H2 到底能不能当"原型开发库"**：今天你看到了 H2 的几处"不较真"
   （没有 utf8 三字节限制、没有字符集概念、`TIMESTAMP` 没有 2038、`DOUBLE` 精度和 MySQL 不同）。
   ⭐ 那么"用 H2 开发、用 MySQL 上线"这种做法的**风险**在哪？
   你在今天的实验里，**哪一条差异最容易让你上线后才发现问题**？
