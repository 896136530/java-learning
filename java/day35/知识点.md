## 1. ⭐ 换库三步（照顺序做，别跳）

**第一步：换依赖**（`pom.xml`）

```xml
<!-- 删掉 H2，换成 MySQL 驱动（不写 <version> 时，SpringBoot 3.3.5 的 parent 给的是 8.3.0） -->
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
```

**第二步：换配置**（`application.properties`）

```properties
spring.datasource.url=jdbc:mysql://127.0.0.1:3306/day35?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=UTF-8
spring.datasource.username=root
spring.datasource.password=root
spring.datasource.driver-class-name=com.mysql.cj.jdbc.Driver
```

### ⚠️⚠️ 这里有一个**会直接连不上**的坑（真机实测）

| URL 里写 | 结果 |
|---|---|
| `characterEncoding=utf8mb4`（看着最"对"）| ❌ **连不上**：`SQLException: Unsupported character encoding 'utf8mb4'` |
| `characterEncoding=UTF-8` | ✅ 能连，协商结果**仍然是 utf8mb4** |

**原因**：`characterEncoding` 要的是 **Java 那边的字符集名**（`UTF-8`），`utf8mb4` 是 **MySQL 那边的名字**。
→ **URL 里永远写 `UTF-8`**。

另外两条老博客说法，在 MySQL 8.4 + Connector/J 8.4 上**不成立**：
- `serverTimezone` **不写也能连**（瞎写反而报 `ZoneRulesException: Unknown time-zone ID`）
- `useSSL` **不写不报错、也没有警告**

**第三步：建库建表**

```sql
CREATE DATABASE IF NOT EXISTS day35 DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
-- 表结构不手写，用项目的 schema.sql（第 5 步的活）
```

## 2. ⭐⭐ 连接池：为什么不能"每次请求新建一个连接"

**真机实测**（同一台机器，60 次取连接）：

| 方式 | 拿到的连接 | 耗时 |
|---|---|---|
| 每次 `DriverManager.getConnection()` | **60 个不同 `CONNECTION_ID`** | 610 ms |
| 走 Hikari 池子 | **1 个**复用 | 42 ms |

差一个量级。原因：新建连接 = **TCP 三次握手 + MySQL 鉴权**，几十毫秒一次，并发一上来就废。

### Hikari 的 4 个参数（SpringBoot 默认池，实测默认值）

| 参数 | 默认 | 管什么 |
|---|---|---|
| `maximum-pool-size` | **10** | 池子最多几条连接 |
| `minimum-idle` | **默认 = max = 10** ⭐ | 空闲保底几条（所以**一启动就占 10 条**，`SHOW PROCESSLIST` 能看到）|
| `connection-timeout` | 30000 ms | 等不到连接多久报错 |
| `max-lifetime` | 1800000 ms | 连接最长活多久（比 MySQL 的 `wait_timeout` 短些更安全）|

**池子耗尽**时（真机原文）：

```
SQLTransientConnectionException: HikariPool-day35 - Connection is not available,
request timed out after 3006ms (total=3, active=3, idle=0, waiting=1)
```

看 `total / active / idle / waiting`：**total 满、active = total、idle=0 = 池子真不够用**。
（`waiting` 可能是 0 或 1，看你打日志的时机；池名取决于 `pool-name`。）

## 3. ⭐⭐⭐ 还债：数据库约束"真的触发"时会发生什么

先回忆 Day32 那张表：

| 层 | 靠什么 | 出错状态码 |
|---|---|---|
| ① 注解校验 | `@NotBlank` / `@Valid` | 400 |
| ② Service 手写 | `if` + 查库 | 409 |
| ③ **数据库约束** | **唯一索引 / NOT NULL / 外键** | **走不到 —— 有问题就是 500** |

**第 ② 层为什么挡不住？** 它"先查再插"（check-then-act）：两个请求同时查到"没有"，然后都去插——唯一索引在**存储引擎里**判重，并发钻不过去。

### 3.1 真机报错原文（背这条）

```
ERROR 1062 (23000): Duplicate entry 'xiaoming' for key 't_user.uk_username'
```

拆开：错误号 `1062` / SQLState `23000`（`23` = 完整性约束违反）/ 重复的值 / 索引名 `表名.索引名`。

### 3.2 从数据库到接口的 5 步链路

```
① MySQL 存储引擎判重 → ERROR 1062 (23000)
② Connector/J → java.sql.SQLIntegrityConstraintViolationException
③ Spring 的 SQLExceptionSubclassTranslator → org.springframework.dao.DuplicateKeyException
④ 事务拦截器先回滚
⑤ 你的 GlobalExceptionHandler 只有 Exception 兜底 → 500「服务器开小差了」
```

⭐ ③ 的机制：MySQL 在 Spring 的 `sql-error-codes.xml` 里**没有** `useSqlStateForTranslation`，
走的是 **JDBC 异常子类兜底**（`SQLIntegrityConstraintViolationException` → `DataIntegrityViolationException` 家族）。

### 3.3 容易漏的点：`CHECK` 违约**不是** `DataIntegrityViolationException`

| 违约类型 | 真机码 | Spring 异常 |
|---|---|---|
| 唯一索引 | `1062` / `23000` | `DuplicateKeyException`（`DataIntegrityViolationException` 子类）|
| NOT NULL | `1048` / `23000` | `DataIntegrityViolationException` |
| 外键 | `1452` / `23000` | `DataIntegrityViolationException` |
| **CHECK** | **`3819` / `HY000`** | ⚠️ **`UncategorizedSQLException`**（不在 DataIntegrity 家族）|

→ 只 `catch (DataIntegrityViolationException)` 的项目，**CHECK 违约会漏网变 500**。

### 3.4 三种正确处理方式（取舍）

| 做法 | 怎么写 | 优点 | 缺点 |
|---|---|---|---|
| **A. 捕获转 409**（推荐）| `@ExceptionHandler(DuplicateKeyException.class)` → 409 | 语义准确、文案可控 | 记得别把 `e.getMessage()` 吐给前端 |
| B. `INSERT ... ON DUPLICATE KEY UPDATE` | 一条 SQL 搞定"有则更新" | 少一次异常 | `ROW_COUNT` 有坑：**插入=1 / 真改了=2 / 值没变=0** |
| C. `INSERT IGNORE` | 重复就跳过 | 最省事 | **会吞掉别的错误**（NOT NULL、外键都变"静默成功"）|

⭐ **三层不是三选一，是三层都留着**：注解拦明显格式错（400）→ Service 拦业务规则（409）→ 数据库兜底保证最终一致。

## 4. ⭐⭐ 约束六件套 + 四个易混点

| 约束 | 作用 | 违约时 |
|---|---|---|
| `NOT NULL` | 不能为空 | `1048` / `23000` |
| `DEFAULT` | 不填给默认值 | — |
| `PRIMARY KEY` | 唯一 + 非空 + 聚簇索引 | 重复 `1062` |
| `UNIQUE` | 唯一，可多个 NULL | 重复 `1062` |
| `FOREIGN KEY` | 引用别的表 | `1452` / `23000` |
| `CHECK` | 表达式校验（8.0.16+ 才真正强制）| `3819` / `HY000` |

1. **唯一约束 = 唯一索引**（本质一回事）：`SHOW INDEX FROM 表` 里 `Non_unique = 0` 就是它。
2. **联合唯一索引**：`UNIQUE KEY uk_user_date (user_id, day)` → 同一用户同一天只一条。
   违约原文：`Duplicate entry '1-2026-10-23' for key 't_checkin.uk_user_date'`（两个值用 `-` 拼）。
3. **外键会自动建索引**：建了 `FOREIGN KEY (sku_id)`，`SHOW CREATE TABLE` 里会多一条 `KEY fk_orders_sku (sku_id)`。
4. **外键约束名在同一个库里必须唯一**：换张表再叫 `fk_order_user` → `ERROR 1826 (HY000): Duplicate foreign key constraint name 'fk_order_user'`。

## 5. ⭐ 逻辑删除 vs 物理删除

```sql
-- 物理删除（真没了，恢复不了、没法追溯）
DELETE FROM sku WHERE id = ?;

-- 逻辑删除（行业标准做法）
UPDATE sku SET is_deleted = 1 WHERE id = ? AND is_deleted = 0;
```

配套三条：
1. 表里加 `is_deleted TINYINT DEFAULT 0`；
2. **所有查询都带 `AND is_deleted = 0`**（漏一处就会查出"已删除"的数据）；
3. 想"删了还能用同一个编码重新加" → 唯一索引建成 **`UNIQUE (code, is_deleted)`**，而不是只 `UNIQUE (code)`。

⚠️ 坑：软删后想用同一个 `code` 重插，若唯一索引只有 `code`，会撞 `1062`（行还在，只是标了删除）。

## 6. ⭐⭐⭐ 字段类型：三个必须记的

**① 金额 = `DECIMAL(10,2)`，绝不用 `FLOAT` / `DOUBLE`**

真机实测（存 0.10 和 0.20 再求和）：

| 类型 | 求和结果 |
|---|---|
| `DECIMAL(10,2)` | `0.30` ✅ |
| `DOUBLE` | `0.30000000000000004` ❌ |
| `FLOAT` | `0.30000000447034836` ❌ |

⭐ 有意思：`SELECT 0.1 + 0.2` 直接算会得到 `0.3`（字面量按 DECIMAL 算）——**问题出在"存进去"那一步，不是加法**。

**② `VARCHAR(n)` 的 n 是"字符数"，不是字节数**

20 个汉字能进 `VARCHAR(20)`（占 60 字节）；第 21 个才报 `1406: Data too long`。

**③ `DATETIME` vs `TIMESTAMP`**

| | `DATETIME` | `TIMESTAMP` |
|---|---|---|
| 范围 | 1000 ~ 9999 年 | 1970 ~ **2038-01-19** |
| 时区 | 存字面值，不转换 | **按 UTC 存，读时转会话时区** |
| 建议 | 业务时间用它 ✅ | 只在需要"自动时区转换"时用 |

真机：2040 年插 `TIMESTAMP` → `ERROR 1292`；插 `DATETIME` → 成功。
会话时区改成 `+00:00` 再看同一行：`DATETIME` 不动（`23:59:59`），`TIMESTAMP` 从 `23:59:59` 变 `15:59:59`（时区转换铁证）。

## 7. ⭐⭐⭐ 字符集：MySQL 里的 `utf8` 是"假的 UTF-8"

`SHOW CREATE TABLE` 里你写 `CHARSET=utf8`，MySQL 存的是 **`utf8mb3`**（最多 3 字节）。

| 字符 | 字节数 | 能进 `utf8mb3` 吗 |
|---|---|---|
| 数字 / 英文 | 1 | ✅ |
| 汉字 | **3** | ✅（所以**看不出问题**，这坑才隐蔽）|
| emoji 😀 | **4** | ❌ `ERROR 1366 (HY000): Incorrect string value: '\xF0\x9F\x98\x80'` |

→ **一律 `utf8mb4`**（建库、建表、列级都写它）。项目里有张 `ch_demo` 表专门对照这两列，用它亲眼确认。

## 8. ⭐⭐ H2 → MySQL 差异：只记"真的不一样"的

| 差异 | 真相 |
|---|---|
| 自增 | H2 `IDENTITY` / MySQL `AUTO_INCREMENT`，DDL 要换写法 |
| 表名大小写 | Windows 不敏感，**Linux 敏感**（本机没条件实测，别当已验证）|
| `LIMIT m,n` | ⚠️ **两边都支持**（H2 2.2.224 实测一致），不是 MySQL 独有 |
| 保留字 | `order`/`desc`/`key`/`group`/`index`/`rank`/`system`/`range`/`condition`/`usage` 要加反引号；**`status` 不是保留字** |
| `VARCHAR` 超长 | ⚠️ **两边都拦**（H2 `Value too long ... [22001-224]` / MySQL `Data truncation ... [1406]`），不是"只有 MySQL 管" |
| 字符集 | H2 没有列级字符集概念，emoji 随便存；MySQL 的 `utf8mb3` 存不了 emoji |
| `TIMESTAMP` | H2 没有 2038 限制；MySQL 有 |
| 浮点精度 | `DECIMAL` 两边都精确；差异在 `DOUBLE`/`FLOAT` |

⭐ 一句话：**"H2 不较真"的地方没有想象的多** —— 真坑你的是**字符集、2038、浮点精度**这三样。

## 9. 🎤 面试三句话（背下来）

1. **"唯一索引是并发下唯一可靠的那道防线，`先查再插`是矮栏杆。"**
2. **"数据库拦截 ≠ 用户体验：前者靠唯一索引保数据正确，后者靠 `DuplicateKeyException → 409` 保体验，两件事分开验收。"**
3. **"金额用 `DECIMAL` 不用 `DOUBLE`；`utf8mb4` 不叫 `utf8`；时间用 `DATETIME` 不用 `TIMESTAMP` —— 这三条都是被真机报错教出来的。"**
