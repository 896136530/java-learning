### 第 1 步（5 分）现状观察

**答案（交付版实测，每个都是"复位 → 打接口 → 查库"）**：

| # | 请求 | HTTP | 响应体字符/字节（⚠️ 仅供参照）| `orders` | `audit_log` | SKU-0001 库存 |
|---|---|---|---|---|---|---|
| ① | `POST /order/place?skuId=1&count=2&fail=none` | **200** | ≈186 / 208 | 1 ✅ | 0 | 8 ✅ |
| ② | `POST /order/place?...&fail=runtime` | **409** | 81 / 127 | **1** ⚠️ | 0 | **8** ⚠️ |
| ③ | `POST /order/place?...&fail=checked` | **500** | 71 / 97 | **1** ⚠️ | 0 | **8** ⚠️ |
| ④ | `POST /order/place-selfcall?...&fail=runtime` | **409** | 81 / 127 | **1** ⚠️ | 0 | **8** ⚠️ |
| ⑤ | `POST /order/place-swallow?...` | **200** | ≈186 / 208 | **1** ⚠️ | 0 | **8** ⚠️ |
| ⑥ | `POST /order/place-audit?...` | **409** | 79 / 121 | 0 ✅ | **0** ⚠️ | 10 ✅ |

> ⚠️⚠️ **关于"字符/字节"这一列（独立复验后的修正说明）**：
> ① 它是**参照值，不是判分依据** —— **今天所有验收只认 `GET /db/state` 的 `orders` / `auditLog` / `STOCK`**。
> ② 凡是**成功下单（200）**的那些行，响应体里带 `createdAt`，而 `LocalDateTime.toString()`
>    会**把小数秒末尾的 `0` 裁掉**，长度因此会飘：连打 60 次 `place?fail=none` 实测得到
>    **58 次 `186/208`、2 次 `185/207`**；修好后的答案版还出现过 **`184/206`**
>    （`…"createdAt":"2026-10-18T16:55:58.80248"`，只剩 5 位小数）。
>    → 这类数字一律写成 **`≈186 / 208`**；学生量到 185/207 或 184/206 **不算错**。
> ③ **失败**响应（409 / 500 / 404 …）不带 `createdAt`，长度是**稳定的**，可以照样精确比对。
> ④ 换句话说：**"长度能对上"从来不是今天的证据**，`/db/state` 的行数才是。

- ②④ 的响应体**一字不差**（同一段 JSON，SHA256 都相同），③ 是 500 —— 但**数据库里的脏数据一模一样**。
- ⑤ 更狠：响应和"正常下单"**外形完全一样**（连 `"id":1` 都给你了；只有 `createdAt` 时间戳不同）。
- ⑥ 是唯一回滚的一组，但**审计也一起没了**。

**给分**：6 个观察点全对给 5 分；只看了 HTTP 状态码、没查库的给 0~1 分
（今天最重要的一课就是"状态码不算证据"）。

### 第 2 步（5 分）谁在回滚 / 什么是代理

**标准回答**：

1. **"异常被 `@RestControllerAdvice` 接住 → 所以回滚了"是错的。** 两者互不相干：
   - **回滚**由 `TransactionInterceptor`（AOP 拦截器，包在方法外面）+ `PlatformTransactionManager`
     （本项目日志里叫 `JdbcTransactionManager`）执行；
   - **统一响应**由 advice 在最外层（DispatcherServlet 里）执行；
   - 事务拦截器**更靠里**：异常一抛出方法边界，它就先回滚了，然后才轮到 advice 把异常包装成 JSON。
2. `place()` 没注解时，SQL 是被 **JDBC 连接的自动提交（HikariCP 默认 `autoCommit=true`）**
   一条一条提交掉的 —— `INSERT` 提交了、`UPDATE` 提交了，后面的异常跟它们没关系。
3. `placeSwallow` 事务**开了**，但 `catch` 把异常**吃掉**了 → 方法正常返回 → 事务拦截器认为"一切顺利" → **commit**。

**给分**：第 1 问说清"两个人、两件事"给 3 分；第 2、3 问各 1 分。
把"回滚是 advice 干的"当成正确答案的，**这一题 0 分**（这是 Day31 的债，没还上）。

### 第 4 步（20 分）⭐⭐ TODO② 同类自调用绕过代理

**答案代码**（三种改法，推荐 A）：

```java
// ── 改法 A（最常用）：谁是对外入口，谁负责开事务 ──────────────────
@Transactional(rollbackFor = Exception.class)     // ⭐ 加在这个"对外入口"上
public Order placeViaSelfCall(Long skuId, int count, String fail) throws ExternalServiceException {
    return this.place(skuId, count, fail);        // this. 依然是原始对象，但现在外层自己就是代理入口了
}

// ── 改法 B（最彻底）：把事务方法拆到另一个 Bean ────────────────────
// OrderTxService（新类，有 @Transactional）里放真正的 writeOrderAndStock
// OrderService 注入它，调 orderTxService.place(...)
```

**⭐ 为什么 `this.place()` 不生效（标准表述）**：

> Spring 的事务是靠**代理对象**实现的：从容器里拿到的是 `OrderService$$SpringCGLIB$$0`，
> 调它的方法时，先由 `TransactionInterceptor` 读方法上的 `@Transactional`（开事务），
> 再调用**原始对象**上的真方法。
> 而 `this` 永远指向**原始对象**自己 —— 同类内部调用**必然**绕过代理，
> 那张"纸条"就没有人读了。所以：**注解没失效，是"没人看注解"。**

**⭐⭐ 三态实测（今天最值钱的一张表）**：

| 状态 | `/order/place?fail=runtime`（对照） | `/order/place-selfcall?fail=runtime`（主坑） |
|---|---|---|
| 交付版 | 409 / 81 字符；`orders=1`、库存 8 ⚠️ | 409 / 81 字符；`orders=1`、库存 8 ⚠️ |
| **中间态**（只修 TODO①）| 409 / 81 字符；`orders=0`、库存 10 ✅ | 409 / **81 字符（一字不差）**；`orders=1`、库存 **8** ⚠️ |
| 答案版 | 409；`orders=0`、库存 10 ✅ | 409；`orders=0`、库存 10 ✅ |

⭐ **中间态那一行就是答案的全部**：同一个方法、同样的参数、**响应体一字不差**，
从 `/order/place` 进就回滚、从 `/order/place-selfcall` 进就不回滚 ——
**唯一的区别是有没有经过代理**。

**日志证据**：

### 第 5 步（15 分）TODO③ 受检异常默认不回滚

**答案代码**：

```java
@Transactional(rollbackFor = Exception.class)     // ⭐ 唯一改动
```

**标准原理**（源码 `DefaultTransactionAttribute#rollbackOn` 就一行判断）：

```java
return (ex instanceof RuntimeException || ex instanceof Error);
```

**必须能回答的两个追问**：

1. **`REQUIRES_NEW` 会额外借一条连接**（外层连接被挂起但不释放）→ 连接池默认 10 条，
   别在循环里狂调（会 `Connection is not available`）。
2. **内层看不到外层未提交的数据**（H2 / MySQL 默认 READ COMMITTED）→
   所以本项目把 `order.getId()` **当参数传进去**，而不是让内层去 `SELECT` 订单表。

**给分**：改成 `REQUIRES_NEW` + `audit_log=1` → 15 分。
能指出日志里的 `Suspending` / `Resuming` → 加分项（记在加分信号里）。
改成 `NESTED` 的：`audit_log` 也留得下来（保存点机制），给 12 分并提醒
"H2 支持保存点，但真实项目里 `REQUIRES_NEW` 更常用、语义更清楚"。

| 观察项 | 结果 |
|---|---|
| HTTP | 409 / 71 字符：`{"code":"409","message":"模拟：包级事务方法里抛异常",…}` |

| 日志 | `Creating new transaction with name [...OrderService.placePackagePrivate]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT,-java.lang.Exception` + `Initiating transaction rollback` |

⭐⭐ **这条推翻了网上大量博客/面试题**："`@Transactional` 只能加在 `public` 方法上"。
本机实测（Spring 6.1 + CGLIB 代理）**包级方法的事务是生效的**。
📌 但 **`private` 一定失效**（CGLIB 是子类，无法覆写 private 方法），
而且 private 方法**只能被同类调用** → 必然同时踩第 4 步的坑，两个原因分不开，
**所以本项目没有单独实测 private（如实标注）**。

| 观察项 | 结果 |
|---|---|
| HTTP | 409 / 81 字符 |
| `orders` / 库存 | **0** / **10** ✅ |
| 日志 | `Creating new transaction with name [...OrderController.placeOnController]` + `Initiating transaction rollback` |

**为什么"不该写在 Controller 上"（三条真实理由）**：
① **事务范围过大**：把参数解析、日志、序列化都圈进来了，连接持有时间变长（连接池压力）；
② **职责错位**：Controller 负责"翻译 HTTP"，不该管数据一致性；一个 Controller 调 3 个 Service 时
"整个请求是不是一个事务边界"根本说不清；
③ **复用性**：Service 事务方法被别的 Service 调用时边界仍然正确；写在 Controller 上就废了。

**给分**：实验① 改对（去掉 readOnly）+ 能说出"H2 实测拦不住写" → 3 分；
实验② 说出"包级方法生效了、与博客相反" → 3 分（**说"失效"的给 0 分**，但也别扣太狠，这是老知识的锅）；
实验③ 说出"没有代理" → 2 分；实验④ 说出"其实生效、但不该这么写 + 理由" → 2 分。

### 第 9 步（5 分）思考题参考答案

**思考题 1：`SkuService.outbound()` 两个人同时出库会怎样？`@Transactional` 能解决吗？**

- 现在 `outbound` 的逻辑是"**先查**（`getById` 读 stock）→ 判断够不够 → 再 `decreaseStock`"。
  两个事务在 READ COMMITTED 下**都读到 stock=1**、都通过判断，
  然后各自的 `UPDATE sku SET stock = stock - 1 WHERE id = ?`（本项目 `decreaseStock` 的 SQL
  **没有 `AND stock >= ?` 这个条件**）→ **两个都成功、都提交 → stock 变成 -1（超卖）**。
- ⭐ **加上 `@Transactional` 不能解决**：事务保证的是"**要么全成、要么全不成**"（原子性），
  而这里"两个事务都成功了"，所以都提交 —— 需要的是"**互斥/隔离**"（Day28 的悲观锁 / 乐观锁）：
  ① 悲观锁：`SELECT ... FOR UPDATE` 把行锁住再算；
  ② 乐观锁 / 条件更新：`UPDATE sku SET stock = stock - ? WHERE id = ? AND stock >= ?`，
  看**影响行数**是不是 1（0 行 = 别人先抢走了）；
  ③ 数据库兜底：`CHECK (stock >= 0)` 约束 / 唯一约束。
- 📌 诚实标注：**"超卖"这件事本项目没有做并发压测**（没实测），
  上面是按代码逻辑 + Day28 知识的分析；`decreaseStock` 的 SQL 原文可在
  `sku/SkuRepository.java` 里核对。

**思考题 2：`setRollbackOnly()` 还是 `throw e;`？**

| | `setRollbackOnly()` | `throw e;` |
|---|---|---|
| 数据 | 回滚 ✅ | 回滚 ✅ |
| 接口 | **200**（前端以为成功）| **409**（前端知道失败）|
| 适用 | "这次失败**不该让用户知道**，但数据必须干净"（比如内部埋点、发短信失败不算下单失败）| ⭐ **更常见**：业务真的失败了，就该让调用方知道 |
| 风险 | 前端可能提示"下单成功"——**用户投诉的经典来源** | 需要前端/上游能正确处理 409 |

⭐ **参考结论**：**默认选 `throw e;`**（失败就要让人知道），
只有在你**明确想"业务照常成功、但某段数据不要留"**时才用 `setRollbackOnly()`。
两者都接受，关键是**能说出理由**。

**思考题 3：用一句话向没学过 Spring 的人解释**

参考答案（大意对即可，**要求不用术语堆砌**）：

> "Spring 给每个服务类请了一个**前台**（代理）。你从外面进大门办事，前台先登记（开事务），
> 再带你去里面找办事员；出了岔子，前台负责撤销登记。
> 但如果你在**里面**直接喊隔壁工位的同事（`this.other()`），那就绕过了前台，
> 没人登记 —— 你写在同事身上的'要登记'那张纸条，自然也没人看。"

**给分**：三题各约 1.7 分，能自圆其说即给分；照抄题目不写理由的不给分。

## 7. 附录：制作本包时踩到的坑（给批改人）

| # | 坑 | 现象 | 教训 |
|---|---|---|---|
| 1 | 复位用 `DELETE FROM` | H2 的自增**不归零** → 复位后 SKU 的 id 变成 4/5/6 → 所有 `skuId=1` 的接口全返回 `404 SKU 不存在：id=1`，十个场景全废 | **"清空数据" ≠ "重置状态"**：要 `TRUNCATE TABLE x RESTART IDENTITY` |
| 2 | PowerShell 里 `$args` 是自动变量 | 我的 `curl` 包装函数用它接参数 → 参数没传进 curl，**响应体被当成状态码**，报"无法将值 … 转换为 System.Int32" | 别用 `$args`/`$input`/`$home` 这类自动变量当自己的变量名 |
| 3 | PowerShell **变量名大小写不敏感** | 我在循环里写了 `$body = $r.body`，把全局的 `$BODY`（响应体临时文件路径）**覆盖成了 JSON 字符串** → 之后所有请求的 `-o` 变成乱路径，前半段还好、后半段全空 | `$body` 和 `$BODY` 是**同一个变量**！改名为 `$btxt` 才修好 |
| 4 | **curl 忘了 `-X POST`** | 验证"救法 B（rethrow）"时漏了 `-X POST` → curl 发 GET → `method 'GET' is not supported` → 500，而数据库"看起来很干净"（因为**根本没进方法**）| **假阴性**：以为回滚了，其实什么都没跑。任何"结论与预期不符"的第一次怀疑对象，应该是**请求有没有真的到达方法** |
| 5 | `Invoke-WebRequest` 拿不到错误响应体 | 401 的响应体被记成 0 字符 | 取"原始真相"一律用 `curl.exe -s -o 文件 -w "%{http_code}"` + 自己按 UTF-8 解码 |
| 6 | 残留进程占 8080 | 上一次没杀干净的 `java.exe` 占着端口，新进程启动失败，请求全打到**旧应用**上，结论全是假的 | 启动前先 `netstat -ano \| findstr :8080`；杀进程**只杀自己记录的 PID**，并且先确认父进程不是 `Code.exe`（Day33 有过误杀 VS Code Java 语言服务器的教训）|
| 7 | `.ps1` 编码 | PowerShell 5.1 把无 BOM 的 UTF-8 当 GBK → "字符串缺少终止符" | 验证脚本 `.ps1` **要 UTF-8 BOM**；`.bat` **不能有 BOM**（要 CRLF）|

⭐ **给批改人的一句话**：今天这张表里，**每一格数字背后都有一次真实的"复位 → 请求 → 查库"**；
凡是本文件没列的数字，都不要替学生"推算"。
