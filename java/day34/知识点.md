## 2. 复习：Day27 手写事务 → 为什么要有声明式

Day27 你在 JDBC 里手写过（那时候还没有 Spring）：

```java
Connection conn = dataSource.getConnection();
conn.setAutoCommit(false);                 // ① 关掉自动提交 = 开事务
try {
    updateAccount(conn, from, -money);     // ② 扣钱
    updateAccount(conn, to,   +money);     // ③ 加钱
    conn.commit();                         // ④ 都成功了才提交
} catch (Exception e) {
    conn.rollback();                       // ⑤ 出任何错，全部撤销
    throw e;
} finally {
    conn.setAutoCommit(true);
    conn.close();
}
```

**这段模板有 3 个现实问题**：

| 问题 | 说明 |
|---|---|
| ① 太啰嗦 | 每个要事务的方法都得抄一遍这 15 行，抄错一个 `commit` 就是事故 |
| ② 容易漏 | 忘了 `rollback()`、或者 `catch` 里又抛了新异常把原异常吃了 |
| ③ 和业务混在一起 | 业务代码里全是 try/catch/setAutoCommit，看不到"业务在干什么" |

**声明式事务就是来收这 15 行的**：

```java
@Transactional(rollbackFor = Exception.class)   // ⭐ 就这一行
public void transfer(Long from, Long to, int money) {
    accountDao.decrease(from, money);   // 业务只管业务
    accountDao.increase(to, money);
}
```

**多出来的那句 `rollbackFor = Exception.class` 是什么？** —— 今天第 6 节的主角，先记住：
**不写它，受检异常不会回滚**。

## 3. ⭐⭐⭐ 声明式事务的三个角色

「`@Transactional` 生效」这件事，是**三个**东西合作的结果，缺一个就静默失效：

```
①  @Transactional                  ← 一张纸条（元数据）："这个方法需要事务"
         ↓ 被谁读到？
②  TransactionInterceptor          ← 读纸条的人（AOP 拦截器 / advice）
         ↓ 它调用谁？
③  PlatformTransactionManager      ← 真正干活的人：begin / commit / rollback
         ↓ 本项目是
    JdbcTransactionManager（Spring 6 里 DataSourceTransactionManager 的新名字）
         ↓ 最终落到
    java.sql.Connection.setAutoCommit(false) / commit() / rollback()
```

### 完整调用链（今天最该刻在脑子里的一张图）

```
浏览器  POST /order/place
  │
  ├─ Filter（OrderProbeFilter / CostFilter）           ← Servlet 容器层
  │
  ├─ DispatcherServlet
  │     ├─ Interceptor.preHandle（TraceInterceptor / AuthInterceptor）  ← Spring MVC 层
  │     ├─ 【拿到 Controller 的代理，调用方法】
  │     │
  │     │   ★★★ 事务拦截器就在这里：TransactionInterceptor.invoke()
  │     │        ├─ 读方法上的 @Transactional（从"代理"上读，见第 5 节）
  │     │        ├─ openTransaction → conn.setAutoCommit(false)
  │     │        ├─ 调用真的 Service 方法（业务 + SQL 都跑在这个连接上）
  │     │        └─ 正常返回 → commit() ／ 抛异常 → rollback()
  │     │
  │     ├─ Interceptor.postHandle / afterCompletion
  │     └─ 抛异常了？→ @RestControllerAdvice 接住 → 返回统一 JSON
  │
  └─ Filter 返回
```

⭐ 从这张图里能看出两件关键的事：

1. **事务拦截器比拦截器"更靠里"**：MVC 拦截器拦的是"请求"，事务拦的是"方法调用"。
2. **异常要先穿过事务拦截器，才能到达 `@RestControllerAdvice`** —— 这就是第 4 节那道题的答案。

### 日志里的证据（真机实测，本项目开着 `logging.level.org.springframework.transaction=debug`）

```
Creating new transaction with name [com.xiaoming.day34.order.OrderService.placeSwallow]:
    PROPAGATION_REQUIRED,ISOLATION_DEFAULT,-java.lang.Exception
Initiating transaction commit
```

这一行信息量极大，四个字段分别对应注解的四个属性：

| 日志片段 | 来自注解的哪一项 | 含义 |
|---|---|---|
| `PROPAGATION_REQUIRED` | `propagation` | 默认传播行为（第 7 节）|
| `ISOLATION_DEFAULT` | `isolation` | 用数据库默认隔离级别（第 9 节）|
| `-java.lang.Exception` | `rollbackFor` | **出了 Exception 也要回滚**（前面那个 `-` 是"包含"的意思）|
| `readOnly` | `readOnly = true` | 只读事务（第 8 节）|

⭐⭐ **这是判断"事务到底开没开"的最硬证据**：
只要有 `Creating new transaction` 这行，事务就开了；没有这行，就是"压根没进代理"。

## 4. ⭐⭐ 还债：回滚不是 `@RestControllerAdvice` 干的

> 这是 Day31 留下的概念债。当时你看到"接口返回了 500 + 统一 JSON"，很自然地以为
> "**异常被全局处理器接住 → 所以数据回滚了**"。这句话里"所以"两个字是错的。

**两件事、两个人、互不相干**：

| | 统一异常处理器（advice） | 事务拦截器（`TransactionInterceptor`）|
|---|---|---|
| 管什么 | 把异常**翻译成对外的响应**（状态码 + JSON 信封）| 把已经做了一半的**数据改回去** |
| 什么时候执行 | 方法**抛出来之后**，在最外层（DispatcherServlet 里）| **包在方法外面**，异常一抛出来它就先看见 |
| 生活类比 | 前台接待（给来访者一张统一的答复单）| 会计（把钱一笔笔退回去）|
| 今天在哪儿 | `common/exception/GlobalExceptionHandler.java` | 你不用写，Spring 自动加的代理 |

**真机证据（同一份日志，两条线各走各的）**：

```
# ① 事务拦截器先看见异常 → 回滚（注意：它比 advice 早）
DEBUG --- JdbcTransactionManager : Creating new transaction with name [...OrderService.place]: ...,-java.lang.Exception
INFO  --- OrderService           : [order] 已写订单 id=1（…216 元），扣库存 2 件…，stock 10 → 8
DEBUG --- JdbcTransactionManager : Initiating transaction rollback          ← 会计在退钱
# ② advice 后看见异常 → 包装响应
WARN  --- GlobalExceptionHandler : 业务异常：code=409, http=409, message=模拟：…被拒（运行时异常）
```

**所以下面这几句话，你今天要能自己纠正过来**：

- ❌ "异常被 advice 接住了，所以事务回滚了。" → 接住异常的是 advice，**回滚是事务拦截器干的**，advice 完全不知道事务的存在。
- ❌ "我把异常 catch 住返回正常响应，事务也会回滚吧？" → 不会（第 11 节），因为事务拦截器**根本不知道出过错**。
- ❌ "没写 advice 就没有事务。" → 两者没关系，advice 只是"对外的话术"。
- ✅ 正确说法：**"回滚看的是'异常有没有抛出方法边界'，响应看的是'异常最终被谁接住'。"**

⭐ 而且反过来也成立：**advice 能接住异常，说明事务拦截器早就已经回滚完了**（它是里层）。

## 5. ⭐⭐⭐ 事务生效的唯一前提：你调的是代理

### 5.1 "代理"是什么（用今天的项目说人话）

Spring 给带 `@Transactional` 的 Bean 生成了一个**子类（CGLIB 代理）**：

```
你从容器里拿到的 OrderService，其实不是 OrderService 本人，而是它的"代办"：

    界面上的名字：OrderService（接口/类型都还是它）
    实际对象：    OrderService$$SpringCGLIB$$0   ← 代理
                     └─ 每次调用方法，代理先执行 TransactionInterceptor
                          ├─ 开事务
                          ├─ 调用 super.place(...)  ← 这才是真的本人
                          └─ 提交 / 回滚
```

⭐ 生活类比：你去政务大厅办事，**窗口**（代理）会先给你盖章登记（开事务），
再把你领到**里面的人**（原始对象）那里；出了问题，**窗口**负责撤销登记。
但如果你**绕过窗口、从后门直接找里面的人**（`this.place()`），那就没有人为你登记了。

### 5.2 什么叫"绕过代理"

```java
// 同一个类里：
public Order placeViaSelfCall(...) {       // ① 这个方法是"从外面调进来的"
    return this.place(...);                // ② this 是"本人"，不是代理！
}                                          //    → place 上那张纸条**没人读**
```

`this` 永远指向**原始对象**（`super` 那半边），所以同类内部调用**必然**绕过代理。
这就是今天的主坑（第 4 步 / 20 分）。

### 5.3 "注解到底生不生效"的 6 种写法 · **真机实测**总表

> 📌 **先看口径，别误会成"6 种全测过"**：下表 **6 行里实测了 4 行** ——
> **失效 3 行**（第 1、3、6 行）、**"其实生效"1 行**（第 2 行）；
> **第 4、5 行本项目没条件测**（如实标注在"实测数据"列里）。
> 再加上第 5.4 节的"写在 Controller 上"（**实测：也生效**），今天真正动手观察过的写法一共 **5 种**。

| # | 写法 | 事务开了吗 | 实测数据（复位后 → 打完后）| 在哪儿 |
|---|---|---|---|---|
| 1 | **同类 `this.xxx()` 调用** | ❌ 没开 | orders 0→**1**、库存 10→**8**（脏）| `/order/place-selfcall` |
| 2 | **方法不是 `public`**（包级）| ✅ **开了** | orders 0→**0**、库存 10→**10**（干净）| `/order/place-package-private` |
| 3 | **异常被自己 catch 吞掉** | ✅ 开了但**提交了** | orders 0→**1**（脏）| `/order/place-swallow` |
| 4 | **数据库引擎不支持事务**（MySQL MyISAM）| — | 本项目用 H2，**没实测**（Day35 换 MySQL 后可以试）| — |
| 5 | **多线程里调用**（事务信息在 ThreadLocal，子线程拿不到）| — | **没实测**（今天不引入线程变量）| — |
| 6 | **这个类不是 Spring Bean**（自己 `new`）| ❌ 没开 | orders 0→**1**（脏）| `/order/place-new` |

⭐⭐ **注意第 2 行 —— 这条推翻了网上大多数博客！**

> 老博客（包括很多面试题答案）都说："**`@Transactional` 只能加在 `public` 方法上，
> 写成 `protected` / 包级（default）/ `private` 就失效**"。
>
> **本机实测（SpringBoot 3.3.5 / Spring 6.1 + CGLIB 代理）**：
> `OrderService.placePackagePrivate(...)` 是**包级方法**，它被 `OrderController`（同包）跨 Bean 调用，
> 事务**正常开启并正常回滚**。日志原文：
>
> ```
> Creating new transaction with name [com.xiaoming.day34.order.OrderService.placePackagePrivate]:
>     PROPAGATION_REQUIRED,ISOLATION_DEFAULT,-java.lang.Exception
> Initiating transaction rollback
> ```
> 数据库也确认回滚了（orders=0、stock=10）。
>
> **为什么会这样？** 因为 Spring 6 起，**基于类的代理（CGLIB）可以覆写 `protected` 和包级方法**，
> 而"`publicMethodsOnly`"这个老限制对 CGLIB 代理不再是一道死墙。
>
> 📌 **但 `private` 依然一定失效**（CGLIB 是子类，子类无法覆写父类的 private 方法）。
> 而 `private` 方法**只能被同类调用**，所以它必然同时踩上第 1 条的坑 ——
> **两个原因分不开，本项目因此没有单独实测 `private`**（如实标注，不编数据）。
>
> ⭐ 面试时怎么说：**"老版本 Spring 上非 public 会失效；我实测 Spring 6 + CGLIB 的包级方法是生效的。
> 但 `private` 一定不行，同类自调用一定不行。"** —— 直接把"实测"两个字说出来，比背博客强得多。

### 5.4 还有一个反直觉的实测：`@Transactional` 写在 Controller 上**也会回滚**

| 写法 | 实测 | 说明 |
|---|---|---|
| `@Transactional` 加在 **Controller 方法**上 | ✅ **回滚了**（orders 0、stock 10）| 日志：`Creating new transaction with name [...OrderController.placeOnController]` |

**为什么？** 因为事务是**线程级**的：Controller 方法上开的事务，会盖住**同一条线程上**后续所有的
Repository / JdbcTemplate 调用 —— 哪怕那些 SQL 写在 Service 里、哪怕 Service 上什么注解都没有。

**那为什么大家还说"事务要写在 Service"？** 理由**不是"写在 Controller 上不生效"**，而是：

1. **事务范围会变大**：把参数解析、序列化、日志都圈进来了，事务持有连接的时间变长（连接池压力 ↑）；
2. **职责错位**：Controller 是"翻译 HTTP"的，不该管"数据一致性"；一个 Controller 方法调 3 个 Service 时，
   你根本说不清"这一整个请求"是不是一个事务边界；
3. **复用性**：Service 事务方法被别的 Service 调用时，事务边界还是对的；写在 Controller 上就废了。

📌 **这也是"实测"的价值**：面试时你要是说"写在 Controller 上不生效"，碰上懂行的会被当场纠正；
说"会生效，但不该这么写，原因是……"就是加分项。

## 6. ⭐⭐⭐ 回滚规则：默认只回滚 `RuntimeException`

### 6.1 默认规则（背下来）

```
   抛出的异常                          Spring 默认怎么办
   ──────────────────────────────────────────────────────
   Error（含子类）                     ✅ 回滚
   RuntimeException（含子类）          ✅ 回滚
   受检异常（Exception 的子类，          ❌ **不回滚！事务照常提交**
           但不是 RuntimeException）
```

源码里就一句话（`DefaultTransactionAttribute.rollbackOn`）：

```java
public boolean rollbackOn(Throwable ex) {
    return (ex instanceof RuntimeException || ex instanceof Error);
}
```

### 6.2 为什么这是个"静默"的坑

因为它**不报错**：接口该 500 还是 500、该 409 还是 409，日志里甚至能看到
`Initiating transaction commit` —— 一切都是"成功"的样子，只是**脏数据进了库**。

**本项目的实测（第 5 步的关键数据）**：

| 状态 | `/order/place?fail=checked`（受检异常）| orders / stock |
|---|---|---|
| 只加了 `@Transactional`（没写 rollbackFor）| HTTP 500 | **1 / 8** ← 脏 |
| 加了 `rollbackFor = Exception.class` | HTTP 500（**一模一样**）| **0 / 10** ← 干净 |

⭐ 注意"HTTP 500 一模一样"这一行 —— 这就是今天为什么必须查库。

### 6.3 怎么写才对

```java
@Transactional(rollbackFor = Exception.class)     // ⭐ 一把梭：出任何异常都回滚
public Order place(...) throws ExternalServiceException { ... }
```

三种常见写法对比：

| 写法 | 含义 | 什么时候用 |
|---|---|---|
| `@Transactional` | 只有 RuntimeException / Error 回滚 | 想"业务异常才回滚，受检异常算可恢复"（少见，容易翻车）|
| `@Transactional(rollbackFor = Exception.class)` | **任何** Exception 都回滚 | ⭐ **绝大多数业务**（本项目所有手写事务方法都用它）|
| `@Transactional(noRollbackFor = XxxException.class)` | 除了 XxxException，其它都回滚 | "这个异常是预期内的，不算失败"（比如"用户已存在"不算失败）|

📌 **一个容易混淆的点**：`rollbackFor` 管的是"**回不回滚**"，
而"**返回什么状态码**"是 `@RestControllerAdvice` 管的事（第 4 节）。
两个属性各管一头，别混。

## 7. ⭐⭐ 传播行为（Propagation）7 种

### 7.1 问题从哪来

今天项目里的真实矛盾：

> **下单要回滚，但"谁下过这一单"的审计日志必须留下。**
> 两个诉求方向相反 —— 一个要"一起撤销"，一个要"单独留存"。
> Spring 的答案是：**让内层方法自己决定"是加入外层事务，还是另开一个"**，这就是传播行为。

### 7.2 七种一览（前 4 个必须背）

| 传播行为 | 一句话 | 典型用途 |
|---|---|---|
| `REQUIRED`（**默认**）| 有事务就加入，没有就新建 | **绝大多数业务**（扣库存、改状态、转账）|
| `REQUIRES_NEW` | **挂起外层**，自己开一个全新的；外层回滚跟我无关 | ⭐ 审计日志、操作流水、失败记录 |
| `NESTED` | 嵌套（用保存点 savepoint），内层失败可单独回滚，外层仍可提交 | 批量导入里"某一条失败不影响其它条" |
| `SUPPORTS` | 有就用，没有就**非事务**执行 | 查询方法 |
| `MANDATORY` | 必须在事务里，否则**报错** | 强制约束（防止有人不走事务就调它）|
| `NOT_SUPPORTED` | 挂起外层，自己非事务执行 | 不想占用事务的操作（发邮件）|
| `NEVER` | 不能在事务里，否则报错 | 极少数 |

⭐ 生活类比：
- `REQUIRED` = **夫妻共用一张卡**：一起记账、一起退账；
- `REQUIRES_NEW` = **另开一张卡自己刷**：你那边退账，退不到我这张卡上。

### 7.3 本项目的实测（第 7 步的核心数据）

`placeWithAudit()` 里：先写订单 + 扣库存，再调 `auditService.writeLog(...)` 写审计，然后**抛异常**。

| `AuditService.writeLog` 的传播行为 | 日志原文 | orders | **audit_log** |
|---|---|---|---|
| `REQUIRED`（交付版）| `Participating in existing transaction` | 0（回滚）| **0** ← 审计也没了 |
| `REQUIRES_NEW`（答案版）| `Suspending current transaction, creating new transaction with name [...AuditService.writeLog]` + `Resuming suspended transaction after completion of inner transaction` | 0（回滚）| **1** ← ⭐ 审计留下了 |

⭐⭐ **这就是"传播行为"这四个字的可见形态**：日志里那个 `Suspending`（挂起）和 `Resuming`（恢复）
就是"另开一张卡"的动作。

### 7.4 用 `REQUIRES_NEW` 必须知道的两个代价

1. **它会另外借一条数据库连接**（外层连接被挂起但不释放）。连接池默认只有 10 条，
   如果在循环里疯狂调 `REQUIRES_NEW`，可能把连接池抽干 → `Connection is not available`（Day35 讲连接池）。
2. **内层看不到外层还没提交的数据**（H2 / MySQL 默认隔离级别是 READ COMMITTED）。
   所以本项目是把 `order.getId()` 当**参数**传进审计方法的，**而不是让内层去查订单表** ——
   内层查的话，那行订单在外层事务里还没提交，**查不到**。
   📌 这条面试常问："REQUIRES_NEW 里能读到我刚插入的数据吗？" → 读不到。

## 8. ⭐ `readOnly = true` 到底是什么（实测：它拦不住你写）

### 8.1 它做了什么

`@Transactional(readOnly = true)` 主要做三件事：
1. Spring 会把连接的 `setReadOnly(true)`（**给数据库的一个提示**）；
2. Hibernate / JPA 会跳过"脏检查"（不比对对象有没有变化），性能好一点；
3. **给人看的语义**："这个方法承诺不写库"。

### 8.2 真机实测（本项目 `/order/place-readonly`，交付版故意写成 `readOnly = true` 却在写库）

| 观察项 | 实测结果 |
|---|---|
| HTTP | **200**，响应体 **≈186 字符 / 208 字节**，**和正常下单外形完全一样** ⚠️ |
| `orders` | **1** ← 写进去了 |
| `SKU-0001` 库存 | 10 → **8** ← 也改了 |
| 日志 | `Creating new transaction with name [...placeReadOnly]: PROPAGATION_REQUIRED,ISOLATION_DEFAULT,readOnly` → 紧跟 `Initiating transaction commit` |

⭐⭐ **结论（这条也是"实测推翻想当然"）**：

> **`readOnly = true` 在 H2（HikariCP + JdbcTemplate）上拦不住写操作，SQL 照常执行、照常提交。**
> 它只是"提示 + 语义"，**不是安全防线**。
>
> 📌 想真的拦住写，得靠**别的**东西：数据库账号权限（只给 `SELECT`）、
> 或者架构上把读写分离（读库账号只读）。

⭐ 那"改前改后"差别在哪？—— **不在数据库**（两次都是 orders=1、stock=8），
差别只有两处：① 代码语义对了；② 日志里那个 `readOnly` 后缀没了。
**这也是今天唯一一个"查库看不出差别"的实验**，所以第 8 步的验收标准写的是"日志 + 解释"，不是行数。

## 10. ⭐ 事务里的"可见性"：自己看得到，别人看不到

同一个事务里的 SQL 用的是**同一条连接**，所以：

| 谁在看 | 能看到本事务刚插入、还没提交的数据吗 |
|---|---|
| **本事务自己**（同一线程 / 同一连接）| ✅ 看得到（`INSERT` 之后马上 `SELECT` 能查到）|
| **别的事务**（别的连接）| ❌ 看不到（H2 / MySQL 默认 READ COMMITTED）|
| **`REQUIRES_NEW` 的内层事务** | ❌ **看不到**（它就是"别的事务"，外层的改动还没提交）|

⭐ 所以有个很实用的结论：**不要在 `REQUIRES_NEW` 的方法里"回头查外层刚写的数据"**，
查不到是**正常行为**，不是 bug。要么把数据当参数传进去（本项目就是这么做的），
要么改成 `REQUIRED`（那就一起提交/回滚了，看你想要哪个）。

📌 再补一条和 JPA 有关的（本项目用 JdbcTemplate 所以不会遇到）：
JPA 的 `save()` 只是把对象放进"持久化上下文"，**可能一条 SQL 都没发**；
这时"查不到那行"可能是"没 flush"，也可能是"回滚了" —— **两种原因混在一起就说不清了**。
这正是第 12 节选型理由的核心。

## 11. ⭐ `setRollbackOnly()`：异常被 catch 之后怎么救

### 11.1 危险写法（本项目交付版就是这个）

```java
@Transactional(rollbackFor = Exception.class)
public Order placeSwallow(Long skuId, int count) {
    Order order = writeOrderAndStock(skuId, count);   // 已经写库了
    try {
        throw new BizRuleException("模拟：调用内部积分服务失败");
    } catch (BizRuleException e) {
        log.warn("[swallow] 异常被我 catch 了……");      // 只记了日志
        return order;                                  // ← 正常返回 → 事务**提交**
    }
}
```

**实测结果（交付版）**：HTTP **200** + 一张订单 JSON（**≈186 字符 / 208 字节**），
但数据库里 `orders=1`、库存 10→8 —— **脏数据留在库里，接口却告诉你"下单成功"**。
⭐ 更阴的一点：返回的那个 `Order` 对象里 `"id":1` 还是数据库生成的真实 id，
你会以为"订单 1 号建好了"，其实**库里根本没有这一行**。

### 11.2 两种救法

**救法 A：`setRollbackOnly()`**（想"吞掉异常、但数据必须回滚"时用 —— 这也是 TODO④ 的标准答案）

```java
import org.springframework.transaction.interceptor.TransactionAspectSupport;

} catch (BizRuleException e) {
    log.warn(...);
    TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();  // ⭐ 这一行
    return order;   // 方法照常返回 200，但事务已被标记为"只能回滚"
}
```

**救法 B：把异常继续抛出去（rethrow）**（最简单，接口会从 200 变成 409）

```java
} catch (BizRuleException e) {
    log.warn(...);
    throw e;        // ← 抛出方法边界，事务拦截器就看见了 → 回滚
}
```

> 📌 **别名对照（两篇文档已统一，别在批改时对不上号）**：
> 本文件与 `标准答案.md` 一律 **A = `setRollbackOnly()`（接口仍是 200）**、
> **B = `throw e;`（接口变成 409）**。
> 两种救法**都接受**，但**数字不同**：A 是 `200 / ≈186 字符 / orders=0 / 库存 10`，
> B 是 `409 / 74 字符 / orders=0 / 库存 10`。

### 11.3 ⭐⭐ 一个必须想清楚的点：**回滚 ≠ 报错**

答案版实测（救法 A：`setRollbackOnly()`）：HTTP 仍然是 **200** + **一模一样的订单 JSON**，
但 `orders=0`、库存 **10**（回滚了）。

| | 交付版 | 答案版（救法 A）|
|---|---|---|
| HTTP | 200 | **200（一样）** |
| 响应体 | **≈186 字符 / 208 字节** | **≈186 / 208（一样）** |
| orders | **1（脏）** | **0（干净）** |
| 库存 | **8** | **10** |

⭐ 所以：**"回滚"说的是数据，不是状态码。**
想让前端也知道失败，就得像救法 B 那样抛出去（→ 409），或者自己返回一个带错误码的统一响应。

> ⚠️ 上面两格的 `≈`：200 的响应体里有 `createdAt`，`LocalDateTime.toString()` 会把小数秒
> 末尾的 `0` 裁掉，长度会偶发少 1~2 字符（实测 60 次里 2 次是 `185/207`）。
> **它是参照值，不是判分依据** —— 判分只看 `orders` / 库存。

⚠️ 还有一个细节：`setRollbackOnly()` 之后再往库里写东西会抛
`UnexpectedRollbackException` / "Transaction is marked rollback-only"。
即：**标记之后，这个事务就只能回滚了，别再指望它提交。**

## 12. ⭐⭐ 为什么本项目选 `JdbcTemplate` 而不是 JPA（选型理由）

Day30 用的是 JPA（`spring-boot-starter-data-jpa`），今天**换成了 JdbcTemplate**
（`spring-boot-starter-jdbc` + `h2`）。四条理由，按重要性排：

| # | 理由 | 具体说明 |
|---|---|---|
| 1 | **今天的证据必须"一条代码 = 一条 SQL"** | `jdbc.update("INSERT INTO orders ...")` 立刻发 SQL，数据库里有没有这行**只取决于 commit/rollback**。JPA 的 `save()` 只是把对象挂进"持久化上下文"，**可能一条 SQL 都没发** → "查不到这行"可能是"没 flush"、也可能是"回滚了"，**两个原因混在一起，实验就不干净了** |
| 2 | **避开"一级缓存"这个假象** | JPA 查询会先看持久化上下文：同一个事务里查到的可能是**内存里的对象**，而不是库里的行。观察"回滚有没有生效"时这是致命的干扰 |
| 3 | **Day38~40 要学 MyBatis，SQL 视角更连贯** | MyBatis 也是"你写 SQL"。今天用 JdbcTemplate 把 SQL 视角先立起来，后面学 MyBatis 就是"把 JdbcTemplate 换成一个会帮你映射的框架" |
| 4 | **Day30 已经用过 JPA 了，换个视角正好对比** | 同一个项目两种数据访问方式都摸过，你才能回答"什么时候用哪个" |

**代价（要诚实说）**：JdbcTemplate 要手写 SQL 和 RowMapper，写 CRUD 比 JPA 啰嗦
（今天的 `SkuRepository` 就是 9 个方法全是 SQL）。真实项目中：

- **后台管理类项目 / 国内主流**：MyBatis / MyBatis-Plus（SQL 可控、好调优）→ **Day38~40 学**
- **对象模型复杂、表结构跟着对象走**：JPA / Hibernate（少写 SQL、迁移数据库方便）
- **一次性脚本、分析型查询、要精细控制 SQL**：JdbcTemplate

⭐ 面试话术："我两种都用过。JPA 开发快、适合模型驱动的场景；MyBatis/JdbcTemplate 对 SQL 的控制更细，
排查和调优更直接。国内业务系统里 MyBatis 更常见。" —— 别站队，说**场景**。

## 13. ⭐⭐ H2 内存库：`进程重启复位` ≠ `事务回滚`

```properties
spring.datasource.url=jdbc:h2:mem:day34;DB_CLOSE_DELAY=-1
spring.datasource.driver-class-name=org.h2.Driver
spring.datasource.username=sa
spring.datasource.password=
spring.h2.console.enabled=true
```

| 配置 | 作用 | 不写会怎样（实测踩过）|
|---|---|---|
| `jdbc:h2:mem:day34` | 内存库，库名 day34 | — |
| `DB_CLOSE_DELAY=-1` | **所有连接断开也不许删库** | 连接池一收连接，库就没了 → 报"表不存在" |
| `spring.h2.console.enabled` | 网页控制台 `/h2-console` | 少了一个"自己敲 SQL"的窗口 |

### ⭐⭐ 两个都叫"数据没了"，但完全是两件事

| | 事务回滚 | 进程重启复位 |
|---|---|---|
| 谁干的 | 事务拦截器 + 数据库 | JVM 退出，内存库跟着消失 |
| 什么时候发生 | **同一次运行中**，一个请求结束的那一刻 | **进程退出**的那一刻 |
| 怎么区分 | 复位后只打**一个**接口、**立刻**查库 | 重启后**一定是**种子数据（orders=0）|

📌 **为什么必须区分？** 因为"我看到订单表是空的"这个现象，
可能是"回滚成功了"，也可能是"你刚才重启了应用"。
**实验纪律：复位 → 只做一个操作 → 立刻查库**（别在中间重启）。

### `/db/reset` 和真机踩到的那个坑

本项目提供了一个复位接口（`POST /db/reset`），它用：

```sql
TRUNCATE TABLE orders RESTART IDENTITY;
```

⚠️ **第一版我写的是 `DELETE FROM orders`，结果整个项目跑不通了**：
`DELETE` 只删行、**不会让自增计数器归零**，复位后 SKU 的 id 变成了 4、5、6，
所有写死 `skuId=1` 的接口全部返回 `404 SKU 不存在：id=1`。

⭐ 教训：**"清空数据"和"重置状态"是两件事**。
凡是要求"回到同一个起点"的地方，都要问一句："自增、序列、时间戳这些**隐藏状态**也回去了吗？"
（Day35 换成 MySQL 时，`TRUNCATE TABLE` 自带重置自增，写法更简单。）

## 14. ⭐⭐ 排错流程：先查库，别看响应码

今天给你一套**四步取证法**（以后遇到"数据不对"的线上问题也是这个顺序）：

```
① POST /db/reset                  ← 回到已知起点（不然结论不可信）
② 只打一个接口，记住它的响应         ← 状态码 + 响应体字符数
③ GET /db/state                   ← 硬证据：orders / auditLog / 每行库存
④ 翻日志：有没有 "Creating new transaction" / "Initiating transaction rollback"
```

**本项目的查库窗口**：

| 接口 | 作用 |
|---|---|
| `GET /db/state` | 一眼看全：`orders` 行数、`audit_log` 行数、三行 SKU 的库存 |
| `GET /db/orders` | 订单表内容 |
| `GET /db/audit` | 审计表内容 |
| `GET /db/sku` | 商品表内容 |
| `GET /db/sql?q=SELECT COUNT(*) AS N FROM orders` | ⭐ 自由查询（本地调试用）|
| `POST /db/reset` | 复位 |
| `GET /h2-console` | ⭐ 网页版 SQL 窗口（JDBC URL 填 `jdbc:h2:mem:day34`，用户 `sa`、密码空）|

⚠️ **安全提醒**：`/db/sql` 这种"能执行任意 SQL"的接口**绝对不能上生产**（等于把数据库交出去）。
今天开放它，只因为它是本地内存库 + 我们就是要"想查什么就查什么"。
真实项目里调试接口要么删掉、要么加权限。

## 15. 常见坑（每条都有实测依据）+ 🎤 面试三句话

### 15.1 常见坑清单

| # | 坑 | 现象 | 正解 |
|---|---|---|---|
| 1 | **同类 `this.xxx()` 调用** | 注解写了，但"什么都没发生"（脏数据入库）| 把事务方法拆到另一个 Bean；或给"对外入口"自己加注解 |
| 2 | **只写 `@Transactional`，不写 `rollbackFor`** | 受检异常时不回滚（接口 500，数据却改了）| `rollbackFor = Exception.class` |
| 3 | **catch 之后不抛也不 setRollbackOnly** | 接口 200 + 脏数据 | `throw e;` 或 `setRollbackOnly()` |
| 4 | **以为是 advice 在回滚** | 排查方向完全跑偏 | 回滚是事务拦截器干的（第 4 节）|
| 5 | **写在 Controller 上，以为"不生效"** | 其实**生效**（实测），但事务范围过大、职责错位 | 写在 Service 层 |
| 6 | **以为 `readOnly = true` 能防写** | H2 实测：**照写不误** | 它是提示，不是防线 |
| 7 | **`REQUIRES_NEW` 里查外层未提交的数据** | 查不到（正常行为）| 当参数传进去 |
| 8 | **在 `REQUIRES_NEW` 里改外层锁住的行** | 死锁（互相等）| 内层只动"不同表"（如审计表）|
| 9 | **复位用 `DELETE`** | 自增不归零 → 后续 `skuId=1` 全 404 | `TRUNCATE ... RESTART IDENTITY` |
| 10 | **重启后看到空表，以为回滚成功** | 其实是内存库没了 | 分清"重启"和"回滚" |
| 11 | **以为接口 500 = 数据没改** | 完全可能改了（受检异常那条）| 任何"失败"都查库确认 |
| 12 | **`@Transactional` import 错了包** | 编译过、跑起来没事务 | 必须是 `org.springframework.transaction.annotation.Transactional` |

📌 **"实测"和"没实测"各是哪些（如实标注，别混在一起说）**：

**✅ 本项目实测过的（5 种写法，都能给出日志原文）**：
- **失效 3 种**：同类 `this.xxx()` 自调用、异常被 `catch` 吞掉（事务提交了）、类不是 Spring Bean（自己 `new`）；
- **"其实生效"2 种**：包级（非 `public`）方法、注解写在 Controller 上。

**⚠️ 本项目没条件测的（3 种，不要当成"已验证"）**：
① **数据库引擎不支持事务**（MySQL MyISAM）—— 今天用 H2，测不了（Day35 换 MySQL 后可以试）；
② **多线程里调用**（事务信息在 `ThreadLocal`，子线程拿不到）—— 今天没引入线程变量；
③ **`private` 方法** —— CGLIB 是子类、无法覆写 `private`，而 `private` 又**只能被同类调用**，
   必然同时踩"自调用"的坑（两个原因分不开，做不成干净的单变量实验）。

> ⭐ 特别说明 **"方法不是 `public` 就失效"**：这条**已经被本机实测推翻**（第 5.3 节，包级方法事务正常开、正常回滚），
> 所以它**不属于"没实测"**，而是**"实测结论与网上博客相反"** —— 批改时别把它算成没验证的。

### 15.2 🎤 面试三句话（背这三句就够）

1. **「`@Transactional` 本身不干活，它只是给代理看的一张纸条；真正开事务/回滚的是
   `TransactionInterceptor` + `PlatformTransactionManager`（本项目是 `JdbcTransactionManager`）。
   所以"注解失效"的本质永远是——你调的不是代理。」**

2. **「默认只对 `RuntimeException` 和 `Error` 回滚，受检异常会照常提交；
   所以业务方法我一般都写 `@Transactional(rollbackFor = Exception.class)`。」**

3. **「想确认事务到底有没有生效，不能看响应码 —— 要看数据库里那几行还在不在，
   以及日志里有没有 `Creating new transaction` / `Initiating transaction rollback`。」**
