## 第 2 步（5 分）想清楚：到底谁在回滚？什么是代理？

### 2.1 三道判断题

1. Day31 你看到"接口返回 500 + 统一 JSON"，当时很自然地想：
   **"异常被 `@RestControllerAdvice` 接住了，所以数据回滚了。"**

  不是@RestControllerAdvice` 接住了了错误，是事务拦截器回滚了数据然后service把错误往外抛，advice只是打包错误

2. 今天的 `OrderService.place(...)` **没有**任何注解。
   那你打 `/order/place?fail=runtime` 时，`orders` 为什么会变成 1？
   这行订单是"谁"替它提交的？（提示：H2 连接池里的连接默认 `autoCommit` 是什么？）
   是 JDBC 自动提交。因为autoCommit是true，所以每个SQL语句都会被提交提交掉。

3. `placeSwallow` 明明**有** `@Transactional`，事务也开了（日志有 `Creating new transaction`），
   为什么最后数据还是脏的？（提示：看它 catch 里干了什么）

### 2.2 一图流：把这张图在纸上默画一遍

```
浏览器 → Filter → Interceptor → DispatcherServlet
           → 【代理】→ ★ 事务拦截器（开事务）
                          → 真的 Service 方法（业务 + SQL）
                       ← 正常? commit : rollback
           → @RestControllerAdvice（异常 → 统一 JSON）
           → Filter 返回
```

⭐ 画完后自己回答：**"事务拦截器"和"MVC 拦截器"是一个东西吗？谁在里面？**

## 🎤 做完之后你应该能回答

1. **`@Transactional` 是怎么生效的？**
   → Spring 给 Bean 生成了一个**代理**；调方法时先进 `TransactionInterceptor`，
   它读方法上的注解（元数据），再交给 `PlatformTransactionManager`（本项目是 `JdbcTransactionManager`）
   去 `setAutoCommit(false)` / `commit` / `rollback`。**注解只是纸条，干活的是后面两位。**

2. **为什么"自己调自己"事务会失效？怎么修？**
   → `this` 指向**原始对象**，不是代理，纸条没人读 → 没事务。
   修法：给**对外入口**方法自己加注解（最常用），或把事务方法拆到**另一个 Bean** 里通过注入调用。

3. **为什么受检异常不回滚？**
   → Spring 默认只对 `RuntimeException` 和 `Error` 回滚（`rollbackOn` 就一行判断）。
   要覆盖就写 `rollbackFor = Exception.class`。

4. **`REQUIRED` 和 `REQUIRES_NEW` 的区别？**
   → `REQUIRED`（默认）加入外层事务，**同生共死**；`REQUIRES_NEW` 挂起外层、自己开一个，
   **外层回滚跟我无关**。用途：审计日志 / 操作流水用 `REQUIRES_NEW`（失败也要留痕），
   业务改动用 `REQUIRED`。

5. **`readOnly = true` 能防止写库吗？**
   → 实测（H2 + JdbcTemplate）**不能**。它只是提示 + 语义。真正的防线是数据库账号权限。

6. **怎么判断"事务到底有没有生效"？**
   → 三步：复位 → 打接口 → **查库看行数**；再配合日志里的
   `Creating new transaction` / `Initiating transaction rollback`。**响应码完全不可靠。**
