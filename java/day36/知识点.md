## 1. 索引是什么

没有索引，`WHERE phone='13800000001'` 只能**从第一页翻到最后一页**（全表扫描，200 万行 = 把整张表读一遍）。
有索引，是先去一张**排好序的小表**（B+ 树）里查到"这行在磁盘第几页"，再直接跳过去。

**代价（面试必问"索引的缺点"）**：

| 代价 | 说明 |
|---|---|
| 占空间 | 一个索引就是一棵额外的树，几十万行能有几十 MB |
| 写变慢 | 每次 `INSERT/UPDATE/DELETE` 都要**同时维护每棵索引树**（还要维护顺序） |
| 选错更糟 | 优化器可能不用它，或者用错它（今天第 6 步就会遇到） |

> 类比：书末尾的索引页。查"索引"这个词，翻索引页 3 秒；没有索引页，只能一页页翻。

## 2. 为什么是 B+ 树

**先记住一个数**：InnoDB 一页 = **16 KB**，也是磁盘 IO 的最小单位。B+ 树的一个节点 = 一页。

**树能有多矮**（这才是"快"的真正原因）：

| 层数 | 能存多少行 | 说明 |
|---|---|---|
| 2 层 | 约 1000 行 | 根页 + 叶子页 |
| 3 层 | 约 **2000 万行** | 根页 + 中间层 + 叶子层 |
| 4 层 | 约 200 亿行 | 基本用不到 |

→ **2000 万行的表，查一行只要 3 次 IO**（根页常驻内存，实际常常 1~2 次）。这就是索引快的本质：**把"翻 N 行"变成"跳 log N 次"**。

**为什么不用别的结构**：

| 结构 | 问题 |
|---|---|
| 二叉搜索树 / 红黑树 | 一个节点只存 1 个值 → 2000 万行要 **24 层**，24 次随机 IO，慢死 |
| 哈希表 | 只能**等值**查，`>`、`BETWEEN`、`ORDER BY` 全部失效（Memory 引擎/自适应哈希才用） |
| B 树 | 非叶子节点也存整行数据 → 一页存的指针变少 → 树更高；范围查询还要中序回溯 |
| **B+ 树** | 非叶子只存"键 + 指针"，一页能存 ~1100 个指针；**所有数据在叶子**，叶子之间还有**双向链表** → 范围查询顺着链表扫即可 |

⭐ 两个必须能说出口的点：
1. **矮**（3 层覆盖 2000 万行，IO 次数少）；
2. **叶子有序且相连**（`BETWEEN`、`ORDER BY`、`LIMIT` 都能直接用上顺序，不用额外排序）。

## 3. 两种索引：聚簇索引 vs 二级索引

InnoDB **一定**有一棵"聚簇索引"：**就是主键那棵树**，叶子节点直接放**整行数据**。

| | 聚簇索引（主键） | 二级索引（普通/唯一索引） |
|---|---|---|
| 叶子存什么 | **整行数据** | **索引列 + 主键 id** |
| 一张表有几个 | 只能 1 个 | 可以有多个 |
| 查 `WHERE id=1` | 一次树查找，直接拿到整行 | —— |
| 查 `WHERE phone='...'` | —— | 先查到 id，**再拿 id 回主键树取整行** = **回表** |
| 范围查询 | 聚簇索引叶子连续 → 顺序读 | 叶子按 phone 排，但整行在别处 → **每行都要回表** |

**回表有多贵**（今天第 3 步你自己量）—— 同样 2 万行、同样的 `SUM(age)`：

| 走哪棵树 | 真机耗时 | 为什么 |
|---|---|---|
| 主键 `id BETWEEN 1 AND 20000` | **3.66 ms** | 叶子就是整行，顺序读完 |
| 二级索引 `phone BETWEEN ...` | **约 24 ms** | 2 万次"按 id 回主键树"，**随机 IO** |

⭐ 两个能背下来的结论：
- 二级索引的叶子**只有 id**，所以 `SELECT *` 走二级索引一定要回表；
- **回表是随机的**，2 万次随机 IO ≈ 6~7 倍时间 —— 这就是"覆盖索引"为什么要存在（Day37 细讲：查询的列全在索引里，就不回表）。

## 4. 索引类型 + 看懂 `SHOW INDEX`

| 类型 | 写法 | 特点 |
|---|---|---|
| 主键索引 | `PRIMARY KEY (id)` | 聚簇索引，唯一 + 非空 |
| 唯一索引 | `UNIQUE KEY uk_phone (phone)` | 值不能重复，**可以有 NULL**（多个 NULL 也算不重复）|
| 普通索引 | `KEY idx_phone (phone)` | 只加速查询，不约束 |
| 联合索引 | `KEY idx_abc (a, b, c)` | **一个索引含多列**，列的顺序有意义（§5）|
| 前缀索引 | `KEY idx_name (name(10))` | 只索引前 10 个字符，省空间（长字符串/URL 用）|

```sql
SHOW INDEX FROM member;            -- 看表上有哪些索引
SHOW CREATE TABLE member;          -- 看完整建表语句（含索引）
ALTER TABLE member ADD INDEX idx_phone (phone);     -- 建
ALTER TABLE member DROP INDEX idx_phone;            -- 删
```

`SHOW INDEX` 里今天只用看懂 4 列：

| 列 | 含义 |
|---|---|
| `Key_name` | 索引名（`PRIMARY` = 主键）|
| `Seq_in_index` | 这列在联合索引里排第几（1 就是最左）|
| `Cardinality` | **区分度估计**：这一列大概有多少个不同值。越高越值得建索引（20 万手机号 ≈ 20 万；城市只有 10）|
| `Non_unique` | 0 = 唯一索引，1 = 普通索引 |

**`key_len` 怎么算**（EXPLAIN 里那一列，今天靠它数"用了几列"）：

| 列类型 | key_len |
|---|---|
| `VARCHAR(20)` + utf8mb4 + `NOT NULL` | `20 × 4 + 2` = **82** |
| `INT` | **4** |
| `TINYINT` | **1** |
| `BIGINT` | **8** |

→ 联合索引 `(city, age, status)`：只用 city = 82；用了 city+age = 86；三列全用 = **87**。
⭐ **`key_len` 是"到底用了几列"的唯一硬证据**，比 `key` 有没有值更可靠。

## 5. 最左前缀原则

联合索引 `(city, age, status)` 在树里是按 **city → age → status** 的顺序排序的（先按城市，同城按年龄，同城同龄再按状态）。

**所以**：能用的只有"**从最左那一列开始、连续的一段**"。

| WHERE 写法（都配 `SELECT *`）| 走索引吗 | 用到几列 | key_len | 为什么 |
|---|---|---|---|---|
| `city='郑州'` | ✅ | city | 82 | 最左列，能用 |
| `city='郑州' AND age=25` | ✅ | city+age | 86 | 连续两列 |
| `city='郑州' AND status=1` | ✅ 但**只用到 city** | city | 82 | **跳过 age** → status 用不上 |
| `age=25` | ❌ | - | - | 没有最左列 city |
| `status=1 AND city='郑州'` | ✅ | city | 82 | **WHERE 里的顺序无关**，看的是索引定义顺序 |
| `age=25 AND status=1` | ❌ | - | - | 同上，缺 city |
| `city='郑州' AND age>30 AND status=1` | ✅ 但**status 用不上** | city+age | 86 | **范围查询之后的列失效** |

三条口诀（背下来）：
1. **从最左开始，不能跳**；
2. **WHERE 里写的先后无所谓**，看索引怎么建的；
3. **一旦某列用了范围（`>` `<` `BETWEEN` `LIKE 'x%'`），它右边的列全部作废**。

⚠️ **例外的例外（真机实测，别当成定律）**：MySQL 8.0.13 起有 **skip scan** —— 如果索引"覆盖"了查询要的列，`WHERE age=25` 也可能出现 `type=range` + `Using index for skip scan`。
但它是在索引里**逐个 city 跳跃扫描**，代价大、只对覆盖查询有效；**`SELECT *` 这类要回表的查询，优化器基本不用它**。所以：**别指望它，按最左前缀写索引。**

## 6. 索引失效的 7 种写法（今天第 5 步逐个验）

| # | 写法 | 走索引 | 原因 | 怎么改 |
|---|---|---|---|---|
| 1 | `WHERE LEFT(phone,3)='138'`、`phone+0=...` | ❌ | 列上**套了函数/运算**，树是按列值排的，算完就没法比 | 把函数挪到右边；或建函数索引/冗余列 |
| 2 | `WHERE phone=13800000001`（列是 varchar，传了数字）| ❌ | **隐式类型转换** = 在列上套了函数（字符串转数字）| 参数类型和列一致，加引号 |
| 3 | `WHERE phone LIKE '%1234'` | ❌ | 前面带 `%` 无法定位起点 | 改成 `'1234%'`（能走索引）；非要中间匹配就上全文索引/ES |
| 4 | `WHERE phone='...' OR name='用户7'`（name 无索引）| ❌ | OR 要求**两边都能走索引**，一边不行就整体全表扫 | 给 name 也建索引，或拆成两条 SQL `UNION` |
| 5 | `WHERE city='郑州' AND age>30 AND status=1` | ⚠️ 部分 | 范围之后的 `status` 用不上（§5）| 把等值列放前面：`(city, status, age)` |
| 6 | `WHERE status=1`（只有 0/1 的低区分度列）| ❌ 常不走 | 区分度太低（一半的行都命中），回表比全表扫还贵 | 别单建；要建就做成联合索引的一部分 |
| 7 | `WHERE phone != '13800000001'` / `NOT IN (...)` | ⚠️ 看情况 | 命中行数太多时优化器宁可全表扫 | 别把它当"一定失效"，**看 EXPLAIN 的 rows** |

⭐ 还有一个**不是失效但常被误会**的：`WHERE id IN (3,1,2)` 走主键索引，返回顺序也是按 id（`1,2,3`），**不是**你写的顺序。

## 7. 什么时候**不该**建索引

| 情况 | 原因 |
|---|---|
| 表很小（几千行以内）| 全表扫一页就完事，索引反而多一次查找 |
| 区分度极低（性别、状态、`is_deleted`）| 命中一半行，回表比全表扫更贵 |
| 写多读少的表 / 频繁更新的列 | 每次写都要改树，索引越多写越慢 |
| 已经能被别的索引"最左前缀"覆盖 | 例如已有 `(a,b,c)`，就不必再单独建 `(a)` |
| 查询里根本没用到的列 | 白占空间 + 拖慢写入 |

→ 建索引的正确顺序：**先看慢查询 → 再算区分度 → 再按"等值列在前、范围列在后"排 → 最后用 EXPLAIN 验证**（EXPLAIN 是明天的主菜）。
