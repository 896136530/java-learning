# Day 36 索引（一）速览：10 分钟复习

> 你 10-28 写过 Day36 了，这份只是**复习卡**：8 件事，每件一句话 + 一个数字。想细看再翻 `知识点.md`。

---

## 1. 索引是什么

给**某一列**建的一份"排好序的小目录"。查数据先翻目录，不用一页页翻表。

**代价**（面试必问）：

| 代价 | 说明 |
|---|---|
| 占空间 | 一个索引就是一棵额外的树 |
| 写变慢 | 每次增删改都要同时维护所有索引 |
| 可能选错 | 优化器可能不用它，或者用错它 |

---

## 2. 为什么快：B+ 树又矮又有序

- InnoDB 一页 **16 KB**，B+ 树一个节点 = 一页；
- **3 层能装约 2000 万行** → 查一行只要 3 次 IO（根页还常驻内存）；
- 叶子节点**首尾相连** → 范围查询、`ORDER BY`、`LIMIT` 顺着链表走就行。

一句话：把"翻 N 行"变成"跳 log N 次"。

---

## 3. 两种索引：主键索引 vs 二级索引（回表）

| | 主键索引（聚簇索引） | 二级索引（普通/唯一索引） |
|---|---|---|
| 叶子存什么 | **整行数据** | **索引列 + 主键 id** |
| 一张表几个 | 1 个 | 可以很多个 |
| 查 `id=1` | 一次找到整行 | —— |
| 查 `phone=...` | —— | 先找到 id，**再拿 id 回主键树取整行** = **回表** |

**回表有多贵**（同一批 2 万行、同样 `SUM(age)`）：

| 走哪棵树 | 耗时 |
|---|---|
| 主键（叶子就是整行，顺序读）| 3.7 ms（你机器上量到 13.5 ms）|
| 二级索引（2 万次随机回表）| 23.9 ms（你机器上量到 69.3 ms）|

→ 差 5~6 倍。这就是 Day37 要讲的"覆盖索引"的动机。

## 4. 五种索引

| 类型 | 写法 | 特点 |
|---|---|---|
| 主键 | `PRIMARY KEY (id)` | 聚簇索引，唯一 + 非空 |
| 唯一 | `UNIQUE KEY uk_phone (phone)` | 不能重复，可以多个 NULL |
| 普通 | `KEY idx_phone (phone)` | 只加速查询，不约束 |
| 联合 | `KEY idx_abc (a, b, c)` | 多列一个索引，**列顺序有意义** |
| 前缀 | `KEY idx_name (name(10))` | 只索引前 10 个字符，省空间 |

## 5. 看懂 `SHOW INDEX`（只看 4 列）

| 列 | 人话 |
|---|---|
| `Key_name` | 索引名（`PRIMARY` = 主键）|
| `Seq_in_index` | 这列在联合索引里排第几（1 = 最左）|
| `Cardinality` | 估计有多少个不同值（越高越值得建）|
| `Non_unique` | 0 = 唯一索引，1 = 普通索引 |

**`key_len` 怎么算**（EXPLAIN 里"用了几列"的硬证据）：

| 列类型 | key_len |
|---|---|
| `VARCHAR(20)` + utf8mb4 + NOT NULL | 20×4+2 = **82** |
| `INT` | **4** |
| `TINYINT` | **1** |
| `BIGINT` | **8** |

→ `(city, age, status)`：只用 city = 82，city+age = 86，三列全用 = **87**。

---

## 6. 最左前缀（三条）

1. **从最左开始，不能跳**：`(city, age, status)` 只写 `age=25` → 用不上；
2. **WHERE 里谁先写无所谓**：看索引怎么建的；
3. **范围之后的列失效**：`city='郑州' AND age>30 AND status=1` → 只用到 city+age。

> 例外：8.0.13+ 有 **skip scan**，覆盖查询时 `WHERE age=25` 也可能走索引，但别指望它。

---

## 7. 索引失效的 7 种写法

| # | 写法 | 为什么失效 |
|---|---|---|
| 1 | `LEFT(phone,3)='138'`、`phone+0=...` | 列上套了函数，索引是按原值排的 |
| 2 | `phone=13800000001`（列是 varchar）| 隐式类型转换 = 在列上套函数 |
| 3 | `LIKE '%1234'` | 前面带 `%`，不知道从哪开始 |
| 4 | `a='x' OR b='y'`（b 没索引）| OR 要求两边都能走索引 |
| 5 | `city='郑州' AND age>30 AND status=1` | 范围之后的列用不上（部分失效）|
| 6 | `status=1`（只有 0/1）| 区分度太低，回表比全表扫还贵 |
| 7 | `!=`、`NOT IN` | 命中行太多时优化器宁可全表扫 |

---

## 8. 什么时候**不该**建索引

| 情况 | 原因 |
|---|---|
| 表很小（几千行以内）| 全表扫一页就完，索引反而多一次查找 |
| 区分度极低（性别、状态、`is_deleted`）| 命中一半行，回表更贵 |
| 写多读少的表 | 每次写都要改树 |
| 已被别的索引最左前缀覆盖 | 例如有 `(a,b,c)` 就不用再建 `(a)` |
| 查询里根本用不到 | 白占空间 + 拖慢写入 |

---

## 9. 建索引的正确顺序

**慢查询 → 算区分度 → 等值列在前、范围列在后 → 用 EXPLAIN 验证**。
