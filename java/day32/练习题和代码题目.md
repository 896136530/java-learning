### ✍️ 第 2 步作答（本题由 AI 代写，务必自己复述一遍）

**先把"观察记录"记下来（第 1 步的三个观察点，实测值）**

| 观察点 | 实测值 | 哪里不对劲 |
|---|---|---|
| ① `POST /sku` 正常体（不传 id） | 400，fieldErrors `{id:"更新时必须指定 id"}` | 明明是**新增**，却按**更新**的口径要求我传 id |
| ① `POST /sku` 带 `id:99` | 400，fieldErrors `{id:"新增时不能自己指定 id（由服务器生成）"}` | 同一件事反过来又不行了 —— id 传也错、不传也错 |
| ② `PUT /sku {"id":1,"price":99}` | 400，fieldErrors `{code, title, stock, id:"新增时不能自己指定 id"}` | 只想改个价格，却被要求把书名/库存/编码全填上；`id` 还报"**新增**时不能指定" |
| ③ `GET /sku/search?limit=0` | **500**「服务器开小差了，请稍后重试」 | 是我参数传错，却报服务器炸了。日志真凶：`jakarta.validation.ConstraintViolationException: search.limit: limit 至少是 1` |

**三个问题**

1. **这两条注解属于同一个组吗？**
   属于。`@Null` 和 `@NotNull` 都没写 `groups`，而"没写 `groups` 的注解一律属于 `Default` 组" ——
   所以它俩现在**躺在同一个组里**，谁也别想单独出场。

2. **`@Null` 和 `@NotNull` 能同时成立吗？**
   不能。`@Null` 要求值是 null，`@NotNull` 要求值不是 null，这是**逻辑上的互补命题** ——
   对任何一个值，两条里必然有且只有一条成立。所以只要它们同时生效，**结果一定是 400**，
   与前端传什么完全无关。这就是"新增怎么都成功不了"的原因。

3. **那"新增管 `@Null`、更新管 `@NotNull`"用现在这套写法能表达出来吗？**
   表达不出来。现在校验时手上只有"一组（Default）"这个概念，而这一组里两条规则全都在，
   框架没有任何信息能判断"这次是新增还是更新"。换句话说：
   **注解本身没错、数量也够，缺的是"让每条规则只在合适场景生效"的机制** —— 这个机制就是"分组"。
   有了 `OnCreate` / `OnUpdate`，`@Null` 挂 `OnCreate`、`@NotNull` 挂 `OnUpdate`，
   校验时由 Controller 说"这次按哪一组来"，两条相反规则就再也不打架了。

**再想一个类似的问题：为什么 `PUT` 会被要求"书名不能为空"？**

`@NotBlank` 对"不传"和"传了空串"是**一样**处理的 —— 它把 `null`、`""`、`"   "` 统统判为不合格。
这是 `@NotBlank` 的语义（"这个名字下必须有个非空白的内容"），没有问题；
问题在于它现在挂在 `Default` 组里，**无条件生效**。
而"部分更新"的语义恰恰是"没传的字段表示不改" —— 于是"不传 title"被它当成了"title 为空"而报错。
要表达"可以不传、传了就不能是空串"，得换一条**对 null 放行**的规则去管更新：
`@Size(min = 1)`（它遇到 null 直接放过），并且把它单独挂在 `OnUpdate` 组里。

> **一句话总结（本步验收的那句话）**：
> **之所以需要分组校验，是因为同一套注解要同时服务"新增"和"更新"两个要求相反的场景，
> 而注解自己不区分场景 —— 只能靠"分组"让每条规则在合适的场景才生效。**

## 第 3 步（25 分）⭐ TODO① 给 `SkuForm` 的注解加 `groups`

### 要做的事

给**每一个**校验注解补上 `groups = ...`，规则照下表：

| 字段 | 注解 | 挂到哪个组 | 为什么 |
|---|---|---|---|
| `id` | `@Null` | `OnCreate.class` | 新增时不许自己传 id |
| `id` | `@NotNull` | `OnUpdate.class` | 更新时必须传 id |
| `title` | `@NotBlank` | `OnCreate.class` | 新增必填 |
| `title` | `@Size(min=1)` | `OnUpdate.class` | 更新可以不传，传了不能是空串 |
| `price` | `@NotNull` | `OnCreate.class` | 新增必填 |
| `price` | `@Min(0)` | `{OnCreate.class, OnUpdate.class}` | 两边都要管 |
| `stock` | `@NotNull` | `OnCreate.class` | 新增必填 |
| `stock` | `@Min(0)` | `{OnCreate.class, OnUpdate.class}` | 两边都要管 |

| `code` | `@SkuCode` | `OnCreate.class` | 只在新增校验格式（编码不许改） |

// 挂一个组
@NotNull(message = "更新时必须指定 id", groups = OnUpdate.class)

@Min(value = 0, message = "价格不能小于 0", groups = {OnCreate.class, OnUpdate.class})

如果你**只改了 Controller、忘了第 3 步的 `groups`**，会发生这些事（**真机实测**）：

| 请求 | 本该 | 实际 | 危险程度 |
|---|---|---|---|

## 第 5 步（15 分）⭐ TODO③ 写 `SkuCodeValidator.isValid`

**文件**：`java/day32/src/main/java/com/xiaoming/day32/sku/valid/SkuCodeValidator.java`

### 要做的事

规则：**商品编码必须是 `SKU-` 后面跟正好 4 位数字**。

现在 `isValid` 直接 `return true`（占位），所以 `code:"abc"` 也能过。把它改成真的校验。

**两条要求（第二条是铁律）：**

1. 用正则判断格式对不对
2. ⭐ **空值必须放行**（`null` / 空串 / 只有空格 → `return true`）

### 提示

- 正则：`"SKU-\\d{4}"`（Java 字符串里 `\` 要写两次 → `\\d`）
- 判断用 `value.matches(...)` —— 它是**整串匹配**，自带 `^...$`
- `@NotBlank` 已经管"必填"了，所以"空值"**不归你管** —— 不然同一个输入框旁边会冒两条红字

写完之后是这个形状：

```java
@Override
public boolean isValid(String value, ConstraintValidatorContext context) {
    if (value == null || value.isBlank()) {
        return true;
    }
    return value.matches("SKU-\\d{4}");
}
```

### 验证

| # | 请求体的 `code` | 应该 |
|---|---|---|
| 1 | `"abc"` | **400**，fieldErrors `{"code":"商品编码格式不对（正确格式：SKU-0001）"}` |
| 2 | `"SKU-123"`（3位） | 400，同上 |
| 3 | `"SKU-12345"`（5位） | 400，同上 |
| 4 | `"xSKU-1234"`（前面有字） | 400，同上 |
| 5 | `"SKU-0015"`（正确格式） | **200** |
| 6 | `""`（空串） | 400，但消息是 **`商品编码不能为空`**（来自 `@NotBlank`，**不是**你的格式消息） |

> ⭐ 第 6 条是**验证铁律**的地方：如果空串报的是"商品编码格式不对"，说明你**没放行空值**。
>
> 📌 顺便注意 4 种错误码的**数字**：`SKU-123`、`SKU-12345`、`xSKU-1234` 都该被拒 ——
> 如果你用了 `find()` 而不是 `matches()`，`xSKU-1234` 会被**放过**（危险！）。

### 为什么

第 1 步你已经看到了：`GET /sku/search?limit=0` 返回 **500**。
日志里的真凶是 `jakarta.validation.ConstraintViolationException`，**没人接它 → 掉进兜底 → 500**。

### 要做的事

在**兜底 handler 之前**加一个新的 handler：

```java
@ExceptionHandler(ConstraintViolationException.class)
public ResponseEntity<Result<Void>> handleConstraintViolation(ConstraintViolationException e) {
    Map<String, String> errors = Result.fieldErrors();
    for (ConstraintViolation<?> v : e.getConstraintViolations()) {
        String path = v.getPropertyPath().toString();       // 形如 "search.limit"
        int dot = path.lastIndexOf('.');
        String field = (dot >= 0) ? path.substring(dot + 1) : path;   // ⭐ 截成 "limit"
        errors.putIfAbsent(field, v.getMessage());
    }
    log.warn("方法参数校验失败：{}", errors);
    return ResponseEntity.status(400)
            .body(Result.failFields(ResultCode.PARAM_ERROR, "参数校验失败，请看 fieldErrors", errors));
}
```

别忘 import：

```java
import jakarta.validation.ConstraintViolation;
import jakarta.validation.ConstraintViolationException;
```

**四个要点：**

| # | 要点 | 为什么 |
|---|---|---|
| 1 | 状态码 **400** | 这是"请求不合法"，不是"服务器出错" |
| 2 | 用 `Result.failFields(...)` 装 fieldErrors | 和请求体校验的格式保持一致，前端好处理 |
| 3 | ⭐ 字段名要**截断** | `getPropertyPath()` 给的是 `search.limit`（带方法名），直接给前端对应不上输入框 |
| 4 | 日志用 **warn** | 预期内的错，不打堆栈（和 ①② 保持一致） |

### ✍️ 第 8 步作答

#### ① 为什么 `@SkuCode` 遇到空值必须放行？（本题由 AI 代写，务必自己复述一遍）

`SkuForm.code` 上**同时**挂着两个注解，但它们的**职责完全不是一回事**：
`@NotBlank` 管"有没有填"，`@SkuCode` 管"格式对不对"。

如果 `@SkuCode` 也把 null / 空串判成不合格，那么前端传 `code:""` 时，
两条规则会**同时**判断为失败，本该给用户两条消息：

```
{"code": "商品编码不能为空"}
{"code": "商品编码格式不对（正确格式：SKU-0001）"}
```

而我们 Day31 那个 handler 是往 `fieldErrors` 这个 **Map** 里 `putIfAbsent` 的
（key 是字段名，同一个 key 只留得下一条）→ 两条里**随机留下一条**给前端。
要是哪天改成把多条原样透传给前端，同一个输入框旁边就会挂**两条红字**。
哪种都不好：用户**根本没填**，却可能被告知"格式不对（正确格式：SKU-0001）" —— 这是答非所问，
他分不清自己是漏填了还是填错了。

所以铁律是：**每个注解只管一件事**。"必填"是 `@NotBlank` 的活，
`@SkuCode` 只在"用户确实填了东西"的时候才去挑格式毛病。
这就是 `isValid` 的第一句永远是 `if (value == null || value.isBlank()) return true;` 的原因。

#### ② 为什么校验器是单例，就决定了它里面只能放配置？（本题由 AI 代写，务必自己复述一遍）

因为 Validator 全程**只 new 一个** `SkuCodeValidator` / `MaxStockValidator` 实例，所有请求共用它。
同理，注解参数（`max`）也不会变，所以"读一次存成字段"很划算；
但如果字段里存的是**每个请求都不一样的数据**，这个共享对象就变成了并发写的公共黑板。

假设 `MaxStockValidator` 里存了一个 `currentTitle`：请求 A 进来先写自己的书名，
还没用完，请求 B 进来把 `currentTitle` 覆盖成 B 的书名，请求 A 再读就拿到 B 的数据。
结果就是 A 的校验按 B 的数据判 —— 这就是 Day18/19 讲的**多线程共享可变状态**：
错得偶发、复现困难、日志里啥也看不出来。

所以结论是：字段只放**只读的配置**（在 `initialize` 里赋一次值，之后再不改），
"每次都可能变的值"只能作为 `isValid` 的**局部变量/形参**用完就丢。

#### ③ 为什么"商品编码重复"写不成注解？（本题由 AI 代写，务必自己复述一遍）

因为 `ConstraintValidator` 是一个**无状态**的判断器，它手上只有两样东西：
当前这个字段的**值**、注解上写的**参数**（外加一个 `context`）。
它没有任何通道去访问 Service、`db` 这个 Map、或者数据库 —— 换句话说，
它**看不到"别的对象"**，也就无从判断"这个编码是不是已经被别人用过了"。

而"编码重复"的本质是一个**跨对象、要查数据**的判断：必须遍历 `db`（将来是 `SELECT ... WHERE code = ?`）
才知道结果。所以它只能写在 Service 里那个手写的 `if`：

```java
for (Sku s : db.values()) {
    if (form.getCode() != null && form.getCode().equals(s.getCode())) {
        throw new BizRuleException("商品编码已存在：" + form.getCode());   // 409
    }
}
```

顺带一个容易忽略的点：这里的状态码是 **409** 而不是 400。
400 的语义是"你这次请求的参数本身就不合法（改参数就能过）"，
而编码重复时参数格式完全没问题，是"和现有数据冲突了" —— 换个编码就能过，所以是 409。

**一句话划界**：**只看当前字段 → 注解（400）；要查别的数据 → Service 手写 `if`（409）。**
