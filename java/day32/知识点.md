## 2. 复习：Day31 的 `@Valid` 是怎么生效的

先把"已经会的"搞清楚，今天的难点才站得住：

```
前端 POST /sku  {"title":"", "price":-1}
        ↓
SpringMVC 拿 Jackson 把 JSON 转成 SkuForm 对象
        ↓
发现参数上有 @Valid → 拿 SkuForm 上的注解挨个验一遍
        ↓
不合格 → 抛 MethodArgumentNotValidException
        ↓
Day31 的 GlobalExceptionHandler ② 接住 → 400 + fieldErrors
```

三个关键认知：

| 认知 | 说明 |
|---|---|
| 校验发生在**"JSON 转对象"的时候** | 还没进你的 Controller 方法，Java 代码一行都没执行 |
| 谁去验 | **Hibernate Validator**（`spring-boot-starter-validation` 带进来的） |
| 失败时**抛异常**，不是返回错误码 | 所以能被全局处理器统一接住（Day31 的设计正好接上了） |

> 📌 这套机制来自 **Jakarta Bean Validation**（标准），Spring 只是"接了个管子"。

## 3. ⭐⭐⭐ 为什么需要"分组校验"

### 一个真实的矛盾

同一个 `SkuForm`，**新增**和**更新**时要求正好相反：

| 字段 | POST /sku（新增） | PUT /sku（更新） |
|---|---|---|
| `id` | 必须**不传**（服务器生成；传了就是越权） | 必须**传**（否则不知道改谁） |
| `title` | 必填 | 可以不传（= 这一项不改） |
| `code` | 必须给，且格式要对 | **不给**（编码是业务主键，不允许改） |
| `price` | 必填 | 可以不传；传了就不能是负数 |
| `stock` | 必填 | 可以不传；传了就不能是负数/超上限 |

### 如果只有一套注解，会发生什么？（真机实测）

Day32 交付给你的时候，`SkuForm` 上的注解**故意没写 `groups`**，注解长这样：

```java
@Null(message = "新增时不能自己指定 id（由服务器生成）")
@NotNull(message = "更新时必须指定 id")
private Long id;
```

实测结果（都是真机跑出来的，见 `练习题和代码题目.md` 文末的验收记录）：

| 请求 | 结果 | 问题在哪 |
|---|---|---|
| `POST /sku` 正常请求体 | **400** `{"id":"更新时必须指定 id"}` | 明明是**新增**，却报"更新时必须指定 id" |
| `POST /sku {}` | 400 + **5 条** fieldErrors（含 `id:"更新时必须指定 id"`） | 又冒出一条跟新增无关的 id 错误 |
| `PUT /sku {"id":1,"price":99}` | **400** fieldErrors 里 `code`/`title`/`stock` 全说"不能为空" | 明明是**部分更新**，却被要求把每项都填全 |

⭐ **结论：这两条注解在同一个组里"打架"—— `id` 无论传不传都错；`PUT` 永远过不了。**
原因很简单：`@Null` 和 `@NotNull` 是**相反**的规则，它们不能同时生效，必须**按场景分开**。

### 三条出路

| 方案 | 评价 |
|---|---|
| 拆两个 DTO 类（`AddForm` / `UpdateForm`） | 能用，但字段全重复；以后加一个字段要改两个类（**容易漏**） |
| 放弃注解，在 Controller 里手写 `if` | 又退回 Day30 的脏代码；而且 Service 被绕过时没防线 |
| ⭐ **分组校验**：一套注解，按场景生效 | 今天的答案 |

## 4. ⭐⭐⭐ 分组怎么用（3 步）

### 第 1 步：定义两个**空接口**当"组名"

```java
public interface OnCreate {   // 一个字都没有
}
public interface OnUpdate {
}
```

> 你可能觉得"空接口能干嘛"？—— 注解的 `groups` 要的是 `Class<?>[]`，
> 也就是**类的 Class 对象**。所以得有个"东西"能被写成 `OnCreate.class`。
> 📌 这个套路叫**标记接口**（Marker Interface），Java 自带 `Serializable`、`Cloneable` 都是它。
> ⭐ 为什么不用字符串？—— 字符串写错编译器不报错，`OnCreate.class` 写错**编译期就红**。

### 第 2 步：注解上写 `groups = ...`

```java
@Null(message = "新增时不能自己指定 id（由服务器生成）", groups = OnCreate.class)
@NotNull(message = "更新时必须指定 id", groups = OnUpdate.class)
private Long id;

@NotBlank(message = "书名不能为空", groups = OnCreate.class)
@Size(min = 1, message = "书名不能是空字符串", groups = OnUpdate.class)
private String title;

// ⭐ 一个约束要管两个场景 → 用花括号一次挂两组
@Min(value = 0, message = "价格不能小于 0", groups = {OnCreate.class, OnUpdate.class})
private Integer price;
```

**不写 `groups` 的注解属于"默认组"`Default`**（就是 Day31 那种情况）。

### 第 3 步：Controller 上指定"这次用哪一组"

```java
@PostMapping
public Result<Sku> add(@Validated(OnCreate.class) @RequestBody SkuForm form) { ... }

@PutMapping
public Result<Sku> update(@Validated(OnUpdate.class) @RequestBody SkuForm form) { ... }
```

⭐ 验证"分组真的生效"的最快办法：看 `POST /sku {}` 的 fieldErrors。

| 状态 | `POST /sku {}` 的 fieldErrors |
|---|---|
| 没分组（模板版） | `{stock, code, price, title, id:"更新时必须指定 id"}` —— **5 条，多出个 id** |
| 分好组（OnCreate） | `{code, price, title, stock}` —— **4 条，没有 id** ✅ |

## 5. ⭐⭐ `@Valid` vs `@Validated`

这是分组校验最容易卡住的地方：**`@Valid` 根本没有 `groups` 属性！**

| | `@Valid` | `@Validated` |
|---|---|---|
| 全名 | `jakarta.validation.Valid` | `org.springframework.validation.annotation.Validated` |
| 出身 | **Jakarta 标准**（Bean Validation 规范里定义的） | **Spring 自己加的**（标准没有，Spring 补的） |
| 能指定分组吗 | ❌ **不能**（只有这一个用法，没有 value()） | ✅ 能，`@Validated(OnCreate.class)` |
| 能贴在类上吗 | 基本不行 | ✅ 能（这就是"方法参数校验"的开关，见第 11 节） |
| 用在哪 | 请求体参数、**级联校验的字段**（见第 13 节） | 请求体参数（要指定组时）、**类上** |

**一句话记法：`@Valid` 是标准，`@Validated` 是 Spring 增强版（多了分组和类级开关）。**

> 📌 顺带一个冷知识：`@Valid` 能用在**字段**上做"级联校验"，`@Validated` 不行（它没有 `ElementType.FIELD`）。
> 所以"嵌套对象的校验"只能用 `@Valid`。

## 6. ⭐⭐⭐ "静默失效" —— 今天最大的坑

### 坑是怎么来的

回顾第 4 步的第 2、3 条：**注解上加 groups** 和 **Controller 上指定组**，是**两件必须同时做的事**。
如果只做了 Controller 那一半：

```java
// Controller：指定了只跑 OnCreate 组
public Result<Sku> add(@Validated(OnCreate.class) @RequestBody SkuForm form) { ... }

// SkuForm：注解没写 groups → 它们全都属于"默认组 Default"
@Null(message = "新增时不能自己指定 id（由服务器生成）")     // ← 忘了写 groups
private Long id;
```

### 关键规则

> ⭐⭐ **只要你在 Controller 上显式指定了组，`Default` 组就不参与了。**
> 没写 `groups` 的注解全都属于 `Default` → **它们一条都不会跑**。

### 后果有多严重（真机实测，全部实测过）

| 请求 | 本该 | 实际 | 为什么危险 |
|---|---|---|---|
| `POST /sku` 带 `{"id":99,...}` | 400（不许自己指定 id） | **200！越权通过了** | 前端能自己指定 id，可能覆盖别人的数据 |
| `POST /sku` `code:"abc"` | 400（格式错） | **200** | 脏数据直接入库 |
| `POST /sku {}`（全空） | 400 + 4 条 fieldErrors | 400 + `message:"书名不能为空"`，**fieldErrors=null** | 注解层压根没跑，是 Service 手写校验兜住的；前端拿不到 fieldErrors 就没法在输入框旁标红字 |
| `PUT /sku {"price":99}`（不带 id） | 400（更新必须给 id） | **404「SKU 不存在：id=null」** | 错误信息驴唇不对马嘴，排查半天 |

### 为什么叫"静默"失效

因为它**不报错、不警告、不抛异常** —— 接口返回 200，程序跑得好好的，
你以为校验在保护你，实际上门是敞开的。

> ⭐ **对比一下两种坑的可怕程度**：
> · 报错的坑（比如少 import）→ 编译不过 / 启动失败 → **你立刻会去修**
> · 静默失效的坑 → 一切"正常" → **你根本不知道有问题**
> 📌 这就是为什么真实项目里，**配置类的东西宁可写刻意一点，也不要依赖"默认值"**。

### 怎么防

| 办法 | 说明 |
|---|---|
| **要写就写全** | 决定用分组，就把每个注解的 `groups` 都补上（哪怕只是 `Default.class`） |
| 写完必测"反例" | 改完校验，**每个约束都要构造一个"该被拒绝"的请求**打一遍 |
| 看 fieldErrors 条数 | 分组写对了，`POST {}` 应该正好 4 条（code/price/stock/title），**多一条少一条都不对** |

## 7. `@GroupSequence`（了解即可，今天不考）

第 6 节的坑还有第二种解法：**让 `Default` 也参与进来**。

```java
// 定义一个"组序列"：先跑 Default，再跑 OnCreate
@GroupSequence({Default.class, OnCreate.class})
public interface CreateChecks {
}
```

然后 Controller 写 `@Validated(CreateChecks.class)`。特性：

| 特性 | 说明 |
|---|---|
| **按顺序**跑 | 前一组失败就**短路**，后面的组不再跑（省性能） |
| 能包含 `Default` | 解决"指定了组，Default 就不跑"的问题 |
| 附带好处 | 可以拿它做"轻量校验先跑、耗时的校验后跑"（比如"查库才知道的规则"放最后一组） |

> ⚠️ 今天**没实测**它（TODO 里也没要求）。知道有这么个东西，哪天遇到"组太多、要控顺序"再回来看。

## 8. ⭐⭐⭐ 自定义校验注解：三件套 + 元注解

### 什么时候需要自己写

Bean Validation 自带的注解是**通用**的：`@NotNull` / `@NotBlank` / `@Size` / `@Min` / `@Max` / `@Email` / `@Pattern` / `@Past` ...
业务规则是**专有**的：

| 业务规则 | 自带的能表达吗 |
|---|---|
| 商品编码必须是 `SKU-` + 4 位数字 | `@Pattern` 能凑（真实项目也常这么干） |
| 手机号 1 开头的 11 位 | `@Pattern` 能凑 |
| 密码必须同时含大小写 + 数字 | 单条 `@Pattern` 很绕 |
| **身份证校验位必须算对** / **用户名不能和已有的重复** | ❌ 必须查数据或计算 → 只能自定义 |

> ⭐ 自定义注解真正的价值不是"能不能做到"，而是 **把一条规则变成一个"能复用的词"**：
> 别人看到 `@SkuCode` 就懂，不用去读一长串正则。

### 一个校验注解的完整解剖（以 `@SkuCode` 为例）

```java
@Target({ElementType.FIELD, ElementType.PARAMETER})   // ① 元注解：能贴在哪
@Retention(RetentionPolicy.RUNTIME)                   // ② 元注解：⭐ 必须 RUNTIME
@Documented                                           // ③ 元注解：生成文档时带上
@Constraint(validatedBy = SkuCodeValidator.class)     // ④ 指定"谁来执行校验"
public @interface SkuCode {

    String message() default "商品编码格式不对（正确格式：SKU-0001）";   // 三件套之一

    Class<?>[] groups() default {};                                     // 三件套之二 ⭐

    Class<? extends Payload>[] payload() default {};                    // 三件套之三
}
```

### ⭐ "三件套"少一个都不行 —— 这是最容易忘的地方

| # | 成员 | 作用 | 忘了会怎样 |
|---|---|---|---|
| ① | `message()` | 失败时的提示语，会原样出现在 fieldErrors 里 | 编译/启动报错 |
| ② | `groups()` | **分组**。不声明它，这个注解**永远只在 `Default` 组生效** | ⚠️ **分组校验时被静默跳过**（第 6 节的坑会以另一种形式重演） |
| ③ | `payload()` | 给框架留的扩展位，**几乎永远不用** | 启动直接报错（格式检查要求必须有） |

> 📌 `payload()` 那个"必须写但没用"的设定确实反直觉 —— 它是规范为了**将来扩展**留的，
> 你只要知道"照抄这三行"就行。**所有校验注解都长这个样。**

### 四个元注解（贴在注解上的注解）

| 元注解 | 值 | 为什么 |
|---|---|---|
| `@Target` | `{FIELD, PARAMETER}` | 限制它能贴在哪；贴错地方会编译报错（帮你防错） |
| `@Retention` | ⭐ **`RUNTIME`** | 校验发生在**运行时**（靠反射读注解）。写成 `SOURCE` → 运行时读不到 → **静默失效** |
| `@Documented` | —— | 生成 javadoc 时把注解带上（纯礼节） |
| `@Constraint` | `validatedBy = 校验器.class` | **关键**：把"注解"和"干活的类"绑起来 |

## 9. ⭐⭐⭐ `ConstraintValidator`：两个方法 + 三条铁律

注解只是"规则的名字"，真正干活的是**校验器**：

```java
public class SkuCodeValidator implements ConstraintValidator<SkuCode, String> {
//                                                        ↑注解    ↑被校验的类型

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null || value.isBlank()) {
            return true;                              // ⭐ 铁律①：空值放行
        }
        return value.matches("SKU-\\d{4}");           // 规则本体
    }
}
```

### 两个泛型别搞反

| 位置 | 含义 | 例子 |
|---|---|---|
| 第 1 个 | **给哪个注解打工** | `SkuCode` |
| 第 2 个 | **这个注解贴的字段是什么类型** | `String` |

### 两个方法的分工

| 方法 | 调用时机 | 干什么 |
|---|---|---|
| `initialize(A annotation)` | **启动时只调一次** | 读出注解上写的**参数**（`@SkuCode` 没参数就不用写；`@MaxStock` 有 `max` 就必须写） |
| `isValid(T value, Context ctx)` | **每个被校验的值都调一次** | 真正判断。`true` 通过、`false` 报 `message` |

> ⭐ 为什么要分成两个？因为**注解参数永远不变**，值每次都变。
> 批量导入几万条时，`initialize` 只跑一次能省掉大量反射开销。

### ⭐⭐⭐ 三条铁律

**铁律①：`null` 一定要放行（`return true`）**

为什么？—— **"必填"是 `@NotNull` / `@NotBlank` 的职责，不是你的职责。**
你要是顺手判了 null 并返回 false，就会出现**一个字段报两条错**：

```json
// 如果 @SkuCode 也管 null，SkuForm.code 忘了填时会收到：
{ "code": "商品编码不能为空", "code": "商品编码格式不对" }   // ← 同一个输入框旁边两条红字
```

> ⭐ 口诀：**每个注解只管一件事**（单一职责）。
> 所以 `isValid` 的第一句永远是：`if (value == null || value.isBlank()) return true;`

**铁律②：校验器是单例 —— 字段只能放"配置"，绝不能放"请求数据"**

Spring / Validator 全程只 `new` 一个实例，所有请求共用同一个对象。
所以：

```java
private int max;          // ✅ 可以：注解参数，只读的配置
// private String currentTitle;  // ❌ 绝对不行：多个请求会互相串数据（Day18/19 的并发问题）
```

**铁律③：能用 `matches()` 就别用 `find()`**

`String.matches(regex)` 是**整串匹配**（自动补 `^...$`），`Pattern.find()` 是**部分匹配**。

| 值 | `matches("SKU-\\d{4}")` | `find()` |
|---|---|---|
| `SKU-1234` | ✅ 通过 | ✅ 通过 |
| `xSKU-1234` | ❌ 不通过 | ✅ **也通过**（危险！） |
| `SKU-12345` | ❌ 不通过 | ✅ 也通过 |

## 10. ⭐⭐ 带参数的注解 + `{max}` 插值

### 注解的"参数"就是注解里的一个方法

```java
public @interface MaxStock {
    int max() default 1000;                        // ⭐ 这就是参数（不写就是 1000）
    String message() default "库存不能超过 {max}";   // ⭐ {max} 会被替换成上面的值
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

用法：

```java
@MaxStock(max = 500)                // 本项目 SkuForm 上就是这么写的
private Integer stock;
```

### ⭐ `{max}` 是**框架自动**替换的，不用你写代码

**真机实测**（`POST /sku` 带 `stock:800`）：

```json
{ "stock": "库存不能超过 500" }
```

> 规则：`{` 里写**注解的属性名**，框架会去调那个方法取值。
> 好处：**一句 message 模板适配所有参数值** —— 不用为每个上限写一条消息。

### 参数怎么读出来：`initialize`

```java
private int max;

@Override
public void initialize(MaxStock annotation) {
    this.max = annotation.max();      // ⭐ 形参就是"贴在该字段上的那个注解对象"
}

@Override
public boolean isValid(Integer value, ConstraintValidatorContext context) {
    if (value == null) return true;   // 铁律①
    return value <= max;              // 注意是 <=，写成 < 的话 max 本身就被判错了
}
```

### ⚠️ 真机实测的一个反面教材（就在你的 `MaxStockValidator` 里）

交付给你的校验器里，`initialize` 是这样写的：

```java
this.max = 1000;      // ← 写死了！注解上的 max = 500 完全没用上
```

后果（实测）：

| 请求 | 写死 1000（TODO④ 没写） | 正确读注解（TODO④ 写完） |
|---|---|---|
| `stock: 800` | **200**（800 ≤ 1000，放过了） | **400**「库存不能超过 500」 |
| `stock: 500` | 200 | 200（`<=` 边界，应放过） |

> ⭐ **教训**：注解的参数**不会自己生效**，必须靠 `initialize` 主动读。
> 忘了读，编译不报错、启动不报错、校验"好像在工作" —— 又一个**静默失效**的兄弟。

## 11. ⭐⭐⭐ 两条校验路径（两个不同的异常）

这是今天最"反直觉"、也最容易漏的一个知识点。

### 现象

Day32 交付给你的 `SkuController` 上有一行：

```java
@Validated                      // ⭐ 加在"类"上
public class SkuController {
    ...
    @GetMapping("/search")
    public Result<List<Sku>> search(
            @RequestParam(value="limit", defaultValue="10")
            @Min(value = 1, message = "limit 至少是 1")
            @Max(value = 50, message = "limit 最多是 50") int limit) { ... }
```

访问 `GET /sku/search?limit=0` → **HTTP 500 + "服务器开小差了，请稍后重试"**。

明明是**你自己参数传错**，服务器却报"服务器炸了"。日志里真凶是：

```
ERROR ... GlobalExceptionHandler : 系统异常
jakarta.validation.ConstraintViolationException: search.limit: limit 至少是 1
    at org.springframework.validation.beanvalidation.MethodValidationInterceptor.invoke(...)
    at com.xiaoming.day32.sku.SkuController$$SpringCGLIB$$0.search(<generated>)
```

### 根因：Spring 里"参数校验"其实有**两条完全独立的路**

| | ② 请求体里的字段 | ⑤ 方法参数（`?limit=0`） |
|---|---|---|
| **谁在校验** | SpringMVC（把 JSON 转对象时） | Spring 的 **AOP**（`MethodValidationInterceptor`，进方法前拦一道） |
| **靠什么开启** | 参数上的 `@Valid` / `@Validated` | ⭐ **类上的 `@Validated`**（会生成 CGLIB 代理） |
| **抛什么异常** | `MethodArgumentNotValidException` | `ConstraintViolationException` |
| **错误从哪取** | `e.getBindingResult().getFieldErrors()` | `e.getConstraintViolations()` |
| **字段名长啥样** | `title`（干净） | `search.limit`（**带方法名前缀**！） |
| **Day31 接住了吗** | ✅ 接住了 → 400 | ❌ **没接** → 掉进兜底 → **500** |

### 怎么修：再写一个 handler（TODO⑤）

```java
@ExceptionHandler(ConstraintViolationException.class)
public ResponseEntity<Result<Void>> handleConstraintViolation(ConstraintViolationException e) {
    Map<String, String> errors = Result.fieldErrors();
    for (ConstraintViolation<?> v : e.getConstraintViolations()) {
        String path = v.getPropertyPath().toString();     // 形如 search.limit
        int dot = path.lastIndexOf('.');
        String field = (dot >= 0) ? path.substring(dot + 1) : path;   // ⭐ 截成 limit
        errors.putIfAbsent(field, v.getMessage());
    }
    log.warn("方法参数校验失败：{}", errors);
    return ResponseEntity.status(400)
            .body(Result.failFields(ResultCode.PARAM_ERROR, "参数校验失败，请看 fieldErrors", errors));
}
```

**实测对比**：

| 请求 | 加 handler 之前 | 加 handler 之后 |
|---|---|---|
| `GET /sku/search?limit=0` | **500**「服务器开小差了」 | **400** `fieldErrors:{limit:"limit 至少是 1"}` |
| `GET /sku/search?limit=99` | 500 | **400** `fieldErrors:{limit:"limit 最多是 50"}` |
| `GET /sku/search?limit=50` | —— | **200**（边界，`<=` 都放过） |

### ⭐ 从这件事该记住的规律

> **兜底 handler 救了所有"意外"，但它分不清"用户手滑"和"服务器炸了"。**
> 所以：**越是常见的错误，越要单独配 handler。**
>
> · Day31：`NoResourceFoundException`（网址打错天天有）→ 你别让它变成 500
> · Day32：`ConstraintViolationException`（参数传错天天有）→ 同理
>
> 📌 一句话：**看日志时凡是"ERROR + 堆栈"里出现的异常，如果是用户经常能触发的，就该给它一条专属 handler。**

## 12. ⭐⭐ 校验的三层（别把三种错混在一起）

| 层 | 靠什么 | 能看到什么 | 例子 | 出错状态码 |
|---|---|---|---|---|
| ① **注解校验** | `@NotBlank` / `@SkuCode` / `@MaxStock` | 只能看**当前对象自己的字段** | 格式对不对、超没超范围 | **400** |
| ② **Service 手写** | `if` + 遍历 / 查库 | 能看**别的数据**（要状态） | **编码有没有重复**、库存够不够 | **409** |
| ③ **数据库约束** | 唯一索引 / NOT NULL / 外键 | 全局、最终 | 并发下的重复插入 | 走不到 —— 有问题就是 **500**（Day35 换 MySQL 后讲） |

### 为什么"编码重复"写不成注解？

> 因为**注解是无状态的** —— 它只能拿到"贴在自己身上的那个字段值"，
> 没法去翻"别的地方有没有同款"。
> **要查数据 = 要有状态 = 只能在 Service 里写。**

实测（答案版）：

```
POST /sku  {"code":"SKU-0001", ...}      ← SKU-0001 已存在
→ 409  {"code":"409","message":"商品编码已存在：SKU-0001"}
```

⭐ 注意状态码是 **409** 不是 400：
**格式没问题（参数没写错），是"和现有数据冲突了"** —— 这正是 Day31 那张 400/404/409 表的活例子。

## 13. 进阶：编程式校验 / 级联校验 / 自定义消息（了解，今天不考）

### ① 级联校验：`@Valid` 贴在**字段**上

如果 `SkuForm` 里嵌了别的对象（比如 `List<Picture> pictures`），
**只写 `@Valid` 在 Controller 参数上是不够的** —— 嵌套对象默认**完全不校验**：

```java
public class SkuForm {
    @Valid                        // ⭐ 贴字段上，才会"往下钻"校验嵌套对象
    private List<Picture> pictures;
}
```

> ⚠️ 这个"嵌套不校验"也是**静默失效**的经典形态。
> 📌 而且这里只能用 `@Valid`，不能用 `@Validated`（后者没有 `ElementType.FIELD`）。

### ② 编程式校验：不靠注解，手动调 Validator

Service 里想手动验一个对象（比如批量导入的每一行）：

```java
@Service
public class SkuService {
    private final Validator validator;              // jakarta.validation.Validator

    public SkuService(Validator validator) { this.validator = validator; }

    public void importOne(SkuForm f) {
        Set<ConstraintViolation<SkuForm>> bad = validator.validate(f, OnCreate.class);
        if (!bad.isEmpty()) {
            // 自己决定：抛异常 / 收集成大报表 / 跳过这一行
        }
    }
}
```

顺手一个实用写法：`validator.validateValue(SkuForm.class, "price", 500)` —— **只验单个字段**。

> 什么时候用？—— 注解管不了的地方：定时任务、消息队列消费、批量导入、
> 以及"想自己控制错误怎么汇总"的场景。

### ③ 自定义消息模板（`{max}` 拼不出来的情况）

`message` 里的 `{max}` 只能引用注解属性。想拼"当前值 + 上限"两个数，就要在校验器里手写：

```java
@Override
public boolean isValid(Integer value, ConstraintValidatorContext context) {
    if (value == null) return true;
    if (value <= max) return true;

    context.disableDefaultConstraintViolation();          // 关掉默认那条
    context.buildConstraintViolationWithTemplate(
            "库存最多 " + max + " 件，你填了 " + value + " 件")   // 自己拼
           .addConstraintViolation();
    return false;
}
```

> 今天**没用到**（`{max}` 够用了），知道有这么个 API 就行。

## 14. 常见坑

| 坑 | 现象 | 解决 |
|---|---|---|
| **注解加了 `groups`，Controller 没改** | 指定的组里没有这些约束 → 该拦的没拦（**静默**） | 两边必须同时改 |
| **Controller 改了，注解没加 `groups`** | `Default` 不参与 → **校验全部失效**，甚至越权通过（实测：带 `id=99` 返回 **200**） | 要写就写全 |
| 用了 `@Valid` 却想指定分组 | **编译不过**（`@Valid` 没有 `groups` 属性） | 换 `@Validated(OnCreate.class)` |
| 自定义注解忘了声明 `groups()` | 它永远只在 `Default` 组生效 → 分组时被跳过 | 三件套一个都不能少 |
| 自定义注解忘了 `@Retention(RUNTIME)` | 运行时读不到注解 → **静默失效** | 必须 `RUNTIME` |
| 校验器里忘了 `initialize` 读参数 | 注解参数完全不生效（实测：`stock:800` 该 400 却 200） | 在 `initialize` 里存成字段 |
| 校验器里判了 `null` 返回 false | 一个字段报**两条错**，fieldErrors 里打架 | 铁律①：`null` 直接放行 |
| 校验器里存了"请求数据"当字段 | 多线程下串数据（校验器是**单例**） | 只放只读的配置 |
| 只写了 `MethodArgumentNotValidException` 的 handler | `@RequestParam` 校验失败 → **500** | 再写 `ConstraintViolationException` 的 |
| 忘了给 `@RequestParam` 的接口加**类级** `@Validated` | `@Min` **完全不生效**（静默） | 类上加 `@Validated` |
| 用了 `javax.validation`（老教程） | 校验**完全不生效且不报错** | SpringBoot 3 用 `jakarta.validation` |
| 以为 `@Min` 会拦 null | 其实 `@Min`/`@Size` 对 null **放行** | "必填"要靠 `@NotNull` |
