## 第 1、2 步：观察和思考的答案

### 三个"不对劲"的根因

| 现象 | 根因 |
|---|---|
| `POST /sku` 传 id 错、不传也错 | `@Null` 和 `@NotNull` 是**相反**的规则，它们都被塞进了 `Default` 组 → 必然有一条不满足 |
| `PUT /sku {"id":1,"price":99}` 被要求填全所有字段 | `@NotBlank`/`@NotNull` 在 `Default` 组里无条件生效 → "部分更新"这种**可以不传**的语义表达不出来 |
| `GET /sku/search?limit=0` 返回 500 | 方法参数校验抛的是 `ConstraintViolationException`，**没人接它** → 掉进兜底 handler |

### 一句话回答第 2 步

> **注解是对的，注解的数量也够；问题是"同一套注解没办法同时满足新增和更新两个场景"。**
> 所以需要"分组"—— 让每条规则**只在合适的场景生效**。

## 第 3 步：TODO① `SkuForm` 加 `groups`

### `sku/SkuForm.java`（完整答案）

```java
package com.xiaoming.day32.sku;

import com.xiaoming.day32.sku.valid.MaxStock;
import com.xiaoming.day32.sku.valid.OnCreate;
import com.xiaoming.day32.sku.valid.OnUpdate;
import com.xiaoming.day32.sku.valid.SkuCode;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Null;
import jakarta.validation.constraints.Size;

public class SkuForm {

    // ⭐ 同一个字段，两条相反的规则，靠分组分开
    @Null(message = "新增时不能自己指定 id（由服务器生成）", groups = OnCreate.class)
    @NotNull(message = "更新时必须指定 id", groups = OnUpdate.class)
    private Long id;

    // @NotBlank 只管新增；@Size 管更新（它对 null 放行 → "不传"没事）
    @NotBlank(message = "书名不能为空", groups = OnCreate.class)
    @Size(min = 1, message = "书名不能是空字符串", groups = OnUpdate.class)
    private String title;

    // @Min(0) 两边都要管 → 花括号一次挂两组
    @NotNull(message = "价格不能为空", groups = OnCreate.class)
    @Min(value = 0, message = "价格不能小于 0", groups = {OnCreate.class, OnUpdate.class})
    private Integer price;

    @NotNull(message = "库存不能为空", groups = OnCreate.class)
    @Min(value = 0, message = "库存不能小于 0", groups = {OnCreate.class, OnUpdate.class})
    @MaxStock(max = 500, groups = {OnCreate.class, OnUpdate.class})
    private Integer stock;

    // 编码只在新增校验（更新不允许改编码，所以不挂 OnUpdate）
    @NotBlank(message = "商品编码不能为空", groups = OnCreate.class)
    @SkuCode(groups = OnCreate.class)
    private String code;

    public SkuForm() {}

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public Integer getPrice() { return price; }
    public void setPrice(Integer price) { this.price = price; }
    public Integer getStock() { return stock; }
    public void setStock(Integer stock) { this.stock = stock; }
    public String getCode() { return code; }
    public void setCode(String code) { this.code = code; }
}
```

### 成品对照表（写完自查）

| 字段 | 新增（OnCreate） | 更新（OnUpdate） |
|---|---|---|
| `id` | `@Null` | `@NotNull` |
| `title` | `@NotBlank` | `@Size(min=1)` |
| `price` | `@NotNull` + `@Min(0)` | `@Min(0)` |
| `stock` | `@NotNull` + `@Min(0)` + `@MaxStock(500)` | `@Min(0)` + `@MaxStock(500)` |
| `code` | `@NotBlank` + `@SkuCode` | （无 —— 编码不许改） |

> 📌 11 个注解 = 2(id) + 2(title) + 2(price) + 3(stock) + 2(code)。**数一遍，一个都不能漏。**

### 为什么必须 `@Valid` → `@Validated`

| | `@Valid` | `@Validated` |
|---|---|---|
| 全名 | `jakarta.validation.Valid` | `org.springframework.validation.annotation.Validated` |
| 出身 | Jakarta 标准 | **Spring 自己加的** |
| `groups` 属性 | ❌ **没有** | ✅ 有（`value()`） |
| 类上能用 | 基本不行 | ✅ 能（方法参数校验的开关） |

> ⭐ 所以 `@Valid` 写 `groups = ...` **编译直接报错**（`找不到符号: 方法 groups()`）。

### 实测（答案版）

| 请求 | 结果 |
|---|---|
| `POST /sku` `{"code":"SKU-0009","title":"测试书","price":50,"stock":5}` | 200 `{"id":4,...}` |
| `POST /sku` `{}` | 400 fieldErrors `{price, title, code, stock}` ← **4 条，没有 id** |
| `POST /sku` `{"id":99,...}` | 400 fieldErrors `{id:"新增时不能自己指定 id（由服务器生成）"}` |
| `PUT /sku` `{"id":1,"price":99}` | 200 `price:99`，`title` 仍是"深入理解 Java 虚拟机" |
| `PUT /sku` `{"price":99}` | 400 fieldErrors `{id:"更新时必须指定 id"}` |
| `PUT /sku` `{"id":1,"title":""}` | 400 fieldErrors `{title:"书名不能是空字符串"}` |
| `PUT /sku` `{"id":999,"price":1}` | 404 `SKU 不存在：id=999` |

### ⭐⭐ 这一步最容易犯的错（真机实测的后果）

只改了 Controller、忘了第 3 步的 `groups`：

| 请求 | 本该 | 实际 |
|---|---|---|
| `POST /sku` 带 `id:99` | 400 | **200！（越权通过）** |
| `POST /sku` `code:"abc"` | 400 | **200** |
| `POST /sku` `{}` | 400 + 4 条 fieldErrors | 400 + `message:"书名不能为空"`，**fieldErrors=null** |
| `PUT /sku` `{"price":99}` | 400 | **404「SKU 不存在：id=null」** |

**为什么会这样**：Contraller 上指定了 `OnCreate` 组 → `Default` 组**不再参与** →
没写 `groups` 的注解（全都属于 `Default`）**一条都不跑**。
它不报错、不告警，接口返回 200 —— 这就是 **"静默失效"**。

## 第 5 步：TODO③ `SkuCodeValidator.isValid`

### `sku/valid/SkuCodeValidator.java`（完整答案）

```java
package com.xiaoming.day32.sku.valid;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

public class SkuCodeValidator implements ConstraintValidator<SkuCode, String> {

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        // ⭐ 铁律①：空值放行 —— "必填"是 @NotBlank 的职责，我不管
        if (value == null || value.isBlank()) {
            return true;
        }
        // 格式：SKU- 后面正好 4 位数字
        // Java 字符串里 \ 要写两次 → \\d 才是正则的 \d
        return value.matches("SKU-\\d{4}");
    }
}
```

### 逐行拆解

| 代码 | 含义 |
|---|---|
| `implements ConstraintValidator<SkuCode, String>` | 第 1 个泛型 = 给哪个注解打工；第 2 个 = 注解贴的字段是什么类型 |
| `if (value == null \|\| value.isBlank()) return true;` | ⭐ 铁律：空值放行。"必填"归 `@NotBlank` 管 |
| `matches("SKU-\\d{4}")` | `SKU-` 字面量 + `\d` 一个数字 + `{4}` 正好重复 4 次 |

### ⭐ 为什么必须放行空值

`SkuForm.code` 上**同时**挂着 `@NotBlank` 和 `@SkuCode`：

```
前端传 code:""
   ↓
@NotBlank 判不合格 → "商品编码不能为空"
@SkuCode  判不合格 → "商品编码格式不对（正确格式：SKU-0001）"
   ↓
同一个输入框旁边出现【两条】红字 ← 前端体验很糟
```

> ⭐ 口诀：**每个注解只管一件事**（单一职责）。所以 `isValid` 第一句永远是放行空值。

### ⭐ `matches()` vs `find()`（一定别搞错）

| 值 | `matches("SKU-\\d{4}")` | `find()` |
|---|---|---|
| `SKU-1234` | ✅ 通过 | ✅ 通过 |
| `xSKU-1234` | ❌ 拒绝 | ✅ **也通过**（危险！脏数据进库） |
| `SKU-12345` | ❌ 拒绝 | ✅ 也通过 |

`matches()` 是**整串匹配**（自动补 `^...$`）。

## 第 6 步：TODO④ `MaxStockValidator`

### `sku/valid/MaxStockValidator.java`（完整答案）

```java
package com.xiaoming.day32.sku.valid;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

public class MaxStockValidator implements ConstraintValidator<MaxStock, Integer> {

    /** ⭐ 只放"配置"（注解参数），绝不放"请求数据" —— 校验器是单例，多线程共用 */
    private int max;

    @Override
    public void initialize(MaxStock annotation) {
        // ⭐ 关键：形参就是"贴在该字段上的那个注解对象"，从它身上把参数读出来
        this.max = annotation.max();
    }

    @Override
    public boolean isValid(Integer value, ConstraintValidatorContext context) {
        // ⭐ 铁律①：空值放行（"必填"归 @NotNull）
        if (value == null) {
            return true;
        }
        // 注意是 <=，写成 < 的话，"正好等于上限"会被判错
        return value <= max;
    }
}
```

### 两个方法的分工

| 方法 | 调用时机 | 干什么 |
|---|---|---|
| `initialize(A annotation)` | **启动时只调一次** | 读注解参数存成字段 |
| `isValid(T value, Context ctx)` | **每个被校验的值都调一次** | 真正判断 |

> ⭐ 为什么分开？注解参数**永远不变**，值每次都变。
> 批量导入几万条时 `initialize` 只跑一次能省大量反射开销。

### ⭐ 交付版里的反面教材（我故意留的坑）

```java
// 交付给你的版本：
public void initialize(MaxStock annotation) {
    this.max = 1000;      // ← 写死了！注解上的 max = 500 完全没用上
}
```

**实测对照**（同一个请求体 `stock:800`）：

| | 写死 1000（没写 TODO④） | 正确读注解（= 500） |
|---|---|---|
| `stock:800` | **200**（800 ≤ 1000，放过了） | **400**「库存不能超过 500」 |

> ⭐ 教训：**注解的参数不会自己生效**，必须靠 `initialize` 主动读。
> 忘了读 → 编译不报错、启动不报错、校验"好像在工作" → 又一个**静默失效**。

### `{max}` 是谁替换的？

```java
String message() default "库存不能超过 {max}";
```

`{max}` 里的 `max` 就是注解的属性名，**Bean Validation 框架自动**去调 `max()` 取值替换。
好处：**一句模板适配所有上限**，不用为每个值写一条消息。

实测：`@MaxStock(max = 500)` + `stock:800` → fieldErrors 里是 **`"库存不能超过 500"`**。

### 实测（答案版）

| `stock` | 结果 |
|---|---|
| `800` | **400** `{stock:"库存不能超过 500"}` |
| `500` | **200**（边界，`<=` 放过） |
| `501` | 400 |
| `0` | 200 |
| `-1` | 400，消息是 `库存不能小于 0`（`@Min` 那条） |

## 第 7 步：TODO⑤ 接住 `ConstraintViolationException`

### `common/exception/GlobalExceptionHandler.java`（新增的方法）

放在 ③ `NoResourceFoundException` 之后、④ 兜底**之前**：

```java
import jakarta.validation.ConstraintViolation;             // ⭐ 新 import
import jakarta.validation.ConstraintViolationException;     // ⭐ 新 import

    /**
     * ⭐ **方法参数**校验失败 → 400 + fieldErrors
     * 触发场景：GET /sku/search?limit=0（limit 上有 @Min(1)）
     */
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<Result<Void>> handleConstraintViolation(ConstraintViolationException e) {
        Map<String, String> errors = Result.fieldErrors();
        for (ConstraintViolation<?> v : e.getConstraintViolations()) {
            String path = v.getPropertyPath().toString();      // 形如 "search.limit"
            int dot = path.lastIndexOf('.');
            String field = (dot >= 0) ? path.substring(dot + 1) : path;   // ⭐ 截成 "limit"
            errors.putIfAbsent(field, v.getMessage());
        }

        log.warn("方法参数校验失败：{}", errors);     // 预期内的错 → warn，不打堆栈
        return ResponseEntity.status(400)
                .body(Result.failFields(ResultCode.PARAM_ERROR, "参数校验失败，请看 fieldErrors", errors));
    }
```

### 三个关键点

| # | 关键点 | 为什么 |
|---|---|---|
| 1 | 状态码 **400** | 这是"请求不合法"，不是"服务器出错"。别让它走 500 的兜底 |
| 2 | 字段名要**截断** | `getPropertyPath()` 给的是 `search.limit`（**方法名.参数名**），
直接给前端会对应不上输入框 → 取最后一个 `.` 之后的部分 |
| 3 | 日志用 **warn** | 预期内的错，不打堆栈（和 ①② 保持一致） |

### ⭐⭐ 为什么这里会出现"第二个校验异常"

Spring 里"参数校验"其实有**两条完全独立的路**：

| | ② 请求体里的字段 | ⑤ 方法参数（`?limit=0`） |
|---|---|---|
| **谁在校验** | SpringMVC（把 JSON 转对象时） | Spring 的 **AOP**（`MethodValidationInterceptor`） |
| **靠什么开启** | 参数上的 `@Valid` / `@Validated` | ⭐ **类上的 `@Validated`** |
| **抛什么异常** | `MethodArgumentNotValidException` | `ConstraintViolationException` |
| **错误从哪取** | `e.getBindingResult().getFieldErrors()` | `e.getConstraintViolations()` |
| **字段名** | `title`（干净） | `search.limit`（带方法名前缀） |
| **Day31 接住了吗** | ✅ → 400 | ❌ 没接 → **兜底 → 500** |

日志原文（改之前的真凶）：

```
ERROR ... GlobalExceptionHandler : 系统异常
jakarta.validation.ConstraintViolationException: search.limit: limit 至少是 1
    at org.springframework.validation.beanvalidation.MethodValidationInterceptor.invoke(MethodValidationInterceptor.java:...)
    at com.xiaoming.day32.sku.SkuController$$SpringCGLIB$$0.search(<generated>)
```

> 📌 注意那个 `$$SpringCGLIB$$0` —— **类上加了 `@Validated`，Spring 就给你的 Controller 生成了一个代理对象**。
> 校验就发生在"进真正方法之前"那一层。Day42 学 AOP 时会把这个机制彻底拆开。

### 实测对照

| 请求 | 改之前 | 改之后 |
|---|---|---|
| `GET /sku/search?limit=0` | **500**「服务器开小差了」 | **400** fieldErrors `{limit:"limit 至少是 1"}` |
| `GET /sku/search?limit=99` | 500 | **400** fieldErrors `{limit:"limit 最多是 50"}` |
| `GET /sku/search?limit=51` | 500 | 400 |
| `GET /sku/search?limit=50` | 200 | **200**（边界放过） |
| `GET /sku/search?limit=1` | 200 | 200 |

⭐ 关键是 fieldErrors 的 key 必须是 **`limit`**（截断成功），不能是 `search.limit`。

## 第 8 步：思考题答案

### ① 为什么 `@SkuCode` 遇到空值必须放行？（2 分）

因为 `SkuForm.code` 上**同时**有 `@NotBlank`（管"有没有填"）和 `@SkuCode`（管"格式对不对"）。
**每个注解只管一件事**：判断"有没有填"是 `@NotBlank` 的活，`@SkuCode` 只该管格式。

如果 `@SkuCode` 也把 null/空串判为不合格：

```
前端传 code:""
   → @NotBlank 报"商品编码不能为空"
   → @SkuCode  报"商品编码格式不对（正确格式：SKU-0001）"
   → 同一个输入框旁边挂【两条】红字
```

前端通常按"字段 → 一条错误"来渲染，两条红字会互相覆盖/堆叠，用户体验很差。
而且语义上也重复了：**"格式不对"这种话对"根本没填"这个情况毫无意义**。

所以 `isValid` 的第一句永远是：`if (value == null || value.isBlank()) return true;`

### ② 为什么校验器里"只能放配置"？（1.5 分）

因为**校验器是单例** —— Spring / Validator 全程只 `new` 一个实例，**所有请求共用同一个对象**
（不可能每个请求都新建一个，那样每次都要重新反射读注解，太慢）。

如果里面存了"当前请求的数据"：

```java
private String currentTitle;                 // ❌ 危险
public boolean isValid(String v, Context c) {
    this.currentTitle = v;                   // 请求 A 写
    // ... 中间别的请求 B 也进来把 currentTitle 覆盖了 ...
    return check(this.currentTitle);         // 请求 A 读到的是 B 的数据
}
```

这就是 Day18/19 学过的**多线程共享可变状态**问题：会串数据，而且问题偶发、极难排查。

所以字段只放**只读的配置**（如 `max`），它们在 `initialize` 里赋值一次，之后再也不改。

### ③ 为什么"编码重复"写不成注解？（1.5 分）

因为**注解是无状态的**。`ConstraintValidator` 能拿到的只有：

| 能拿到 | 拿不到 |
|---|---|
| 当前这个字段的**值** | 数据库里有没有同款 |
| 注解上的参数（`max` 等） | 别的对象、别的请求的数据 |
| `ConstraintValidatorContext` | 其他表/集合的内容 |

"编码是否重复"必须去**遍历 `db`（或查数据库）**才知道 —— 这是"**要状态**"的判断。
而注解是"**只看自己**"的机制。

所以这类规则只能在 Service 里手写：

```java
for (Sku s : db.values()) {
    if (form.getCode() != null && form.getCode().equals(s.getCode())) {
        throw new BizRuleException("商品编码已存在：" + form.getCode());    // 409
    }
}
```

> ⭐ 顺便：状态码是 **409** 不是 400 —— 格式没问题（参数没写错），是"和现有数据冲突了"。
> 实测：`POST /sku` `{"code":"SKU-0001",...}` → `409 商品编码已存在：SKU-0001`

**📍 划清界限：**

| 判断需要什么 | 放哪 | 状态码 |

## 🎓 这一天的三句话总结

1. **分组校验**解决的是"同一套注解要适配多个场景" —— 而它的代价（静默失效）比它解决的问题更值得警惕。
2. **自定义注解**的本质是"给一条规则起个能复用的名字"，而**校验器是单例**这件事决定了两条铁律（空值放行 + 只放配置）。
3. **Spring 里"参数校验"有两条路**（请求体 / 方法参数），抛两个不同的异常 —— 漏接一条，用户手滑就会变成"服务器炸了"。

> 📌 判断"该不该给异常配 handler"的通用标准：
> **日志里凡是 ERROR+堆栈、但其实是用户经常能触发的异常，都该有一条专属 handler。**
