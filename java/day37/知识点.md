## 0. 名词速查（看不懂词就回这张表）

### 0.1 昨天（Day36）见过的

| 词 | 人话 | 生活里的比喻 |
|---|---|---|
| 索引 | 给**某一列**建的一份排好序的小目录 | 书最后面的索引页：查词先翻它，不用一页页找 |
| 主键索引（聚簇索引） | `id` 那一列；整行数据就按 id 排着放 | 按学号排的档案柜，格子里是一整份人事档案 |
| 二级索引（普通索引） | 你自己在别的列上建的目录；每一条只记「这一列的值 + id」 | 一张小卡片，上面写：手机号 138… → 学号 7 |
| **回表** | 卡片上只有 id，想要别的列，得拿 id 去档案柜再取一次 | 查卡片拿到学号 → 再跑去柜子取那份档案 |
| 联合索引 | 一个索引里放好几列，按 (a, b, c) 的顺序排 | 电话簿：先按城市排，同城再按姓排 |
| 最左前缀 | 联合索引只能从**第一列**开始连续用，中间不能跳 | 电话簿不能跳过城市，直接按姓找 |

### 0.2 今天新出现的

**必须能自己讲清的 6 个**（面试也会问）：

| 词 | 人话 | 比喻 |
|---|---|---|
| **覆盖索引** | 你要的列，索引卡片上全有，**不用回表** | 卡片上直接写了手机号，不用再跑柜子 |
| **type** | MySQL 选的那种"查法"，一共 6 档，越靠右越慢 | 直接知道在哪一格 → 查目录 → 翻整个房间 |
| **Extra** | 执行计划的"备注栏"：有没有回表、要不要额外排序 | 方案图上的小字备注 |
| **Using filesort** | 备注里出现它 = 数据取出来以后在内存里**重新排队** | 把书全搬出来重新排一遍架 |
| **深分页** | `LIMIT 150000, 20` 这种翻到很后面的写法 | 从第 1 页数到第 7500 页，数一页扔一页 |
| **ICP（索引下推）** | 能在索引卡片上判断的条件，先在卡片上判断，不合格的就不去取档案 | 卡片上有"积分"，先把积分 < 10 的划掉 |

**认识就行**（看到不懵即可）：

| 词 | 人话 |
|---|---|
| EXPLAIN（执行计划） | 让 MySQL 先说"我打算怎么查"，**不真的查** |
| `key` | 这次实际用了哪个索引（`-` 就是没用索引） |
| `key_len` | 用到了索引的**几列**（比"有没有 key"更可靠） |
| `rows` | 它**估计**要读多少行 —— 注意是估计，不是结果行数 |
| `filtered` | 它**估计**读完这些行还剩百分之几 —— 常常直接猜 10% |
| `Using index` | 备注里出现它 = 只用索引就够，**没回表** |
| `Using index condition` | 备注里出现它 = 在索引上先过滤（ICP 在工作） |
| 延迟关联 | 先只查 id，再拿这 20 个 id 去取整行 |
| 游标法 | 用"上一页最后一条"当起点，不用偏移量 |
| 优化器 | MySQL 里那个"决定怎么查"的决策者，按**估计**的成本选方案 |
| `ANALYZE TABLE` | 让它重新数一遍数据、更新估计（估算离谱时先做这个） |
| 区分度 | 这一列有多少个不同的值；越高越值得建索引（手机号高、性别低） |

## 1. 一个故事：产品提了 5 个需求

表：`member`，20 万行，只有 `id` 主键 + 一个 `(city, age)` 的联合索引。

| 需求 | 昨天的办法 | 今天要解决的问题 | 实测 |
|---|---|---|---|
| ① 按手机号查一个人 | 建索引 | ——（昨天就会了）| 160 ms → 0.34 ms |
| ② 查郑州的 2 万个手机号 | 建 `(city, age)` 索引 | 索引里只有 id，**要回表 2 万次** | 110 ms → **19.7 ms**（覆盖索引）|
| ③ 按时间倒序看最新 20 条 | —— | 没索引 → 20 万行搬出来**排队** | 123 ms → **0.79 ms**（给时间列建索引）|
| ④ 翻到第 7500 页 | —— | 不是"跳过去"，是**从第 1 页数过去** | 309 ms → **3.8 ms**（换写法）|
| ⑤ 郑州 + 积分 < 10 的人 | 建 `(city, age)` | 条件里有的列**不在卡片上** | 108 ms → **16.8 ms**（ICP）|

下面的 §2~§6 就是把 ②~⑤ 一个个讲清楚。

## 2. 覆盖索引：卡片上直接有答案

### 先看问题

```sql
SELECT phone FROM member WHERE city = '郑州';   -- 2 万行
```

索引是 `(city, age)`。MySQL 顺着索引找到 2 万个"郑州"，但索引里只有 `city、age、id`——**没有 phone**。
所以每一行都得：拿 id → 回主键树取整行 → 抠出 phone。**2 万次回表。**

### 解决：把 phone 也加进索引

```sql
ALTER TABLE member ADD INDEX idx_city_age_phone (city, age, phone);
```

现在索引里有 phone 了，2 万行全部**从索引里直接返回**，一次都不用回表。

| 同一条 SQL | 改造前 | 改造后 |
|---|---|---|
| 耗时 | 110.4 ms | **19.7 ms** |
| `Extra` | 空 | **`Using index`** |

### 代价（不是白给的）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 索引总大小 | 8,929,280 字节 | 17,891,328 字节（**多了 8.5 MB**）|

索引越宽 → 占空间、写入更慢。**这是拿空间换读速度**，只给"真的很热的查询"用。

### 三个判断口诀

1. `Extra` 里出现 **`Using index`** → 覆盖了，**没回表**；
2. `Extra` 是**空的** → 走了索引，但**回表了**；
3. **`SELECT *` 永远覆盖不了**（它要整行），所以它永远回表。

第 3 条有实测：加宽索引后，`SELECT * ... WHERE city='郑州' AND age=25` 的 `Extra` 还是空的——MySQL 知道覆盖不了，干脆选了更窄的旧索引。

> **记住这一句**：索引里有的列，查询就不用回表；要的列不在索引里，就一定回表。

## 3. 执行计划：让 MySQL 交一份"体检报告"

```sql
EXPLAIN SELECT ...;          -- 只看方案，不执行
EXPLAIN ANALYZE SELECT ...;  -- 真跑一遍，给"实际读了多少行、花了多久"
```

`EXPLAIN` 会输出一行（联表时多行），有 11 列。今天只看 6 列：

| 列 | 人话 | 你要盯的是什么 |
|---|---|---|
| `type` | 查法 | 是 `ALL`（全表扫）还是 `ref/range/const`（走索引）|
| `key` | 实际用的索引 | `-` = 没用索引 |
| `key_len` | 用了几列 | 联合索引里"到底用上几列"就靠它 |
| `rows` | **估计**要读多少行 | 只是估计，不能当结果行数 |
| `filtered` | **估计**还剩百分之几 | 没统计的列，它就是"猜 10%" |
| `Extra` | 备注 | 有没有 `Using index` / `Using filesort` |

### `type` 的 6 档（从快到慢）

| type | 人话 | 例子 |
|---|---|---|
| `const` | 直接知道在哪一格 | `WHERE id = 1` |
| `eq_ref` | 联表时对方按唯一索引精确查 1 条 | 联 `city_dict` 的 `name` |
| `ref` | 按某个值查到一片 | `WHERE city = '郑州'` |
| `range` | 按范围扫一段 | `WHERE id BETWEEN 100 AND 200` |
| `index` | 把整本索引翻一遍（但不回表）| `SELECT COUNT(*)` |
| `ALL` | 把整张表翻一遍 | `WHERE status = 1` |

记忆法：**`const` → `eq_ref` → `ref` → `range` → `index` → `ALL`，越往右越慢。看到 `ALL` 就该想想能不能建索引 / 改写法。**

### 最容易骗人的：`rows` 和 `filtered` 都是"估计"

真机对比同一条 SQL：

| 查询 | `EXPLAIN` 的估计 | 真实 |
|---|---|---|
| `WHERE city='郑州'` | `rows=38930` | **20000** 行 |
| `WHERE city='郑州' AND status=1` | `38930 × filtered 10%` ≈ **3893** | **17143** 行 |

- `rows` 是统计信息算出来的估计值，偏大偏小都正常；
- `filtered=10%` 是"`status` 没有索引，那就按 10% 猜"——真实是 85.7%（6/7 的人在用）。
- 所以：**`rows` 只能用来比较"两个方案谁更小"，不能当"会返回多少行"**。

> **记住这一句**：看执行计划先看 `type` 和 `Extra`，`rows` 只当参考，别当事实。

## 4. 排序：为什么 `ORDER BY` 会慢

数据库里的行**不是按时间排的**（按 id 排）。所以：

```sql
SELECT * FROM member ORDER BY created_at DESC LIMIT 20;
```

它只能把 20 万行全读出来，**在内存里重新排队**，再取前 20。`Extra` 里会写 `Using filesort`（名字叫"文件排序"，其实大多数时候在内存里排）。

给这一列建索引就没事了，因为**索引本身就是排好序的**：

```sql
ALTER TABLE member ADD INDEX idx_created (created_at);
```

| | 建索引前 | 建索引后 |
|---|---|---|
| 耗时 | 123 ms | **0.79 ms** |
| `Extra` | `Using filesort` | **`Backward index scan`**（倒着读索引，读 20 条就停）|

### 三条规矩

1. 排序列**和索引列顺序一致**，才能借上索引的"已经排好"；
2. `WHERE` 里有等值条件时，排序键可以接在后面：`WHERE city='郑州' ORDER BY age` 配 `(city, age)`；
3. `DESC` 不用专门建降序索引——MySQL 8 会"倒着扫"。

> **记住这一句**：`Using filesort` = 取出来重新排队；索引有序 = 不用排队。

## 5. 深分页：翻到第 7500 页为什么慢

```sql
SELECT * FROM member ORDER BY created_at DESC LIMIT 150000, 20;
```

看起来像"跳到第 150000 行"，**其实不是**。它是：

> 按顺序**读出 150020 行**，把前 150000 行**扔掉**，返回最后 20 行。

所以越往后越慢。更糟的是：**即使有索引，MySQL 也可能不用**——它算了一笔账，觉得"走索引要回表 15 万次"比"全表扫一遍再排序"还贵，于是放弃索引（`type=ALL`）。

实测三种写法（同一个查询、同一批数据）：

| 写法 | SQL 关键部分 | 耗时 |
|---|---|---|
| A 老写法 | `LIMIT 150000, 20` | **309 ms** |
| B 延迟关联 | 子查询只查 `id`，再用这 20 个 id 取整行 | **77 ms** |
| C 游标法 | `WHERE created_at < '上一页最后一条的时间'` | **3.8 ms** |

- **B 延迟关联**：子查询只要 `id`，索引里就有（不回表），跳过 15 万行只花"翻索引"的钱；拿到 20 个 id 再回表 20 次。
- **C 游标法**：用"位置"代替"偏移量"，索引直接定位到起点。代价：不能"跳到第 N 页"，只能"下一页"。App 的下拉刷新、feed 流都是这么做的。

> **记住这一句**：`LIMIT N, 20` 的 N 不是"跳过"，是"读出来扔掉"；翻得越深越亏。

## 6. 索引下推（ICP）：先在卡片上划掉

条件：`WHERE city='郑州' AND age>20 AND score<10`，索引 `(city, age, score)`，命中 186 行。

没有 ICP：索引先找出"郑州 + 年龄 > 20"的 **3.5 万行**，**全部回表**，再在 Server 层筛 `score<10`。
有 ICP：`score` 就在索引卡片上，**先在卡片上看一眼**，不合格的不去回表 → 只回表 186 次。

| 做法 | 耗时 | `Extra` |
|---|---|---|
| ICP 开（强制走 score 索引）| **16.8 ms** | `Using index condition`（没有 `Using where`）|
| ICP 关（同一个索引）| **108 ms** | `Using where` |

### 关键边界：只能推"卡片上有的列"

| 条件 | 能 ICP 吗 | 为什么 |
|---|---|---|
| `score < 10`，索引是 `(city, age, score)` | ✅ | score 在索引里 |
| `status = 1`，索引是 `(city, age, phone)` | ❌ | **status 不在索引里**，只能回表后再筛（`Extra` 只有 `Using where`）|

> **记住这一句**：ICP 就是"索引里有的列，先在索引上判断"；索引里没有的列，它没办法。

## 7. 索引到底怎么设计（五步）

| 步 | 做什么 | 人话 |
|---|---|---|
| 1 | 找出**真正慢的**查询 | 别拍脑袋，先看是哪条 SQL 慢 |
| 2 | 算**区分度** | 这列有多少个不同值？手机号值得建，性别不值得 |
| 3 | 排顺序：**等值列在前、范围列在后，排序键接最后** | 先把范围缩小，再排 |
| 4 | 能**覆盖**就覆盖 | 把查询要的列也放进去，省回表 |
| 5 | **EXPLAIN 验证** | `type` 有没有升级、`Extra` 有没有 `filesort` |

### 前缀索引：省空间，但别乱用

长字符串（网址、备注）可以只索引前 N 个字符，像"只抄书名前 8 个字"。N 选多少？算区分度：

| 前缀 | 不同值个数 | 结论 |
|---|---|---|
| `LEFT(name, 4)` | 99 | 太短，一查一大片 |
| `LEFT(name, 6)` | 9,999 | 约 5% |
| `LEFT(name, 8)` | 200,000 | 和全名一样（本表名字最长 8 个字）|

所以本表**不要**用前缀索引：名字太短，前缀 8 就等于全列，白折腾。

### 冗余索引：同一份目录印了两遍

已经有 `(city, age, phone)` 和 `(city, age, score)`，那 `(city, age)` 就是多余的——它俩的**最左前缀**已经能顶替它。
多余的索引白占空间、拖慢写入，该删。

### 优化器也会选错

第 6 节那条 SQL：不强制时它选了 `(city, age, phone)`（108 ms），`FORCE INDEX` 指到 `(city, age, score)` 只要 16.8 ms。
因为它是按**估计**选方案的。遇到这种情况：先 `ANALYZE TABLE member;` 更新统计，还错再考虑 `FORCE INDEX`（**只在确认过的单条 SQL 上用**）。

> **记住这一句**：索引不是越多越好，是"按查询的顺序排、能覆盖就覆盖、最后用 EXPLAIN 验收"。

## 8. 常见坑（口语版）

| # | 坑 | 正解 |
|---|---|---|
| 1 | `key` 有值就以为优化好了 | 看 `Extra`：有 `Using index` 才是真的不回表 |
| 2 | 把 `rows` 当返回行数 | 它是估计；真实值用 `EXPLAIN ANALYZE` 或 `COUNT` |
| 3 | 以为 `LIMIT 100000,20` 是"跳过去" | 是"读出来扔掉"，深分页要换写法 |
| 4 | 以为 `Using filesort` 一定很慢 | 数据少 + LIMIT 小时无所谓，看 `rows` |
| 5 | 看到 `Using index condition` 就以为 ICP 生效 | 范围查询也会显示它；要看有没有 `Using where` |
| 6 | 给 `status`（只有 0/1）单建索引 | 区分度太低，命中的行太多，不如不建 |
| 7 | 索引建完不 `ANALYZE` 就下结论 | 统计信息旧了，优化器会按旧数据选错 |
| 8 | 为了"覆盖"把 10 个列都塞进索引 | 索引会变得又大又慢，写一次要改十处 |
