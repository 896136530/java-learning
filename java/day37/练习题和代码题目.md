## B. 读执行计划（30 分，3 组 × 10 分）

### 报告一（覆盖索引）

同一条 SQL：
```sql
SELECT phone FROM member WHERE city = '郑州';
```

改造前（索引是 `(city, age)`）：
```
type=ref  key=idx_city_age  key_len=82  rows=40110  Extra=（空）
```
把索引加宽成 `(city, age, phone)` 之后：
```
type=ref  key=idx_city_age_phone  key_len=82  rows=38930  Extra=Using index
```

1. 两次 `key_len` 都是 82，说明**用到了几列**？是哪一列？
2. 加宽索引后 `Extra` 变成了 `Using index`，这代表什么？
3. 改造后还需要回表吗？为什么？这条 SQL 总共返回 2 万行，改造前后"回表次数"各是多少？

> 你的答案：1.都只用到了city列
> 2.代表了从需要回表到覆盖索引不需要回表
> 3.改造后旧不需要回表了因为原来的需要的信息不在二级索引里面需要回到主键去查找

2.### 报告二（估算 vs 真实）

```sql
SELECT * FROM member WHERE status = 1;
```
```
type=ALL  key=-  rows=199269  filtered=10.0  Extra=Using where
```
（真实返回 **171429** 行）

1. 这条走索引了吗？从哪一列看出来的？
2. `rows=199269`、`filtered=10.0`，按它的估计应该返回多少行？和真实的 171429 差多少倍？按rows的估值是199269差了
3. `filtered=10.0` 是怎么来的？为什么这么不准？
4. 要不要给 `status` 建个索引？为什么？

> 你的答案：1.没有从type=ALL看出来的2.按rows的估值是199269差了0.16倍3.是优化器估算的值因为这是优化器大概估算的一般是10.0%
4.不建议给 status 建索引。满足`status=1`的数据占比很高，使用索引需要大量回表，成本高于全表扫描，索引几乎没有性能收益。
### 报告三（排序与深分页）

```sql
-- ①
SELECT * FROM member ORDER BY created_at DESC LIMIT 20;
-- 建索引前：type=ALL     key=-            rows=199269  Extra=Using filesort
-- 建索引后：type=index   key=idx_created  rows=20      Extra=Backward index scan

-- ②
SELECT * FROM member ORDER BY created_at DESC LIMIT 150000, 20;
-- 有 idx_created：type=ALL  key=-  rows=199269  Extra=Using filesort
```

1. ①建索引后 `rows=20`，为什么不是 199269？
2. `Backward index scan` 是什么意思？为什么它就不需要 `Using filesort` 了？这个
3. ②明明已经有 `idx_created`，为什么 MySQL 还是选了 `ALL`？它在算什么账？
4. ②这种查询，除了改索引，还能怎么改？（说出两种写法）

> 你的答案：1.因为建索引后倒着检索索引，所以返回的是20行数据2.因为建索引后倒着检索索引，已经排过序了所以不需要额外排序
3.`limit 150000,20`需要先跳过前面 15 万条索引记录，每一条都要回表拿完整数据，回表成本极高；MySQL 一算，不如直接全表扫描 + 排序，开销更小，所以放弃索引选了 type=ALL。
---4.方案 1：延迟关联，子查询先利用索引分页拿到主键，再关联查询完整数据；方案 2：书签分页，记录上一页末尾的 created_at，用`where created_at < 时间`替代大 offset。

**2.** 列表页：
```sql
SELECT id, name, phone, score FROM member
WHERE city = '郑州' AND status = 1
ORDER BY score DESC LIMIT 20;
```
写出你要建的索引（DDL），并解释**列的顺序为什么这么排**。

> 你的答案：CREATE INDEX idx_city_status_score ON member(city, status, score);因为根据联合索引做左侧原则会从最左侧开始一一对照，所以city, status, score的顺序是正确的。


**3.** 搜索页：
```sql
SELECT id, name FROM member WHERE name LIKE '%1234';
```
这条能靠索引变快吗？为什么？想让这类搜索变快，有哪两条路？（提示：一条跟 `%` 有关，一条跟"全文检索"有关）

> 你的答案：不能用普通 B + 树索引提速。
原因：`LIKE '%1234'` 通配符在左边，B + 树索引是按字符串前缀排序，没法利用前缀快速定位，只能全表扫描。
方法1：改成`LIKE '1234%'`，利用前缀快速定位。
方法2：给 name 创建**全文索引 FULLTEXT**，用全文检索函数搜索，支持后缀、中间关键词检索。

**4.** 现有索引 `(city, age, phone)`：
```sql
SELECT * FROM member WHERE city = '郑州' AND age > 20 AND score < 10;
```
（真实命中 186 行，但符合 city+age 的约有 3.5 万行）
这条大概要回表多少次？建什么索引能让它"少回表"？这个机制叫什么？

> 你的答案：要会表3.5万次建覆盖索引idx_city_age_score (city, age, score)这个机制叫icp

**5.** 现在表上有：`(city, age)`、`(city, age, phone)`、`(city, age, score)`。
哪个索引是**冗余**的？删掉它有风险吗？为什么？

> 你的答案：冗余索引：`(city, age)`。
原因：`(city, age, phone)` 的最左前缀就是 `city,age`，可以替代 `(city,age)`。
删除有轻微风险：`(city,age,phone)` 索引字段更多、体积更大，只查询 city+age 的 SQL，扫描代价会略高于原来短索引；但一般业务上可以删掉，减少索引维护开销。
