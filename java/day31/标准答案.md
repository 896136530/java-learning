## 第 1 步：默认错误页（实测）

```bash
GET /abc
```
```json
{ "timestamp":"2026-10-08T11:42:45.106+00:00", "status":404, "error":"Not Found",
  "message":"No static resource abc.", "path":"/abc" }
```
**状态码 404，是 JSON**（不是 HTML）—— 因为 `spring.mvc.throw-exception-if-no-handler-found` 未开，
经典错误页在新版本里默认返回 JSON。**但格式和我们自己的完全不同**（`{timestamp,status,error,message,path}`）。

```bash
GET /sku/boom
```
```json
{ "timestamp":"2026-10-08T11:44:41.626+00:00", "status":500, "error":"Internal Server Error",
  "message":"Cannot invoke \"com.xiaoming.day31.sku.Sku.getTitle()\" because \"sku\" is null",
  "path":"/sku/boom" }
```

⭐ **泄露点**（批改时必须确认学生指出了这两个）：
1. **完整类名 + 方法名**：`com.xiaoming.day31.sku.Sku.getTitle()` —— 内部包结构暴露
2. 如果是 SQL/反射异常，会进一步泄露**表名、字段名、SQL 语句** → 安全漏洞

**批改口径**：只要学生答出"泄露了类名/方法名"或"泄露内部实现"即给满分。

## 第 2 步：异常体系（答案要点）

| 问题 | 答案 |
|---|---|
| `BaseException` 存了哪两样 | `code`（业务码）+ `http`（HTTP 状态码）；message 交给父类 `RuntimeException` |
| 为什么子类只有 5 行 | **逻辑全在父类**；子类唯一的作用是让"错误类别"成为**类型信息**，供处理器按类型分派 |
| 为什么继承 `RuntimeException` | `Exception` 是受检的 → 每个调用它的方法都要 `throws`/try-catch，污染整条调用链；`RuntimeException` 能穿透多层直达 `@RestControllerAdvice` |
| 两个 handler 都匹配时走哪个 | 走 **`ParamException`**（更具体）。Spring 选继承关系中**最近**的那个 |

## 第 3 步：TODO① 兜底处理器（答案）

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<Result<Void>> handleOther(Exception e) {
    log.error("系统异常", e);                       // ⭐ 异常对象当最后一个参数 → 自动打完整堆栈
    return ResponseEntity.status(500)
            .body(Result.fail(ResultCode.SYSTEM_ERROR, "服务器开小差了，请稍后重试"));
}
```

**实测结果（已打补丁验证）**：

```bash
GET /sku/boom
→ HTTP 500
{ "code":"500", "message":"服务器开小差了，请稍后重试", "data":null, "fieldErrors":null }
```

### ⚠️ 批改要点（按严重程度排序）

| 级别 | 错误写法 | 为什么不给分 |
|---|---|---|
| 🔴 严重 | `log.error("系统异常：" + e.getMessage())` | **堆栈丢了**，线上无法排查 —— 这是本次最重要的知识点，必扣 |
| 🔴 严重 | `.body(Result.fail(ResultCode.SYSTEM_ERROR, e.getMessage()))` | **泄露内部信息**（安全漏洞），必扣 |
| 🔴 严重 | 忘了 `ResponseEntity.status(500)`，直接返回 `Result` | 状态码变 200 → 退回 Day30 的坑 |
| 🟡 中等 | 方法写成 `private` | Spring 不会调用它，功能不生效 |
| 🟡 中等 | 用 `@ExceptionHandler(Throwable.class)` | 太宽，会吞掉 Spring 内部异常（如 `NoHandlerFoundException`），导致 `/abc` 行为异常 |
| 🟢 轻微 | `log.error("系统异常", e.getMessage())` | 传的是 String，**堆栈仍然丢失**（易错点！必须是 `e` 对象） |
| 🟢 轻微 | 消息文案不同（"服务器开小差了" 换成别的） | 不扣分，只要笼统 |

### 常见误解

> "为什么业务异常（①②）不也打堆栈？" —— 因为业务异常是**预期内**的
> （用户输错库存一天可能几万条），打堆栈会淹没真正的 bug。
> **两个级别 = 两种性质**，这是工程经验。

## 第 4 步：三种业务异常（实测值）

| 请求 | 状态码 | message |
|---|---|---|
| `POST /sku/outbound?id=1&count=0` | **400** | `出库数量必须大于 0，你传的是 0` |
| `GET /sku/999` | **404** | `SKU 不存在：id=999` |
| `POST /sku/outbound?id=2&count=100` | **409** | `库存不足：「Java 并发编程实战」现有 3 件，你想出库 100 件` |
| （补充）`POST /sku/outbound?id=999&count=1` | **404** | `SKU 不存在：id=999` |

**为什么不能共用一个状态码**（答案要点）：
> 状态码是"**告诉调用方该怎么办**"的：400 → 改请求；404 → 改 ID；409 → **重试没用**，得先改变现实。

**③ 和 ① 的区别**：
> 400 是"你传的参数本身不合法"（count=0 永远是错的，任何时间都错）；
> 409 是"参数没错、东西也在，但**当前状态不允许**"（库存 3 件要出库 100 件，
> 等进了货再试就能成功）—— **可重试性**是本质区别。

## 第 5 步：校验失败（实测）

```bash
POST /sku   {"title":"","price":-1,"stock":null}
→ HTTP 400
{ "code":"400", "message":"参数校验失败，请看 fieldErrors", "data":null,
  "fieldErrors": {
    "price":"价格不能小于 0",
    "stock":"库存不能为空",
    "title":"书名不能为空"
  } }
```

**为什么要按字段收集**：
> 前端要**把红字标在对应输入框旁边**。拼成一句话前端还得自己切字符串 ——
> **接口设计要替调用方考虑**。

**`@Min(0)` 拦下了，Service 里的 if 还有用吗**：
> **有用**。`@Valid` 只作用于**这个接口**；定时任务、内部方法调用、导入功能都会**绕过接口层**。
> Service 的校验是**最后一道防线**。

## 第 6 步：日志（实测原文）

```
WARN  ... c.x.d.c.e.GlobalExceptionHandler : 业务异常：code=409, http=409, message=库存不足：...
WARN  ... c.x.d.c.e.GlobalExceptionHandler : 业务异常：code=404, http=404, message=SKU 不存在：id=999
ERROR ... c.x.d.c.e.GlobalExceptionHandler : 系统异常
    （紧接着整段堆栈，含 java.lang.NullPointerException at com.xiaoming.day31.sku.SkuService.boom(SkuService.java:...))
```

| | 级别 | 堆栈 |
|---|---|---|
| 业务异常 | `WARN` | **不打**（只打一行 code/http/message） |
| 系统异常 | `ERROR` | **必打**（完整堆栈） |

**理由（答案要点）**：
> 业务异常是**预期内**的正常分支（用户输错而已），量大、无需排查 → 一行足够；
> 系统异常是**真 bug**，没有堆栈根本不知道哪一行炸的 → 必须完整。
> ⭐ 一句话总结：**日志里要详细，返回给外面要笼统。**

| 级别 | 写法 | 判定 |

| 🔴 错 | 只判空没判库存 | 没实现需求，扣 10 分 |

### ⭐ 核心问题：为什么不用改 `GlobalExceptionHandler`？

> 因为"库存不能删"属于**业务规则冲突**，复用现成的 `BizRuleException`（409）就够 ——
> **新增一种错误只需在 Service 里 throw 一下，状态码和 JSON 格式自动就对**。
> 这就是把横切逻辑抽出去的价值：**不是少写代码，而是加功能时不会漏、不会改错**。

## 第 8 步：三道思考题（参考答案）

### 题 1：`fieldErrors` 总是 null

**方案 B 的做法**：在 `Result` 的字段上加

```java
@JsonInclude(JsonInclude.Include.NON_NULL)
private Map<String, String> fieldErrors;
```

加完后成功响应变成 `{code,message,data}`（少一个字段）。

**该不该做？**（关键在"想到了影响"）
> · 好处：响应更干净
> · ⚠️ 代价：**这是"改动响应格式"** —— 如果前端已经按 `body.fieldErrors === null` 判断过，
>   而现在字段**直接不存在**，可能导致 `undefined` 相关问题。
> · 结论：**能用，但要意识到"改格式是契约变更"，要与前端同步**。
>   本周项目自己玩无所谓，真实项目要走接口文档变更流程。

**批改**：只要学生提到"**这属于改接口格式/契约，要考虑前端**"即满分。

### 题 2：为什么 `/abc` 不走我们的处理器？

**答案**：异常**来源不同**。
> · `/sku/999`：是我们**自己的代码**在 `SkuService` 里 `throw ResourceNotFoundException` →
>   属于 SpringMVC **执行业务方法**期间的异常 → `@ExceptionHandler` 能接住。
> · `/abc`：是 SpringMVC 在**查找"哪个方法能处理这个 URL"**的阶段就找不到 →
>   抛 `NoResourceFoundException`/`NoHandlerFoundException`，此时**还没进入我们的 Controller**，
>   由 `BasicErrorController`（`/error`）接管，所以是自带格式。
>
> 想统一的话：Day32/33 会用 `NoHandlerFoundException` 的 handler 或自定义
> `ErrorController` 来解决。（能想到"来源不同/阶段不同"即满分）

### 题 3：Day30 写法 vs Day31 写法（⭐ 最重要的思考）

| 写法 | 要改几个文件 | 大概多少行 |
|---|---|---|
| Day30（每个接口自己判断） | **每个涉及该错误的接口都要改**（假设 3 个接口 → 3 个文件），且**状态码、JSON 拼装要重复写** | 每个接口 5~10 行 → **15~30 行**，且**极易漏改** |
| Day31（全局异常处理器） | **1 个文件**（甚至 0 个 —— 复用已有异常类时只改 Service 里 1 行 throw） | **1~3 行** |

**答对这题的核心**：
> 关键不是"少写代码"，而是"**加新功能时不会漏、不会不一致**"。
> Day30 的写法改 3 个接口，很可能漏了第 4 个；而且 3 处的 JSON 格式可能拼得不一样。
> Day31 只有一处，**格式必然统一**。

**批改**：只要学生答出"改动集中/不会漏/格式统一"其中一点即给满分；
只答"少写代码"给一半分。
