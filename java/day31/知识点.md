# Day 31 知识点：全局异常处理 + 统一响应

> 今天的主题只有一句话：**让"出错"也变成一种"规范的输出"**。
>
> Day30 你的 `/tasks/999` 返回了 **HTTP 200 + 一片空白** —— 调用方没法区分"没找到"和"服务器坏了"。
> 今天就把这个坑彻底填上，而且要做到**全项目只写一次**。

---

## 1. 先看清"没有异常处理"到底有多糟

Day30 的写法：

```java
@GetMapping("/{id}")
public Task one(@PathVariable Long id) {
    return taskRepository.findById(id).orElse(null);   // 找不到 → null
}
```

真机实测：`GET /tasks/999` → **HTTP 200**，响应体 **0 字节**。

**为什么这是灾难？** 站在前端角度想：

```js
const r = await fetch('/tasks/999');
if (r.ok) {                    // r.ok 是 true！状态码 200
    const data = await r.json();   // 💥 JSON 解析失败：响应体是空的
    render(data.title);            // 永远走不到
}
```

于是前端只能写这种代码：

```js
if (!r.ok || body === '' || body === null) { 猜是"没找到"还是"服务器炸了"？ }
```

**猜不出来。** 这就是"接口设计不合格"。

### 四种典型错误 + 它们该返回什么

| 场景 | Day30 返回 | 应该返回 |
|---|---|---|
| 查一个不存在的 id | `200` + 空白 | **404** + `{"code":"404","message":"SKU 不存在：id=999"}` |
| 传了负的价格 | 可能算出脏数据 | **400** + 明确指出**哪个字段**错 |
| 库存 3 件却要出库 100 | 库存变成 -97 | **409** + "库存不足：现有 3 件，你想出库 100 件" |
| 代码有空指针 | HTML 错误页 + 堆栈 | **500** + 笼统提示（堆栈只进日志） |

## 2. SpringBoot 自带的错误处理（先看默认的）

SpringBoot **不是完全不管** —— 它有一个 `BasicErrorController`，会给出默认错误响应。

⭐ 真机实测（本项目）：

```bash
GET /abc          # 一个不存在的地址
```

```json
{
  "timestamp" : "2026-10-08T11:42:45.106+00:00",
  "status" : 404,
  "error" : "Not Found",
  "message" : "No static resource abc.",
  "path" : "/abc"
}
```

**默认错误响应的缺点**（这就是我们要自己写的原因）：

| 缺点 | 说明 |
|---|---|
| ① 格式和我们成功的响应**不一样** | 成功是 `{code,message,data}`，出错是 `{timestamp,status,error,...}` → 前端要写两套 |
| ② 没有**业务码** | 前端只知道 HTTP 404，不知道是"用户不存在"还是"订单不存在" |
| ③ `message` 默认**是空的** | 得配 `server.error.include-message=always` 才显示（本项目已配） |
| ④ 业务逻辑的错误它管不了 | "库存不足"这种不是标准异常，默认处理器不认识 |
| ⑤ 如果是浏览器访问，会返回 **HTML 错误页** | 前端 `JSON.parse` 直接崩 |

> 📌 一句话：**自带的只能兜底，不能表达业务。**

## 3. 自定义异常：让"错误"变成"类型"

### 3.1 为什么不直接 `throw new RuntimeException("库存不足")`？

```java
throw new RuntimeException("库存不足");     // ❌
throw new ResourceNotFoundException("..."); // ✅
```

| 用 RuntimeException | 用自定义异常 |
|---|---|
| 全局处理器**分不清**是"没找到"还是"业务冲突" | 处理器按**类型**分派，清清楚楚 |
| 只能解析 message 字符串（改错别字就崩） | 类型就是契约 |
| 调用方看不出这个方法有几种错 | 一看异常类名就知道 |
| 想给不同的错配不同的 HTTP 状态码？做不到 | 异常自己带着状态码 |

### 3.2 本项目的异常体系（4 个类，加起来不到 80 行）

```
RuntimeException
  └── BaseException                  ← 带 业务码 code + HTTP 状态码 http
        ├── ApplicationException     通用业务异常（不想专门建类时用它）
        ├── ParamException           400 参数不合法
        ├── ResourceNotFoundException 404 东西不存在
        └── BizRuleException         409 请求合法但业务不允许
```

**核心在 `BaseException`**：

```java
public class BaseException extends RuntimeException {
    private final String code;
    private final int http;

    public BaseException(int http, String message) {
        super(message);                                  // ⭐ 交给父类，日志才能看到
        this.http = http;
        this.code = ResultCode.ofHttp(http).getCode();
    }
    public String getCode() { return code; }
    public int getHttp()    { return http; }
}
```

子类就一行有效代码：

```java
public class ResourceNotFoundException extends BaseException {
    public ResourceNotFoundException(String message) {
        super(ResultCode.NOT_FOUND.getHttp(), message);   // 404
    }
}
```

> ⭐ **为什么继承 `RuntimeException` 而不是 `Exception`？**
> `Exception` 是**受检异常**：谁调用谁就得 `throws` 或 try-catch，会污染一整条调用链的方法签名。
> `RuntimeException`（非受检）能"穿透"多层调用，直接被最外层的 `@RestControllerAdvice` 接住。
> **业务异常用 RuntimeException** —— 这是 Spring 项目的主流做法。

## 4. ⭐⭐⭐ 全局异常处理器：`@RestControllerAdvice`

### 4.1 它是什么

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BaseException.class)
    public ResponseEntity<Result<Void>> handleBase(BaseException e) {
        log.warn("业务异常：code={}, http={}, message={}", e.getCode(), e.getHttp(), e.getMessage());
        return ResponseEntity.status(e.getHttp())
                .body(Result.fail(ResultCode.ofHttp(e.getHttp()), e.getMessage()));
    }
}
```

| 注解 | 含义 |
|---|---|
| `@RestControllerAdvice` | `@ControllerAdvice`（给所有 Controller 加公共逻辑）+ `@ResponseBody`（返回值转 JSON） |
| `@ExceptionHandler(X.class)` | "X 类型的异常，交给我这个方法处理" |

**它和 try-catch 的本质区别**：

| | try-catch | @RestControllerAdvice |
|---|---|---|
| 写在哪 | **每个**可能出错的地方 | 全项目**一处** |
| 新增一种错 | 去改 N 个 Controller | Service 里 throw 一下，**完事** |
| 状态码 | 自己 `setStatus` | 异常自己带着 |
| 会漏吗 | 一定会漏（总有忘记的地方） | 兜底方法接住一切 |

> 📌 这个思想叫「**横切关注点（cross-cutting concern）抽离**」——
> 错误处理是"每个接口都要考虑、但和业务无关"的事，所以抽出来统一管。
> Day42 学 AOP 时你会看到它就是这么实现的（动态代理，你在 Day28 已经手写过了）。

### 4.2 ⭐ 为什么用 `ResponseEntity` 而不是直接 `return Result`？

这是今天**最容易写错的一处**：

```java
// ❌ 错误写法：状态码还是 200
@ExceptionHandler(BaseException.class)
public Result<Void> handle(BaseException e) {
    return Result.fail(...);      // 响应体对了，但 HTTP 状态码是 200！
}
```

那样就等于"**又回到了 Day30 的坑**"：前端看到 200 以为是成功。

```java
// ✅ 正确写法：同时控制状态码 + 响应体
return ResponseEntity.status(e.getHttp()).body(Result.fail(...));
```

`ResponseEntity` = **状态码 + 响应头 + 响应体** 三件套。

### 4.3 匹配规则：选"最具体"的那个

同时存在多个能处理的 handler 时，Spring 选**继承关系中最近的**：

```
ParamException（子类）  ← 优先
    ↓
BaseException（父类）
    ↓
Exception（最终兜底）    ← 最后
```

所以写法顺序是：**先具体，后兜底**。

### 4.4 兜底方法必须有（TODO①）

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<Result<Void>> handleOther(Exception e) {
    log.error("系统异常", e);                    // ⭐ 完整堆栈，只进日志
    return ResponseEntity.status(500)
            .body(Result.fail(ResultCode.SYSTEM_ERROR, "服务器开小差了，请稍后重试"));
}
```

**两个关键点**：

| 点 | 说明 |
|---|---|
| ① **必须打完整堆栈** `log.error("系统异常", e)` | 这是"出 bug 了"，不打堆栈线上根本没法查 |
| ② **绝对不能**把 `e.getMessage()` 返回给前端 | 真机实测的默认响应长这样：`Cannot invoke "com.xiaoming.day31.sku.Sku.getTitle()" because "sku" is null` —— **类名、方法名全暴露了**。如果是 SQL 异常，连表名、字段名、SQL 语句都会泄露 → 这是**安全漏洞** |

> ⭐ 记牢这条：**日志里要详细，返回给外面要笼统。**
> 用户看"服务器开小差了"，你在日志里看完整堆栈 —— 两边都满意。

## 5. 统一响应体 `Result<T>`

所有接口（**成功和失败**）都返回同一个"信封"：

```json
{ "code" : "200", "message" : "操作成功", "data" : { ... }, "fieldErrors" : null }
```

### 5.1 为什么成功也要包一层？

有人觉得"成功就直接返回数据不好吗"。统一包一层的理由：

| 理由 | 说明 |
|---|---|
| 前端只写一套解析逻辑 | `if (body.code !== '200') 弹错误提示 else 用 body.data` |
| 有地方放业务码和提示语 | 直接返回数据的话，错误信息往哪塞？ |
| 以后加东西不用改前端 | 想加 `requestId`（排查用）、`timestamp`、分页信息，加在信封上即可 |

### 5.2 ⭐ HTTP 状态码 vs 业务码：两者都要有

这是新手最容易糊涂的地方 —— **它们是两个层次的东西**：

| | HTTP 状态码 | 业务码 `code` |
|---|---|---|
| 谁看 | 浏览器、网关、Nginx、监控系统、日志 | **前端业务代码** |
| 粒度 | 粗（404 就是"没有"） | 细（"40401 用户不存在" / "40402 订单不存在"） |
| 作用 | 让基础设施知道成功还是失败 | 让前端知道该弹什么、跳哪个页面 |

**本项目简单起见，两者取了一样的值（"404"/"409"）**。真实项目里业务码通常更细：

```
HTTP 404 + code "40401" → 用户不存在
HTTP 404 + code "40402" → 商品不存在
HTTP 409 + code "40901" → 库存不足
HTTP 409 + code "40902" → 订单状态不允许取消
```

> 💡 为什么要这么细？前端要"库存不足"时跳去补货页、"订单状态"错时提示联系客服 ——
> 只看 HTTP 404 是分不出来的。

## 6. 400 / 404 / 409 到底怎么选（⭐ 最常混）

```
┌────────┬──────────────────────────┬──────────────────────────────┐
│ 状态码 │ 什么错                    │ 例子                          │
├────────┼──────────────────────────┼──────────────────────────────┤
│ 400    │ 请求本身就不合法           │ price=-5、id=abc              │
│        │ （改请求就能通过）          │ → 前端该拦在输入框里           │
├────────┼──────────────────────────┼──────────────────────────────┤
│ 404    │ 东西不存在                 │ 查 id=999 的 SKU              │
│        │ （地址/ID 错了）            │ → 改 ID 就能通过               │
├────────┼──────────────────────────┼──────────────────────────────┤
│ 409    │ 请求合法，但违反业务规则     │ 库存 3 件要出库 100 件         │
│        │ （得先改变现实才能通过）     │ → 先去进货再重试，重试没用      │
├────────┼──────────────────────────┼──────────────────────────────┤
│ 500    │ 我们的代码出 bug 了         │ 空指针、数组越界               │
│        │ （跟调用方无关）            │ → 必须改代码                   │
└────────┴──────────────────────────┴──────────────────────────────┘
```

**记忆口诀：**
> **400 是"你说的不对"，404 是"你要的没有"，409 是"现在不行"，500 是"我的锅"。**

真机实测对照（本项目 `/sku/outbound`）：

| 请求 | 状态码 | message |
|---|---|---|
| `?id=1&count=0` | **400** | `出库数量必须大于 0，你传的是 0` |
| `?id=999&count=1` | **404** | `SKU 不存在：id=999` |
| `?id=2&count=100` | **409** | `库存不足：「Java 并发编程实战」现有 3 件，你想出库 100 件` |

## 7. 参数校验失败：`@Valid` + `fieldErrors`

### 7.1 两个层次都要校验

| 层次 | 手段 | 作用 |
|---|---|---|
| **接口层** | `@Valid @RequestBody SkuForm` + `@NotBlank/@Min` | 快速拦掉明显的脏数据，**在进入业务之前** |
| **Service 层** | 手写 `if` + throw | ⭐ **最后一道防线**（定时任务、内部调用会绕过接口层） |

```java
public class SkuForm {
    @NotBlank(message = "书名不能为空")
    private String title;

    @NotNull(message = "价格不能为空")
    @Min(value = 0, message = "价格不能小于 0")
    private Integer price;
}
```

> ⚠️ SpringBoot 3 用的是 **`jakarta.validation`**，不是老教程里的 `javax.validation` —— 用错包注解**完全不生效且不报错**。

### 7.2 ⭐ 为什么错误要按字段收集，而不是拼成一句话

真机实测 `POST /sku` 传 `{"title":"","price":-1,"stock":null}`：

```json
{
  "code" : "400",
  "message" : "参数校验失败，请看 fieldErrors",
  "data" : null,
  "fieldErrors" : {
    "price" : "价格不能小于 0",
    "stock" : "库存不能为空",
    "title" : "书名不能为空"
  }
}
```

**关键**：前端拿到 `fieldErrors` 就能把红字**标在对应输入框旁边**：

```js
for (const [field, msg] of Object.entries(body.fieldErrors)) {
    document.querySelector(`#${field}-error`).textContent = msg;
}
```

如果拼成 `"书名不能为空,价格不能小于0"` 一句话，前端还得自己切字符串 —— **接口设计要替调用方想**。

`MethodArgumentNotValidException` 的处理：

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<Result<Void>> handleValidation(MethodArgumentNotValidException e) {
    Map<String, String> errors = Result.fieldErrors();
    e.getBindingResult().getFieldErrors().forEach(fe ->
            errors.putIfAbsent(fe.getField(), fe.getDefaultMessage()));   // getDefaultMessage() = 注解里写的
    return ResponseEntity.status(400)
            .body(Result.failFields(ResultCode.PARAM_ERROR, "参数校验失败，请看 fieldErrors", errors));
}
```

## 8. 分层：Service 才是"抛异常"的地方

Day30 你把业务逻辑写在 Controller 里（能跑）。今天的正确分层：

```
Controller  → 收请求、包结果、**不写业务规则、不 try-catch**
Service     → 业务规则 + 校验 + 抛异常   ← 今天的异常全在这里
Repository  → 只管存取数据
```

**怎么判断一段逻辑该放哪？**

> 问自己："这条规则**离开了 HTTP 还成立吗**？"
> "库存不够不能出库" —— 定时任务调用也成立 → **属于业务 → 放 Service**。
> "请求头缺 token 要 401" —— 离开 HTTP 没意义 → **放 Controller/拦截器**。

**Service 的编码风格：不返回错误，直接 throw**

```java
public Sku outbound(Long id, int count) {
    if (count <= 0) {
        throw new ParamException("出库数量必须大于 0，你传的是 " + count);   // 400
    }
    Sku sku = getById(id);            // ← 不存在就在里面抛 404（复用，不用重复写判空）
    if (sku.getStock() < count) {
        throw new BizRuleException("库存不足：「" + sku.getTitle() + "」现有 " + sku.getStock() + " 件，你想出库 " + count + " 件");
    }
    sku.decreaseStock(count);
    return sku;                        // ⭐ 正常路径：只写"成功"的代码，看不到错误处理
}
```

⭐ 看这个方法的可读性：**主干逻辑只有 3 行**，错误全在 `if` 里 throw 掉了。
对比"返回错误码"的写法（每步都要 `if (result != null) return result;`）—— 差得很远。

## 9. 日志：什么级别、打什么

| 情况 | 级别 | 打不打堆栈 | 例子 |
|---|---|---|---|
| 业务异常（预期内） | `warn` | **不打**（太吵） | 库存不足、找不到 |
| 系统异常（意料外） | `error` | **必打** | 空指针、SQL 异常 |
| 请求入口 | `info`/`debug` | 不打 | 哪个请求进了哪个接口 |

```java
log.warn("业务异常：code={}, http={}, message={}", e.getCode(), e.getHttp(), e.getMessage());
log.error("系统异常", e);     // ⭐ 异常对象作为**最后一个参数**，日志框架会自动打完整堆栈
```

> ⚠️ 别写 `log.error("系统异常：" + e.getMessage())` —— 这样**堆栈就丢掉了**，线上排查等于瞎。
> 正确姿势：`log.error("系统异常", e);`（异常当参数传）

## 10. 今天的完整数据流（一张图记住）

```
        ┌─────────── 正常路径 ───────────┐
浏览器 → Controller → Service → 返回数据 → Result.ok(data) → 200 + {code:"200",data:...}
        └────────────────────────────────┘

        ┌─────────── 出错路径 ───────────┐
浏览器 → Controller → Service → throw XxxException
                                       ↓（一路穿透，Controller 不用管）
                          @RestControllerAdvice
                                       ↓ 按异常**类型**选 handler
                              log（warn/error）
                                       ↓
                    ResponseEntity.status(异常带的 http)
                                       ↓
             404/400/409/500 + {code, message, data:null}
```

## 12. 常见坑

| 坑 | 现象 | 解决 |
|---|---|---|
| handler 返回类型写成 `Result` | HTTP 状态码永远是 200 | 用 `ResponseEntity.status(...)` |
| 兜底 handler 写成 `@ExceptionHandler(Throwable.class)` | 太宽，会把 Spring 内部异常也吞掉 | 用 `Exception.class` |
| 忘了兜底 handler | 出错返回 HTML 错误页 / 泄露堆栈 | 一定要写 `Exception.class` 那个 |
| 把 `e.getMessage()` 返回给前端 | 泄露类名/SQL/表名（**安全漏洞**） | 日志里详细、外面笼统 |
| 用了 `javax.validation` | 校验**完全不生效且不报错** | SpringBoot 3 要用 `jakarta.validation` |
| 子类异常忘了 `super(message)` | 日志里 message 是 null | 构造方法第一行 `super(message)` |
| 在 Controller 里 try-catch 后返回统一格式 | 全局处理器形同虚设，代码又变脏 | Service throw，Controller 不 catch |
| `@ExceptionHandler` 方法写成 `private` | Spring 不调用它 | 必须是 `public` |
