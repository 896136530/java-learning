## 第 3 步（代码 ⭐⭐）：TODO① —— 写兜底处理器

**文件**：`src/main/java/com/xiaoming/day31/common/exception/GlobalExceptionHandler.java`

**现状**：这个类里已经有 2 个 handler（业务异常、校验失败），**唯缺兜底的那个**。
所以现在 `/sku/boom` 返回的是 SpringBoot 自带的错误页。

**要求**：加一个方法，处理 `Exception.class`（所有异常的最终兜底）：

| 要求 | 细节 |
|---|---|
| ① 注解 | `@ExceptionHandler(Exception.class)` |
| ② **打完整堆栈** | `log.error("系统异常", e);` ← 异常对象当**最后一个参数** |
| ③ 返回 500 | `ResponseEntity.status(500)` |
| ④ 消息**要笼统** | `"服务器开小差了，请稍后重试"` |
| ⑤ ⚠️ **绝对不用** `e.getMessage()` | 会泄露类名/SQL/表名（安全漏洞） |
| ⑥ 方法必须是 `public` | 写成 private Spring 不会调用 |

**参考写法**（照抄上面那个 `handleBase` 改）：

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<Result<Void>> handleOther(Exception e) {
    log.error("系统异常", e);                       // ← 完整堆栈只进日志
    return ResponseEntity.status(500)
            .body(Result.fail(ResultCode.SYSTEM_ERROR, "服务器开小差了，请稍后重试"));
}
```

**验收**：

```bat
curl -i http://localhost:8080/sku/boom
```

**期望**：状态码 **500**，响应体是**统一格式的 JSON**（不再是 SpringBoot 自带的那种），
且 `message` 里**看不到**任何类名/方法名。

> ⚠️ 改完**必须重启**（`Ctrl+C` 停掉再选 1）—— Java 代码改了不会热生效。

## 第 7 步（代码 ⭐⭐⭐）：TODO② —— 自己加一种新错误

**背景**：现在 `SkuService.delete(id)` 是这样的：删不存在的 → 抛 404。

```
DELETE /sku/999   → 404 SKU 不存在
```

**新需求**（来自"业务方"）：

> 库存为 0 的 SKU **可以删**（反正没货了）。
> 但**库存大于 0 的 SKU 不许删** —— 得先把货处理掉，否则会"突然少了一批货"。
> 删这种 SKU 应该返回 **409**，提示：`「书名」还有 N 件库存，不能删除`

**要做的**：

| 步骤 | 位置 | 做什么 |
|---|---|---|
| ① | `SkuService.delete(Long id)` | 删之前先判断库存，`> 0` 就 `throw new BizRuleException(...)` |
| ② | （提示）| 用 `getById(id)` 先拿到对象 —— **它自己会处理"不存在"的情况**，不用你重复写判空 |

**验收**：

```bat
rem ① 库存 10 的不能删 → 期望 409
curl -i -X DELETE http://localhost:8080/sku/1

rem ② 库存 0 的能删 → 期望 200
curl -i -X DELETE http://localhost:8080/sku/3

rem ③ 不存在的 → 期望 404
curl -i -X DELETE http://localhost:8080/sku/999
```

**⚠️ 想清楚这件事再动手**：为什么这个需求**不用改 `GlobalExceptionHandler`**？

（答：因为它是**业务规则冲突**，复用现成的 `BizRuleException`（409）就够了 ——
**这就是异常体系的价值：新增一种错误，只需要在 Service 里 throw 一下，状态码和 JSON 格式自动就对了**。
对比一下：如果没有全局处理器，你得去 `delete` 接口里手写状态码和错误 JSON。）
